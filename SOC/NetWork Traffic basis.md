# DNS Tunneling and Beaconing 
Пример DNS тунеллинга:

```bash
2025-10-03 09:15:23    SRC=192.168.1.16      QUERY=aj39skdm.malicious-tld.com    QTYPE=A      
2025-10-03 09:15:31    SRC=192.168.1.16      QUERY=msd91azx.malicious-tld.com    QTYPE=A     
2025-10-03 09:15:45    SRC=192.168.1.16      QUERY=cmd01.malicious-tld.com       QTYPE=TXT     
2025-10-03 09:15:45    SRC=192.168.1.16      QUERY=cmd01.malicious-tld.com       QTYPE=TXT     
```

обращается на один адрес с разными поддоменами которые выглядят подозрительно
Базируясь на логах DNS мы можем извлечь следующую информацию
- Запросы и тип запросов 
- Поддомены и top-level домены, мы можем проверить в инструментах таких как abuseDB или VirusTotal для проверки если домен опасен
- Host IP, мы можем идентифицировать систему отправляющую хост запросы
- Destion IP, проверить адрес назначения с помощью как [AbuseIPDB(opens in new tab)](https://www.abuseipdb.com/) или [VirusTotal(opens in new tab)](https://virustotal.com/) чтобы понять помечен ли он как опасный
- TimeStamp мы можем построить временную линию подозрительных запросов

Логи днс не содержат информации больше чем это, так что сложно сделать заключение основываясь только на этой информации, нам нужно проверить dns трафик более глубоко и проверить контент в DNS запросах и ответах, все это позволит нам определить характер запросов и ответов

Далее представлен пример который показывает почему нам нужен анализ трафика. Firewalls и другие устройства логируют DNS запросы и их ответы но их содержимое. Злоумышленники могли например использовать использовать TXT записи чтобы отсылать Command and Control инструкции для компрометации системы. Мы можем исследовать это для проверки содержимого DNS запросов. Пакеты захваченные нижк содержат фрагменты C2 команд

# Почему мы должны анализировать сетевой трафик?
Определенно мы будем использовать анализ трафика для

- Мониторинга сетевой производительности
- Проверки на аномалии в сети и так далее, например внезапные скачки производительности, замедление сети и т.д.
- Проверка содержимого подозрительных коммуникаций, внешних и внутренних, например: эксфильтрация через DNS, скачивание опасных ZIP файлов через HTTP, боковое перемещение и так далее

Для SOC  в перспективе анализ трафика помогает

- Определять подозрительную и опасную активность
- Реконструировать атаки во время реагирования на инцидент
- Проверять и валидировать алерты

Ниже приведены два сценария которые иллюстрируют важность анализа трафика:

- Основываясь на логах конечного пользователя было установлено что в 16 система начала отклоняться от своего нормального поведения Анализируя сетевой трафик, поступающий в эту систему и исходящий из нее мы обнаружили подозрительный HTTP запрос и смогли извлечь подозрительный ZIP файл
- Мы получили предупреждение о том, что система конечного пользователя отправляет гораздо больше DNS запросов чем базовый уровень сети. После проверки DNS запросов мы обнаружили что данные передаются с использованием метода, называемого DNS туннелированием

# Приложения (Application)
На уровне приложений мы можем найти две важные информационные структуры, это: application header information и application data itself (payload), эта информация будет меняться в зависимости от использования протокола прикладного уровня. Ниже приведен пример с HTTP

```http
GET /downloads/suspicious_package.zip HTTP/1.1
Host: www.tryhackrne.thn
User-Agent: curl/7.85.0
Accept: */*
Connection: close
```

Здесь представлены заголовки клиентского GET и ответа сервера. Большинство прокси и firewalls логируют эти заголовки. Что они не логируют так это application дата или payload. Из GET запроса мы можем выделить что клиент запросил файл названный `suspicious_package.zip`, сервер ответил кодом 200 что означает что запрос обработан корректно. Однако в логах не будет видно содержимого ZIP файла

```http
HTTP/1.1 200 OK
Date: Mon, 29 Sep 2025 10:15:30 GMT
Server: nginx/1.18.0
Content-Type: application/zip
Content-Length: 10485760
Content-Disposition: attachment; filename="suspicious_package.zip"
Last-Modified: Mon, 29 Sep 2025 09:54:00 GMT
ETag: "5d8c72-9f8a1c-3a2b4c"
Accept-Ranges: bytes
Connection: close

[binary ZIP file bytes follow — 10,485,760 bytes]
```
## Транспортный (Transport)
С уровня приложения данные и заголовки сегментируются и инкапсулируются на транспортный уровень в маленькие куски. Каждый кусок включает транспортный заголовок, в большинстве своем это TCP или UDP. Вот пример как выглядят логи firewall для этого уровня

```bash
2025-10-13 09:15:32 ACCEPT TCP src=192.168.1.45 dst=172.217.22.14 sport=51432 dport=443 flags=SYN len=60
2025-10-13 09:15:32 ACCEPT TCP src=172.217.22.14 dst=192.168.1.45 sport=443 dport=51432 flags=SYN,ACK len=60
```

Логи Firewall часто включают source and destination порты и флаги, но большинство других полей часто не включены. Однако они полезны для обнаружения определенных типов атак, таких как перехват сессии(session hijacking). Session hijacking может быть задектирован с помощью анализа **sequence numbers**, включенных в заголовок. Если номера заголовков неожиданно стали далеко друг от друга, тогда необходимо провести дальнейшее расследование. Ниже показан пример дампа такого трафика

```
No.     Time        Source          Destination     Protocol Length  Info
1       0.000000    192.168.1.45    172.217.22.14   TCP      74      51432 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460
2       0.000120    172.217.22.14   192.168.1.45    TCP      74      80 → 51432 [SYN, ACK] Seq=0 Ack=1 Win=65535 Len=0 MSS=1460
3       0.000220    192.168.1.45    172.217.22.14   TCP      66      51432 → 80 [ACK] Seq=1 Ack=1 Win=64240 Len=0
4       0.010500    192.168.1.45    172.217.22.14   TCP      1514    51432 → 80 [PSH, ACK] Seq=1 Ack=1 Win=64240 Len=1460
5       0.010620    172.217.22.14   192.168.1.45    TCP      66      80 → 51432 [ACK] Seq=1 Ack=1461 Win=65535 Len=0
6       0.020100    192.168.99.200  172.217.22.14   TCP      74      51432 → 80 [PSH, ACK] Seq=34567232(номер намного больше чем предыдущий) Ack=1 Win=64240 Len=20  
```

- 1-3 показывают процесс нормального трехстороннего рукопожатия для TCP 
- 4-5 показывают легитимную пересылку данных
- 6 показывает пакет из другого ресурса который пытается самоинжектироваться в сессию, потому что слишком большой прыжок в sequnce number
## Интернет(Internet)
Когда транспортный уровень отправляет сегмент ниже, уровень интернета так же добавляет заголовок. Если сегмент больше чем `Maximum Transmission Unit (MTU)` он будет разбит на фрагменты и заголовки будут добавлены к каждому из них. Поля которые чаще всего логируются это source и destination IP и TTL, и для большинства случаев этого вполне достаточно. Но если мы хоти например увидеть фрагменты атаки, нам нужно проверить поля смещения фрагмента (fragment offset) и длину (total length). Существуют различные вариации атаки фрагментации. Например атакующий может создать маленькие фрагменты для обхода IDS или нарушить сборку фрагментов используя перекрывающие диапазоны байт. Пример ниже иллюстрирует перекрывающие диапазоны байт. Смещение в строке 3 перекрывается со смещением в строке 2. Это означает, что весь пакет может быть собран тем или иным способ. Злоумышленники могут использовать этот метод для обхода IDS

```
No.   Time       Source        Destination   Protocol Length Info
1     0.000000   203.0.113.45  192.168.1.10  UDP      1514    Fragmented IP protocol (UDP) (id=0x1a2b) [MF] Offset=0, Len=1480
2     0.000015   203.0.113.45  192.168.1.10  UDP      1514    Fragmented IP protocol (UDP) (id=0x1a2b) [MF] Offset=1480, Len=1480
3     0.000030   203.0.113.45  192.168.1.10  UDP       600    Fragmented IP protocol (UDP) (id=0x1a2b) Offset=1480, Len=64   <-- Overlap
4     0.000045   192.168.1.10  203.0.113.45  ICMP      98     Destination unreachable (Fragment reassembly time exceeded)
```

то есть фрагмент 2 и фрагмент 3 претендуют на одни и те же байты, такая атака называется фрагментацией

| Фрагмент | Offset | Len  |      Занимает байты      |
| :------: | :----: | :--: | :----------------------: |
|    1     |   0    | 1480 |          0–1479          |
|    2     |  1480  | 1480 |        1480–2959         |
|    3     |  1480  |  64  | **1480–1543** ← конфликт |
Почему это атака на IDS
При пересборке OC должна решить: чьи байты победят на этом участке 1480-1543 - фрагмента 2 или фрагмента 3

- BSD/Windows побеждает первый пришедший фрагмент, то есть фрагмент 2
- В Linux побеждает последний пришедший фрагмент, то есть фрагмент 3

IDS может пересобрать по одной логике а IDS по другой, соответственно атакующий кладет в фрагмент 2 безобидный payload а в фрагмент 3 вредоносный. Если жертва использует Linux, то она подставит байты из фрагмента 3 поверх фрагмента 2
## Канальный(Link)
После завершения инкапсуляции на интернет уровне IP пакет отправляется на канальный уровень. Канальный уровень так же добавляет свой заголовок содержащий больше адресной информации. Большинство логов отобразят source и destination MAC адреса. Для определенной части атак, например ARP poisoning или spoofing, информации из логов будет недостаточно. Для этого типа атак нам нужен полный packet и context. Например в логах нельзя увидеть, когда MAC адрес появляется в нескольких интерфейсах или когда отправляется множество нежелательных ARP пакетов конфликтующих с MAC адресами. Ниже пример которые показывает ARP poisoning attack. Host с IP 192.168.1.200 на каждый ARP запрос отвечает одним и тем же MAC адресом 

```
No.   Time       Source           Destination      Protocol Length Info
1     0.000000   192.168.1.1      Broadcast        ARP      60     Who has 192.168.1.10? Tell 192.168.1.1
2     0.000025   192.168.1.10     192.168.1.1      ARP      60     192.168.1.10 is at 00:11:22:33:44:55
3     1.002010   192.168.1.200    192.168.1.1      ARP      60     192.168.1.10 is at aa:bb:cc:dd:ee:ff  <-- Attacker spoof
4     1.002015   192.168.1.200    192.168.1.10     ARP      60     192.168.1.1 is at aa:bb:cc:dd:ee:ff  <-- Attacker spoof
5     1.100000   192.168.1.10     172.217.22.14    TCP      74     54433 → 80 [SYN] Seq=0 Win=64240 Len=0
6     1.100120   192.168.1.200    172.217.22.14    TCP      74     54433 → 80 [SYN] Seq=0 Win=64240 Len=0  <-- Relayed via attacker
```

# Потоки и источники
Корпоративная сеть имеет определенные сетевые потоки и источники. 
Мы можем разделить источники на две категории:

- Промежуточные
- Конечные точки

Потоки так же можно разделить на две категории:

- Север-юг: трафик который выходит из локальной сети или входит в нее и проходит через межсетевой экран
- Восток-запад: трафик который остается внутри локальной сети(включая локальную сеть которая распространяется за облако)
