Атакующие целятся в сервисные аккаунты через Keberoasting потому что у них часто слабые пароли и высокие привилегии. Сервисный SQL аккаунт запущенный под Domain Admin дает атакующему полный контроль над доменом в момент взлома пароля. При этом сама атака требует не больше чем обычная учетная запись доменного пользователя
# Как аккаунты становятся уязвимыми к Kerberoasting
Когда пользователю нужен доступ к сервису в AD он запрашивает билет Kerberos TGS у DC. DC ищет шифрует билет хэшем пароля сервисного аккаунта и возвращает его. В норме пользователь предъявляет билет сервису и сервис расшифровывает его для верификации личности.

Вся проблема в том что любой доменный пользователь может запросить сервисный билет для любого SPN в домене. DC не проверяет действительно ли пользователь намерен обращаться к сервису - он просто выдает билет. Атакующий берет этот билет и взламывает шифрование локально. Если у сервисного аккаунта слабый пароль, атакующий получает его в открытом виде

![[Pasted image 20260618130027.png]]

Обнаружение такой атаки сосредоточено на событии 4769(Kerberos Service Ticket Requested) которое регистрируется контроллером домена при обработке TGS-Req. В современных AD по умолчанию используется AES-256(0x12) для билетов Kerberos. Большинство инструментов обнаружения уязвимостей Kerberos, такие как Rubeus и GetUserSPN.py понижают уровень шифрования до RC3 (0x17) поскольку хэши RC4 взламываются быстрее. Запрос TGS c Ticket_Encryption_Type=0x17 в среде которая использует AES сильный идентификатор обнаружения. 

Вот какие поля важны для события 4769 для обнаружения Keberoasting

| Поле                   | Что содержит                              | Почему это важно                                                     |
| ---------------------- | ----------------------------------------- | -------------------------------------------------------------------- |
| Service_Name           | Какой сервис был запрошен то есть его SPN | Идентифицирует какой сервисный аккаунт выбран целью                  |
| Ticket_Encryption_Type | 0x12(AES) или 0x17(RC4)                   | запросы RC4 являются основным сигналом Kerberoasting                 |
| Account_Name           | аккаунт который запросил билет            | идентифицирует скомпрометированного пользователя который начал атаку |
| Client_Address         | IP адрес источника запроса                | Идентифицирует машину атакующего                                     |

> [!warning] ВАЖНО!!!!
> `Client_Address` в событии 4769 часто использует IPv6 сопоставленное с IPv4. Заместо отображения `10.5.90.1` это поле показывает `::ffff:10.5.90.1`

# Поиск атаки Kerberoasting
Нормальный Kerberos трафик включает в себя множество событий 4769. Аккаунты компьютеров оканчивающихся на `$` и krbtg запросы создают большой шум как часть обычной доменной активности. Мы исключаем оба варианта, чтобы сосредоточиться на учетных записях служб, которые могут стать целями атаки kerberoasting. Нас основной фильтр - `Ticket_Encryption_Type=0x17`, поскольку это сигнал понижения версии RC4. На диаграмме ниже сравниваются шаблоны TGS с атакой Kerberoasting

![[Pasted image 20260618133304.png]]

```
index=task2 EventCode=4769 Ticket_Encryption_Type=0x17 Service_Name!="*$" Service_Name!="krbtgt" 
| table _time, Account_Name, Service_Name, Ticket_Encryption_Type, Client_Address 
| sort _time
```

![[Pasted image 20260618133320.png]]

Множество TGS запросов с RC4 шифрованием, все от одного аккаунта, нацеленные на разные сервисные аккаунты с коротким временным окном. Этот паттерн это указатель на Kerberoasting. 

Для ответа на вопросы: сколько учетных записей стало целью атаки, с какой учетной записи была совершена атака и откуда она исходила

```
index=task2 EventCode=4769 Ticket_Encryption_Type=0x17 Service_Name!="*$" Service_Name!="krbtgt" 
| stats dc(Service_Name) as targeted_services count by Account_Name, Client_Address
```

Следующий приоритет при сортировке - уровень привилегий целевых учетных записей. Если какие либо из этих служебных учетных записей входят в привилегированные группы, злоумышленник может уже иметь доступ на уровне домена после взлома хэша. Это отличает оповещение от активного взлома домена.

Следующий запрос группирует запросы TGS в 5 минутные окна и помечает любую учетную запись, которая запросила билеты более чем для 5 уникальных учетных записей служб в течении этого окна

```
index=task2 EventCode=4769 Service_Name!="*$" Service_Name!="krbtgt" | bin _time span=5m 
| stats dc(Service_Name) as unique_spns count by Account_Name, Client_Address, _time 
| where unique_spns > 5
```

# Обнаружение AS-Rep Roasting
AS-Rep Roasting нацелен на учетные записи с отключенной предварительной аутентификацией. Для этого не требуется SPN и в отличие от Kerberoasting злоумышленнику не нужны валидные учетные данные для выполнения атаки. Основная уязвимость та же что и в Kerberoasting: контроллер домена возвращает зашифрованный материал, который злоумышленник может взломать в автономном режиме, чтобы восстановить пароль в открытом виде. Разница заключается в том, что побуждает контроллер домена передать данные и чем он зашифрован.

При обычной аутентификации Kerberos когда пользователь запрашивает TGT, контроллер домена сначала требует доказать, что пользователь знает свой пароль. Для этого пользователь шифрует временную метку с помощью хэша своего пароля и отправляет ее вместе с запросом AS-REQ. Контроллер домена расшифровывает полученные данные, проверяет, что временная метка является актуальной и только после этого выдает TGT. При этом DC регистрирует событие 4768 (Kerberos TGT Request) со значением `Pre_Authentication_Type=2`, затем событие 4769, когда пользователь запрашивает сервисный билет(serviceticket) и событие 4624 когда пользователь выполняет вход на целевой сервис. На схеме ниже показан процесс:
![[Pasted image 20260618141022.png]]

С другой стороны когда у аккаунта стоит `DONT_REQUIRE_PREAUTH`, DC пропускает шаг верификации. Эта атака отправляет TGT не проверяя предварительно знает ли тот кто запросил свой пароль. Возвращаемый AS-REP зашифрован хешем пароля учетной записи, что означает, что злоумышленник может получить к нему доступ извне и взломать его, чтобы восстановить пароль в открытом виде. Злоумышленнику даже не нужна действующая учетная запись домена. Ему достаточно знать имена пользователя учетной записи с отключенной предварительной аутентификацией. ![[Pasted image 20260618141419.png]]

Эта ошибка конфигурации существует из-за того, что некоторые устаревшие приложения такие как старые ERP или системы расчета заработной платы не проходят аутентификацию Kerberos, если для их служебной учетной записи включена предварительная аутентификация. Чтобы заставить такое приложение работать, администраторы могут отключить preauth для сервисной учетной записи а затем забыть об этом

Ключевое отличие AS-Rep Roasting от обычного процесса аутентификации заключается в том, что злоумышленник запрашивает TGT исключительно для получения хэша, который можно подобрать офлайн. Он никогда не запрашивает сервисный билет. Поэтому контроллер домена регистрирует событие 4768 с параметром `Pre_Authentication_Type=0`, однако события 4769 и 4624 отсутствуют

![[Pasted image 20260618142154.png]]

На что следует обратить внимание так это `Pre_Authentication_Type=0` и RC4 шифрование

и если их нет, в этом случае TGT был запрошен для взлома в автономном режиме а не для доступа к сервису, хотя это не является окончательным доказательством.

Легитимное приложение все еще могло бы воспроизвести подобную схему, если бы оно завершилось с ошибкой до запроса сервисного билета, использовало ранее кешированный билет или по другой причине не выполнило стандартный процесс аутентификации Kerberos до конца Тем не менее, если это же событие содержит `Pre_Authentication_Type=0` и использует RC4 отсутствие каких-либо последующих событий значительно повышает вероятность того что активность носит вредоносный характер

# Обнаружение дампа кред через LSASS
Дамп LSASS это метод прямой кражи учетных данных, который выполняется на конечной точке, где эти данные хранятся и для его обнаружения требуется совершенно иной подход.

Злоумышленники целятся на LSASS (Local Security Authority Subsystem Service), поскольку этот процесс хранит учетные данные всех пользователей аутентифицировавшихся на данном компьютере. Если администратор домена ранее в течение дня входил в рабочую станцию его NTLM - и билеты Kerberos находятся в памяти LSASS. Злоумышленник, сделавший дамп LSASS на этой машине немедленно получает эти учетные данные без какого либо взлома.

Если первый этап атаки с Kerbreroasting и AS-Rep Roasting не имеет нужных прав то существует несколько путей что делать дальше один из вариантов

Найти машину на которой есть активный сеанс DA(Domain Admin) или любой другой учетной записи с повышенными привилегиями. Дамп LSASS будет следующим этапом
## Что хранит LSASS
LSASS содержит различные типы учетных данных в зависимости от версии Windows и ее конфигурации

- NTLM хэши паролей для всех аутентифицированных пользователей
- Билеты Kerberos (TGT и TGS) для активных сеансов
- Пароли в открытом виде в системах где включен WDigest(Windows 8 / Server 2012 и более ранние версии. Либо более новые в которых параметр реестра `UseLogonCredential` установлен в 1)
- Кэшированные доменные учетные данные для автономного входа

## Обнаружение Sysmon Event 10
Sysmon event 10 (Process Access) показывает когда один процесс открывает дескриптор другого процесса. Когда такие инструменты как Mimikatz или ProcDump получают доступ к `lsass.exe` Sysmon записывает какой процесс это сделал, какой уровень доступа он запрашивал и стек вызовов, который привел к доступу.


> [!warning] ВАЖНО!!!
> Sysmon Event ID 10 регистрирует доступ к процессу только в том случае если конфигурация Sysmon включает явные правила ProcessAccess нацеленные на `lsass.exe`. Стандартная установка Sysmon не регистрирует эти события. Если в вашей среде используется минимальная конфигурация Sysmon, дамп lsass будет невидим для Sysmon

Поля используемые для детектирования 

| Поле          | Что содержит                                                | Почему это важно                                                                                       |
| ------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| SourceImage   | полный путь процесса получившего доступ к lsass             | идентифицирует инструмент который использовался для дампа                                              |
| SourceUser    | учетная запись от имени которой запущен процесс источник    | идентифицирует скомпрометированный аккаунт. SYSTEM - ожидаемо<br>доменная учетная запись подозрительно |
| TargetImage   | Полный путь целевого процесса<br>(lsass.exe)                | подтверждает что целью был LSASS                                                                       |
| GrantedAccess | Шестнадцатеричная маска доступа с запрошенными разрешениями | Разные инструменты запрашивают разные уровни доступа                                                   |
| CallTrace     | Стек вызовов DLL, приведший к обращению                     | Раскрывает использованный метод (MiniDump API, инъекция и прочие)                                      |
### Понимание поля GrantedAccess
`GrantedAccess` это hex битовая маска созданная путем суммирования прав доступа отдельных процессов. Понимание того как формируются эти значения поможет вам при работе с незнакомой маской доступа.

| Право доступа                     | Hex      | Назначение                                |
| --------------------------------- | -------- | ----------------------------------------- |
| PROCESS_QUERY_LIMITED_INFORMATION | 0x1000   | Запросить базовую информацию о процессе   |
| PROCESS_QUERY_INFORMATION         | 0x0400   | запросить детальную информацию о процессе |
| PROCESS_VM_READ                   | 0x0010   | Читать память процесса                    |
| PROCESS_ALL_ACCESS                | 0x1FFFFF | Полный доступ к процессу                  |
Например 
0x1010= `0x1000` (PROCESS_QUERY_LIMITED_INFORMATION) + `0x0010` (PROCESS_VM_READ). `0x0010` - критичный бит, именно он позволяет читать память LSASS и извлекать оттуда учетные данные
Сигнатуры для инструментов:
- 0x1010 - Mimikatz
- 0x1FFFFF - ProcDump, comsvcs.dll, Task Manager
### Понимание поля CallTrace
показывает цепочку dll вызовов которые использовались для доступа к LSASS и он может различаться в зависимости от метода дампа

- Known DLLS такие как dbcore.dll и dbghelp.dll они указывают на MiniDump API использование. Это как ProcDump и `comsvcs.dll` создают дампы памяти. это легитимные API которые используются во вредоносных целях 
- Неизвестные смещения памяти(адреса не сопоставленные ни с одним известным DLL файлом) указывают на вредоносный код. Это сигнатура маяков CobaltStrike и Meterptrenter и других имплантов работающих в памяти и обращающихся к LSASS из внедренного шелл кода

## Что нормально видеть
В рамках обычных операций Windows к LSASS обращаются по несколько легитимных процессов. Знание этих процессов помогает отфильтровать лишнюю информацию.

| Полный путь процесса             | Типичный предоставляемый доступ | Зачем                                               |
| -------------------------------- | ------------------------------- | --------------------------------------------------- |
| C:\Windows\System32\csrss.exe    | 0x1000 или 0x1400               | Подсистема windows управления процессами            |
| C:\Windows\System32\WerFault.exe | 0x1000                          | Обработчик сбоев системы отчетов об ошибках Windows |
| C:\Windows\System32\svchost.exe  | 0x1010                          | Различные сервисные функции                         |
| AV/EDR agent paths               | Varies                          | Безопасные продукты мониторят LSASS для защиты      |

> [!warning] ВАЖНО!!!
> При фильтрации по процессам всегда используйте полный путь, а не только имя исполлняемого файла. Злоумышленник может назвать свой инструмент svchost.exe и разместить его в `C:\Users\Public` или в `C:\Users\Temp`. Имя процесса выглядит легитимно но путь его выдает. Та же логика применима к csrss.exe. WerFault.exe и любому другому системному процессу. Если путь к SourceImage не C:\Windows\System32\ следует рассматривать его как подозрительный независимо от имени файла. Это так же означает что маски доступа связанные с инструментами для извлечения учетных данных не являются автоматически вредоносными. Все зависит от контекста: какой процесс обращается к LSASS и зачем

## Другие хранилища учетных данных 
LSASS - не единственное хранилище учетных данныз на windows машине, но наиболее ценная цель для компрометации домена:

- SAM база (`C:\Windows\System32\config\SAM`) хранит только хэши локальных учетных записей без доменных учетных данных. Извлекается через `reg save` или `lsadump::sam` в mimikatz, но дает доступ только к локальным учетным данным
- Кэшированные доменные учетные данные (реестр: `SECURITY\Cache`) - хэши DCC2 для офлайн входа при недоступности DC. Медленно поддаются перебору и не пригодны для Pass-the-hash, поэтому имеют низкий приоритет для всех атакующих
- База NTDS.dit на контроллерах домена содержит хэши всех учетных записей домена. Для ее извлечения необходим привилегированный доступ непосредственно к DC

LSASS является основной целью потому что хранит живые доменные учетные данные в готовом к использованию виде. Если атакующий делает дамп LSASS на машине, где активна сессия администратора домена, эти учетные данные можно немедленно применить для Pass-The-Hash или Pass-The-Ticket без какого либо перебора

# Обнаружение DCSync
На этом уровне цепочки атаки представим что атакующий имеет Domain Admin credentials. То есть мы имеем наивысшие привилегии и что нам теперь делать

Атакующие целятся в DCSync потому что это дает им извлечь каждый hash пароля без взаимодействия с диском контроллера домена, не создавая теневых копий томов и не требуя физического доступа к DC. Атака работает за счет злоупотребления протоколом репликации (DRSUAPI) - тем же протоколом, который легитимные контроллеры домена используют для синхронизации данных каталога между собой. Машина атакующего притворяется контроллером домена и запрашивает данные паролей через DRSUAPI. Если учетной записи есть нужные права, настоящий DC выполняет запрос. Права на репликацию по умолчанию имеют Domain Admins, Enterprice Admins и машинные учетные станции контроллеров домена.

В некоторых средах атакующие могут получить права репликации через злоупотребление ACL(WriteDACK для объекта домена) не будучи при этом в группе администратора домена.

## Как работает DCSync 

AD репликация построена на наборе расширенных прав, которые определяют кто может запрашивать данные каталога. Важны 3 конкретных GUIDs

- `{1131f6ad-9c07-11d1-f79f-00c04fc2dcd2}` - это DS-Replication-Get-Changes-All(Получение всех изменений репликации DS)
- `{1131f6aa-9c07-11d1-f79f-00c04fc2dcd2}` - DS-Replecation-Get-Changes(Получение изменений репликации DS)
- `{89e95b76-444d-4c62-991a-0facbeda640c}` - DS-Replication-Get-Changes-In-Filtered-Set(Получение изменений репликации DS в отфильтрованном наборе)

Один из низ наиболее важный: `1131f6ad` который соответствует разрешению DS-Replecation-Get-Changes-All. Это разрешение позволяет получать данные о паролях и является основным индикатором работы в DCSync
## Обнаружение с событием 4662
DCSync обнаружение использует событие 4662 (Была проведена операция над объектом). Когда кто то использует расширенные права для репликации раздела домена, срабатывает событие 4662 в необработанные данные события которого встроен GUID репликации

| Поле        | Что содержит                                                  | Почему это важно                                                    |
| ----------- | ------------------------------------------------------------- | ------------------------------------------------------------------- |
| user        | аккаунт запросивший репликацию                                | Идентифицирует кто запустил DCSync                                  |
| Access_Mask | 0x100(Контроль доступа)                                       | Указывает на то что было использовано расширенное право             |
| Properties  | Отображает управление доступа (GUID в необработанном событии) | Идентификатор репликации (GUID) подтверждающие синхронизацию DCSync |
| Logon_ID    | Hex идентификатор сессии                                      | ссылки на 4624 logon event для корреляции с IP источника            |
Сигналом детектирования можно считать EventID 4662 вместе с `Access_Mask=0x100`, GUIDами репликации вы сырых данных события и `user` который не является машинной учетной записью (не оканчивается на `$`)

> [!warning] ВАЖНО!!!
> DCSync через EventID 4662 требует двух предварительно настроенных условий:
> 1. Включенного аудита `Audit Directory Service Access` через групповую политику
> 2. SACL (System Access Control List) на разделе домена для аудита операций репликации
> 
>Ни то ни другое не включено по умолчанию. Без обоих условий DCSync полностью невидим в журналах. Это один из наиболее распространенных пробелов в обнаружении в реальных средах - стоит проверить наличие обеих настроек в любой сети, за которую вы отвечаете

## Нормальная репликация vs Подозрительная
В средах где несколько контроллеров домена, события 4662 с GUID репликации это нормально. Контроллеры домена постоянно проводят репликацию. Различие между обычным и вредоносным заключается в источнике

![[Pasted image 20260618185800.png]]


| Паттерн     | Нормально                          | Подозрительно                                    |
| ----------- | ---------------------------------- | ------------------------------------------------ |
| User        | Аккаунт машины оканчивается на `$` | Аккаунт человека                                 |
| Source Host | Другой контроллер домена           | хост не контроллер домена                        |
| Frequency   | Регулярные интвервалы              | Один запрос либо много запросв                   |
| Scope       | Изменения специфичных разделов     | Запрос всех данных (-just-dc-ntlm или full dump) |
## Найти IP источника
Event 4662 не содержит IP источника. Для нахождения инициатора нам нужно произвести корреляцию по полю `Logon_ID` с EventID 4624 события одной сессии которая в свою очередь содержит `Source_Network_Address`![[Pasted image 20260618190929.png]]

# Обнаружение извлечения NTDS.dit 
DCSync работает удаленно и перемешивается с трафиком репликации. Но это не единственный путь для атакующего извлечь креды из AD. Перед тем как DCSync стал стандартом, атакующие копировали NTDS.dit напрямую из контроллера домена. Это старый подход более шумный но еще активно используется в атаках в реальном мире
## Как работает извлечение NTDS.dit 
NTDS.dit это файл из Active Directory базы данных который есть на каждом DC(Обычно расположен по пути `C:\Windows\NTDS\ntds.dit`). Он содержит хэши паролей для каждого аккаунта в домене. Проблема для атакующего это то что Windows блокирует этот файл пока AD DS запущен, и поэтому он не может быть скопирован. Атакующие используют два основных способа обхода защиты:

- Теневые копии тома (vssadmin): создается моментальный снимок файловой системы что позволяет обойти блокировку файла. Атакующий создает теневую копию, копирует из нее `ntds.dit` и куст реестра `SYSTEM`(необходимый для расшифровки хэшей), после чего удаляет теневую копию
Обычно команды для этого выглядят так: 
```cmd
C:\Windows\System32> vssadmin create shadow /for=C: C:\Windows\System32> copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\Windows\NTDS\ntds.dit C:\temp\ntds.dit 
C:\Windows\System32> copy \\?\GLOBALROOT\Device\HarddiskVolumeShadowCopy1\Windows\System32\config\SYSTEM C:\temp\SYSTEM C:\Windows\System32> vssadmin delete shadows /shadow={shadow-id} /quiet
```

- Install From Media/ntdsutil легитимный инструмент управления AD предназначенный для повышения роли контроллера домена. Атакующий злоупотербляет функцией IFM (Install From Media), чтобы получить чистую копию `ntds.dit` и куста `SYSTEM` сохраняя их в локальный каталог
Команды: 
```cmd
C:\Windows\System32> ntdsutil "ac i ntds" "ifm" "create full C:\temp" q q
```

Оба метода требуют привилегии на контроллере домена. `vssadmin` нужны права локального администратора, `ntdsutil` требует Domain Admin или эквивалентных AD DS разрешений. Оба дают один и тот же результат: копия базы данных AD DC, которую можно проанализировать с помощью таких инструментов как `securitydump.py` или `NTDSDumpEx` для извлечения всех хэшей паролей

## Обнаружение извлечения NTDS.dit 
Извлечение NTDS.ditопределяется событием создания процесса. Мы ищем `vssadmin.exe` или `ntdsutil.exe` которые были выполнены на DC с аргументами относящимися к теневым копиям или IFM

- Sysmon EventID 1 захватывает полную строку команды. Сигналы обнаружения следующие
	- `ntdsutil.exe` - с командной содержащей `ifm` и `create`
	- `vssadmin` - с командой содержащей `create shadow`
- Sysmon EventID 11 захватит когда `nsdt.dit` запишется в необычное место с помощью `ntdsutil.exe`
