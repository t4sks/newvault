## Domain Users VS Local Users
Важное ограничение не все аккаунты являются доменными аккаунтами, некоторые могут быть локлаьными

- Domain Users - Пользователи домена проходят аутентификацию на контроллере домена. Их учетные данные хранятся в базе данных Active Directory (`NTDS.dit`). При входе в систему контроллер домена участвует в процессе, поэтому события отражаются на контроллере домена
- Локальные пользователи проходят аутентификацию в локальной базе данных диспетчера учетных записей безопасности (SAM) на каждом компьютере. Контроллер домена не участвует в процессе поэтому события отражаются только на этом конкретном компьютере.

| Тип пользователя      | Креды хранятся           | Где отображаются события аутентификации |
| --------------------- | ------------------------ | --------------------------------------- |
| Доменный пользователь | NTDS.dit(В DC)           | Domain Controller                       |
| Local User            | SAM(на локальной машине) | Только на локальной машине              |
# Аутентификация по Kerberos

## Что если пользователь ввел неправильный пароль или аутентификация сорвалась по другой причине?

## Типы шифрования в событиях 4768/4769
Билеты в Kerberos как правило шифруются. AD использует два типа шифрования:

- RC4 - встречается в средах со старыми системами или приложениями, не поддерживающими AES
- AES-256 - используется современными системами

Понимание того, какое шифрование должно присутствовать в вашей среде, позволяет определить какие типы ожидать и откуда они берутся.

| Значени | Алгоритм | Когда встречается                                           |
| ------- | -------- | ----------------------------------------------------------- |
| 0x12    | AES-256  | Современные системы, функциональный уровень домена 2008+    |
| 0x17    | RC4-HMAC | Устаревшие системы, старые приложения, доверие между лесами |

![[Pasted image 20260616204320.png]]

| table _time, Account_Name, Client_Address, Ticket_Encryption_Type

# NTLM Аутентификация
NTLM это старый протокол аутентификации используемый в случаях недоступности Kerberos. Это происходит при доступе к ресурсам по IP адресу, когда целевая система не может быть найдена в DNS или при аутентификации в системах не входящих в домен

| Шаг | Что происходит                          | EventID | Где логируется |
| --- | --------------------------------------- | ------- | -------------- |
| 1   | Целевой сервер просит DC проверит креды | 4776    | DC             |
| 2   | Сессия создана на цели                  | 4624    | Целевой сервер |

![[Pasted image 20260616204916.png]]

Событие 4776 появляется на контроллере домена при проверке учетных данных NTLM. Типичные сценарии включают:

- Доступ к общим файловым ресурсам по IP адресу (`\\10.0.1.50\shared`)
- Устаревшие приложения не поддерживающие kerberos
- Аутентификация в недоверенных доменах

Для поиска NTLM аутентификации на контроллере домена в Splunk 

```
index=* EventCode=4776 
| table _time, Logon_Account, Source_Workstation
```

![[Pasted image 20260616205142.png]]

Это показывает нам

- Какой аккаунт был аутентифицирован
- С какой машины

Между тем на целевом хосте отображается следующее

```
index=* EventCode=4624 Account_Name=michelle.smith Authentication_Package=NTLM 
| table _time host user Workstation_Name Source_Network_Address Authentication_Package
```

![[Pasted image 20260616205320.png]]

NTLM аутентификация в современных средах встречается реже чем kerberos. Большое количество событий 4776 может указывать на неправильную конфигурацию системы, устаревшие приложения и службы, обращающиеся к ресурсам по IP адресу вместо имени хоста

# Аккаунты, группы и события доступа к ресурсам
Каждый аккаунт в AD проходит жизненный цикл:

- Создание аккаунта
- Сброс пароля
- Периодические блокировки
- Блокировка когда кто то уходит из компании

Обычные административные действия создают специфические eventID которые создают базовый уровень нормальной активности 

| EventID | Что произошло         |
| ------- | --------------------- |
| 4720    | Аккаунт создан        |
| 4722    | Аккаунт активирован   |
| 4724    | Попытка сброса пароля |
| 4725    | Аккаунт деактивирован |
| 4740    | Аккаунт заблокирован  |
В типичном окружении, жизненный цикл следует определенному паттерну 

- Когда HR находит нового сотрудника IT создает ему аккаунт (4720) и активирует его (4722)
- Когда сотрудник забывает свой пароль поддержка сбрасывает его (4724)
- Когда сотрудник уходит из компании IT деактивирует его аккаунт (4725)

```
index=* EventCode=4720 
| table _time, SAM_Account_Name, Subject_Account_Name
```

![[Pasted image 20260617120830.png]]

Здесь `SAM_Account_Name` показывает какой аккаунт был создан, а `Subject_Account_Name`показывает какой админ создал этот аккаунт

Если увидим создание аккаунтов с неожиданными правами администратора, подозрительных имен или необычное время то стоит это расследовать 

## События членов группы
Добавление кого то в привилегированную группу это один из самых быстрых способ для атакующего для эскалации от первых шагов до контроля в масштабах всего домена и обеспечение постоянного доступа. К счастью Windows регистрирует каждое изменение членства в группах безопасности с помощью отдельных идентификаторов событий

| EventID | Что произошло                                             | Область действия группы                                           |
| ------- | --------------------------------------------------------- | ----------------------------------------------------------------- |
| 4728    | Член добавлен в глобальную группу безопасности            | Весь домен                                                        |
| 4732    | Член добавлен в локальную группу безопасности             | Уровень машины (уровень локального домена на контроллерах домена) |
| 4756    | Пользователь добавлен в универсальную группу безопасности | Весь лес                                                          |
Active Directory использует разные области действия для групп(Глобальные доменные и универсальные) чтобы организовать пользователей и контроль доступа. Именование может вызывать путаницу(например глобальные группы фактически ограничены одним доменом а не глобально)

Для мониторинга важно чтобы все три идентификатора событий указывали на добавление пользователя в группу безопасности. Следите за всеми ними, особенно за привилегированными группами, такими как администраторы домена, администраторы предприятия и локальные администраторы

![[Pasted image 20260617122903.png]]

На контроллере домена мы можем увидеть эти группы кликнув правой кнопкой мыши на специфический OU -> New -> Group

![[Pasted image 20260617123026.png]]

Для того чтобы увидеть изменения членов группы:

```
index=* (EventCode=4728 OR EventCode=4732 OR EventCode=4756) | table _time, Member_Account_Name, Group_Name, Subject_Account_Name
```

![[Pasted image 20260617123237.png]]

Это показывает:

- Кто был добавлен(`Member_Account_Name`)
- В какую группу он был добавлен(`Group_Name`)
- И кто сделал это изменение (`Subject_Account_Name`)

# События Directory Service
Событие 5136 фиксирует изменения на уровне атрибутов Active Directory. В отличие от события 4728, который лишь сообщает о добавлении пользователя в группу, событие 5136 показывает конкретный измененный LDAP атрибут и его новое значение

Наиболее часто встречаемые атрибуты:

- `userAccountControl` - изменения статуса учетной записи (отключена, пароль никогда не истекает и так далее)
- `servicePrincipalName` - изменения SPN
- `scriptpath` - путь к скрипту входа(Скрипты выполняемые при входе пользователя)
- `member` - изменения членства в группе на уровне атрибута
-  `displayName`, `description`, `title` - поле с информацией о пользователе

Например когда IT администратор назначает пользователю скрипт входа, Event 5136 фиксирует точный путь: 

![[Pasted image 20260617123950.png]]

В данном случае мы видим, что для пользователя внесшего изменения (`Subject_Account_Name:adm-luke.sullivan`), был настроен сценарий входа в систему, а так же указан путь к этому сценарию

Мониторинг всех этих изменений помогает убедиться, что модификации конфигурации внесены авторизированными администраторами и соответствуют нашему процессу управления изменениями

## Отслеживание GPO модификаций
Один из важных примеров использования события 5136 это мониторинг изменений в Group Policy Objects (Объектах групповой политики). GPO дает администраторам централизованно управлять конфигурацией в рамках домена. Одна GPO может устанавливать программное обеспечение, устанавливать настройки безопасности или менять политики аудита на тысячах машинах сразу.

Это ответ на вопрос почему атакующий целятся в них. Изменение одной GPO позволяет атакующим развертывать ransoware, выключать проверки безопасности или обеспечивать закрепление во всей области домена одним действием

```
index=* EventCode=5136 Class="groupPolicyContainer" 
| table _time, Subject_Account_Name, DN, LDAP_Display_Name, Value 
| sort - _time
```

![[Pasted image 20260617125233.png]]

это запрос вернет все GPO изменения и покажет нам:

- Кто изменил (`Subject_Account_Name`)
- Какая GPO была затронута (`DN`)
- И какие изменения (`LDAP_Display_Name` и `Value`)
	- `gPCFileSysPath` , указывает путь на `SYSVOL`, где хранится настраиваемая групповая политика
	- `versionNumber` атрибут(показывает количество модификаций)

Эти параметры говорят нам когда GPO объекты созданы, переименованы или модифицированы. `displayName`  и `DN` поля помогают нам идентифицировать какую GPO трогали и `Subject_Account_Name` показывает кто сделал эти изменения

> [!warning] ВАЖНО!!
> Event 5136 фиксирует изменения метаданных GPO, хранящихся в AD(например имя GPO, номер версии или путь `SYSVOL`), однако не фиксирует изменения самих параметров внутри политики GPO. 
> Например если администратор изменил требование к длине пароля с 10 до 14 символов, Event 5136 отобразит увеличение `versionNumber` объекта GPO, но не покажет какой именно параметр был изменен. Фактически конфигурации политик хранятся в файлах `SYSVOL` и требуют отдельного мониторинга

Понимание событий входа помогают ответит на фундаментальные вопросы

- Кто получил доступ к системе
- Когда 
- Откуда

| EventID | Что произошло   |
| ------- | --------------- |
| 4624    | Успешный вход   |

## Понимания типов входа
Поле тип входа говорит нам какой тип активности создал `logon event`. Например:

- Type 2 означает что кто то физически сел за клавиатуру
- Type 3 означает удаленный доступ к файловому ресурсу

Понимание разницы помогает определить соответствует ли активность ожидаемому поведению для данной учетной записи и контекста

| Тип | Значение              | Пример                                                                 |
| --- | --------------------- | ---------------------------------------------------------------------- |
| 2   | Interactive           | Пользователь за клавиатурой физическая консоль                         |
| 3   | Network               | Доступ к файловым ресурсам, WMI запросы удаленное администрирование    |
| 4   | Batch(пакетный)       | Запланированные задачи выполняемые от имени учетной записи пользовтеля |
| 5   | Service(сервисный)    | Службы Windows, запускаемые от имени сервисной учетной записи          |
| 7   | Unlock(разблокировка) | Пользователь разблокирует ранее заблокированную рабочую станцию        |
| 10  | RemoteInterective     | RDP сессия                                                             |

# Понимание Базовой активности

## Шум это нормально
|Событие|Типичный суточный объём|
|---|---|
|4769 (TGS-запросы)|50 000 — 100 000+|
|4768 (TGT-запросы)|5 000 — 10 000+|
|4624 (входы в систему)|Сильно варьируется в зависимости от роли сервера|
Этот шум не проблема а нормальное поведение сервера
## Учетные записи компьютеров ($)
В производственных средах огромная часть трафика Kerberos поступает от учетных записей компьютеров а не от пользователей. Учетные записи компьютеров в AD заканчиваются `$`(Например: `THM-DC$, THM-IT-DESK$`) Эти учетные записи постоянно проходят аутентификацию для связи между машинами, обновления системы и автоматизированных процессов

В загруженных средах учетные записи компьютеров могут генерировать 70-80% всего трафика Kerberos. При исследовании активности пользователей мы обычно хотим отфильтровать нечеловеческую активность чтобы сосредоточиться на поведении людей. 

Чтобы увидеть разницу мы можем сравнить общее количество событий аутентификации для учетных записей компьютеров и учетных записей пользователей:

```
index=* EventCode IN (4624, 4768, 4769) 
| eval AccountType=if(like(Account_Name, "%$%"), "Computer Account", "User Account") 
| stats count by AccountType, EventCode 
| sort AccountType, -count
```

![[Pasted image 20260617142350.png]]

Мы видим что аккаунты компьютеров имеют более 1500 успешных входов

## Техника Stack Counting
Одна из наиболее полезных техник обнаружения аномалий. Суть подсчитать сколько раз встречается каждое значение, отсортировать по частоте и сосредоточить внимание на редких событиях в конце списка.

Техника демонстрируется на Event 4769, поскольку он отображает запросы сервисных билетов - из них видно к каким ресурсам обращались пользователи и как часто. Высокочастотная активность - норма, редкая 0 как правило аномалия которая требует расследования

Например для поиска подозрительных учетных записей через Stack counting:

```
index=* EventCode=4769 NOT Account_Name="*$*" | stats count by Account_Name | sort -count
```

![[Pasted image 20260617143726.png]]

Как видно из результатов

- Верхние результаты базовый уровень: обычные авторизованные учетные записи, регулярно обращающиеся к сервисам
- Нижние результаты - редкие события: учетные записи появившиеся лишь один два раза. Именно здесь как правило и скрываются аномалии

Если 90% запросов сервисных билетов поступает от известных авторизированных учетных записей - это норма. Учетная запись в конце списка с одним, двумя запросами выделяется именно своей редкостью и требует расследования

Техника применима к любому полю в любом типе событий:

- Stack count by Account_Name - поиск нетипичных учетных записей
- Stack count by Client_Address - поиск нетипичных IP адресов источника
-  Stack count by Service_Name - поиск нетипичных сервисов
- Stack coun by Ticket_Encryption_Type - поиск нетипичных методов шифрования

Редкие значения в конце списка это и есть фокус расследования

## Time Based паттерны
Время имеет значение при оценке нормальности активности. Бизнес приложения используются в рабочие часы, резервное копирование - ночью, пакетные задания - плановых окнах. Видя активность нудно спрашивать: соответствует ли время характеру учетной записи и ее назначению

Понимание этих паттернов в своей среде формирует ожидания:

| Активность                          | Ожидаемое время                |
| ----------------------------------- | ------------------------------ |
| Входы пользователей                 | Рабочие часы (8:00-18:00)      |
| Активность backup учетных записей   | Ночью (0:00-4:00)              |
| Учетные записи пакетных заданий     | Плановые временные окна        |
| Использование админ-учетных записей | Во время окон тех обслуживания |
