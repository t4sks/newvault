# Протоколы используемые в AD

| Протокол                | Порты                | Что это делает                                     | Обычное использование                                                    |
| ----------------------- | -------------------- | -------------------------------------------------- | ------------------------------------------------------------------------ |
| Kerberos                | 88                   | Базовая аутентификация в AD                        | Вход пользователей, доступ к сервисам, запрос билетов                    |
| LDAP                    | 389, 636, 3268, 3269 | Запрос и изменения каталога                        | Поиск пользователей, проверка членства в группах, запросы адресной книги |
| SMB                     | 445                  | общий доступ к файлам, удаленное администрирование | Доступ к общим папкам, принтерам и административным инструментам         |
| RDP                     | 3389                 | Интерактивный удаленный рабочий стол               | Поддержка пользователей(help desk), администрирование серверов           |
| Name Resolution(Legacy) | 137,138,5455         | NetBios (TCP/UDP - 137/138) и LLMNR(5355)          | Резервный механизм при недоступности DNS, для устаревших приложений      |

# События аутентификации
когда пользователю нужно получить доступ к ресурсам домена он должен аутентифицироваться. Тоже самое можно сказать и про нападающих. 
Эвенты аутентификации могут сказать нам:

- Кто запросил доступ
- Когда
- Откуда
- И было ли это успешно 

## Domain Users VS Local Users
Важное ограничение не все аккаунты являются доменными аккаунтами, некоторые могут быть локлаьными

- Domain Users - Пользователи домена проходят аутентификацию на контроллере домена. Их учетные данные хранятся в базе данных Active Directory (`NTDS.dit`). При входе в систему контроллер домена участвует в процессе, поэтому события отражаются на контроллере домена
- Локальные пользователи проходят аутентификацию в локальной базе данных диспетчера учетных записей безопасности (SAM) на каждом компьютере. Контроллер домена не участвует в процессе поэтому события отражаются только на этом конкретном компьютере.

| Тип пользователя      | Креды хранятся           | Где отображаются события аутентификации |
| --------------------- | ------------------------ | --------------------------------------- |
| Доменный пользователь | NTDS.dit(В DC)           | Domain Controller                       |
| Local User            | SAM(на локальной машине) | Только на локальной машине              |
# Аутентификация по Kerberos
Kerberos это прокол основанный на билетах используемый в AD для верификации и идентификации пользователей без отправки пароля в сети.

Когда пользователь аутентифицируется, его первый запрос TGT от DC. Этот TGT можно использовать чтобы запросить TGS для специфических ресурсов. Каждый шаг генерирует определенное событие

![[Pasted image 20260616203138.png]]

| Шаг | Что произошло                         | EventID | Где логируется    |
| --- | ------------------------------------- | ------- | ----------------- |
| 1   | User Request a TGT                    | 4768    | Domain Controller |
| 2   | Users Requests a TGS                  | 4769    | Domian Controller |
| 3   | User создает сессию на целевой машине | 4624    | Target Server     |

## Что если пользователь ввел неправильный пароль или аутентификация сорвалась по другой причине?
Ошибка предпарольной аутентификации создает событие 4771 на контроллере домена. Мы увидим 4771 событие в среде где пользователи иногда забывают или неправильно печатают свой пароль

## Типы шифрования в событиях 4768/4769
Билеты в Kerberos как правило шифруются. AD использует два типа шифрования:

- RC4 - встречается в средах со старыми системами или приложениями, не поддерживающими AES
- AES-256 - используется современными системами

Понимание того, какое шифрование должно присутствовать в вашей среде, позволяет определить какие типы ожидать и откуда они берутся.

| Значени | Алгоритм | Когда встречается                                           |
| ------- | -------- | ----------------------------------------------------------- |
| 0x12    | AES-256  | Современные системы, функциональный уровень домена 2008+    |
| 0x17    | RC4-HMAC | Устаревшие системы, старые приложения, доверие между лесами |

| table _time, Account_Name, Client_Address, Ticket_Encryption_Type

# NTLM Аутентификация
NTLM это старый протокол аутентификации используемый в случаях недоступности Kerberos. Это происходит при доступе к ресурсам по IP адресу, когда целевая система не может быть найдена в DNS или при аутентификации в системах не входящих в домен

| Шаг | Что происходит                          | EventID | Где логируется |
| --- | --------------------------------------- | ------- | -------------- |
| 1   | Целевой сервер просит DC проверит креды | 4776    | DC             |
| 2   | Сессия создана на цели                  | 4624    | Целевой сервер |

![[Pasted image 20260616204916.png]]

Событие 4776 появляется на контроллере домена при проверке учетных данных NTLM. Типичные сценарии включают:

- Доступ к общим файловым ресурсам по IP адресу (`\\10.0.1.50\shared`)
- Устаревшие приложения не поддерживающие kerberos
- Аутентификация в недоверенных доменах

Для поиска NTLM аутентификации на контроллере домена в Splunk 

```
index=* EventCode=4776 
| table _time, Logon_Account, Source_Workstation
```

![[Pasted image 20260616205142.png]]

Это показывает нам

- Какой аккаунт был аутентифицирован
- С какой машины

Между тем на целевом хосте отображается следующее

```
index=* EventCode=4624 Account_Name=michelle.smith Authentication_Package=NTLM 
| table _time host user Workstation_Name Source_Network_Address Authentication_Package
```

![[Pasted image 20260616205320.png]]

NTLM аутентификация в современных средах встречается реже чем kerberos. Большое количество событий 4776 может указывать на неправильную конфигурацию системы, устаревшие приложения и службы, обращающиеся к ресурсам по IP адресу вместо имени хоста
