# Как работает боковое перемещение
После построения карты AD атакующий будет перемещаться к тому что ему больше интересно, это может быть Domain Controller, сервер базы данных или файло обменник который содержит ценную информацию 

Любая техника бокового перемещения следует одной и той же базовой схеме, злоумышленник проходит аутентификацию на удаленном компьютере используя украденные или неправомерно используемые учетные данные, а затем выполняет на нем какие либо действия. Техника может отличаться но эта последовательность аутентифкация затем исполнение присутствует всегда

## Модель источника и назначения
Каждое удаленное подключение оставляет артефакты на двух машинах

- Источник - машина с которой атакующий инициирует соединения. Видит только то, какие учетные данные пользователей и какая цель была выбрана
- Назначение - машина на которой сессия устанавливается и выполняются действия. Видит факт подключения и все, что было сделано в рамках сессии

Если анализировать только назначение - известно что атака произошла но не известно ее происхождение. Если анализировать только источник - известен умысел но неизвестно был ли он реализован.

# Logon Type: первая вещь которую нужно проверять

Когда кто то конектится к удаленной машине, windows Event Logs создает Event 4624 на назначении. The `Logon_Type` покажет как произошло соединение

| Logon Type | Значение                      | Общие протоколы | Что это нам говорит                                 |
| ---------- | ----------------------------- | --------------- | --------------------------------------------------- |
| 3          | Network Logon                 | SMB, PsExec     | удаленный доступ без интерактивной сессии           |
| 7          | Разблокировка/переподключение | RDP             | заблокированная рабочая станция или реконект сессии |
| 10         | RemoteInteractive             | RDP             | Полная десктоп сессия                               |
Тип 10 понятен это RDP. Тип 3 сложнее потому что и SMB и PsExec генерируют вход в систему типа 3, поэтому нам нужны дополнительные артефакты, чтобы их различать.

> [!warning] ВАЖНО!!!
> Если злоумышленник подключается через RDP когда у той же учетной записи уже есть активная или отключенная сессия на этом хосте Windows переподключает его к существующей сессии вместо создания новой. Это приводит к входу в систему типа 7 вместо 10. В ходе расследования, если мы видим вход в систему типа 7 с удаленным IP это указывает на переподключение через RDP а не на физическую разблокировку рабочей станции. Имейте это в виду при поиске активности RDP, фильтрация по Logon_Type=10 пропустит эти переподключения. Также обратите внимание что при переподключении назначается новый Logon_ID, даже если сама сессия RDP сохраняется, поэтому корреляция на основе Logon_ID может нарушаться на границах отключения/повторного подключения

## Event 4648 Отслеживание источника
Событие 4648(Logon Using Explicit Credentials) подсвечивает на машине источника когда учетные данные отличаются от учетных данных текущего пользователя вошедшего в систему

Например ниже показано что если `liam.patel` запустит `net use \\THM-SHR-SRV\ADMIN$ /user:luke.sullivan` Event 4648 залогирует на `THM-MKT-WS` и запишет оригинальный аккаунт `liam.patel`, альтернативный аккаунт `luke.sullivan` и целевое имя сервера `THM-SHR-SRV`![[Pasted image 20260618224647.png]]
Это говорит нам какая машина инициировала соединение и какие учетные данные были использованы. Большинство точек назначения логирует только кто подключился, нет значения которое покажет кто сидел за клавиатурой когда событие произошло

Susmon Event 1 (Process Creation) так же захватывает `net.exe` процесс вместе с полной командной строкой, включает целевой сервер и аккаунт указанный в `/user` флаге и пароль 

![[Pasted image 20260618225051.png]]

Вместе эти два источника события предоставляет лучший контекст для похожей активности


> [!warning] ВАЖНО!!!
> Событие 4648 подсвечивает когда учетные данные явно предоставлены, например как `net use /user:`, `runas` или ввод учетных данных в диалоговом окне RDP. Но это не подсвечивает Pass-The-Hash или Pass-The-Ticket или вход Kerberos, поскольку эти методы повторно используют кэшированные учетные данные без явного их предоставления

Легитимная сессия админа и боковое перемещение атакующего генерируют одинаковые EventID. Оба производят 4624, оба создают 4648 и оба успешно аутентифицируются на удаленном хосте. Их отличает контекст:

# Обнаружение SMB Lateral Movement
SMB это самый популярный протокол который используется для бокового перемещения, и так же самый шумный. Каждый раз кто то подключает свой сетевой диск, открывает расшаренный документ или печатает на сетевом принтере, участвует SMB.
Групповые политики обновлений и backup агенты создают постоянный SMB трафик. Поэтому в сети много легитимной SMB активности которую любят использовать атакующие
## Админские shares
В системах windows по умолчанию сохраняются административные общие ресурсы такие как `C$, ADMIN$, IPC$` создаваемые службой сервера при загрузке. Эти ресурсы используют SMB (порт 445) для обеспечения удаленного управления

- `C$` - сопоставлен с корнем системного диска, дополнительные диски следуют той же схеме
- `ADMIN$` - Указывает на `%SystemRoot%`(обычно это `C:\Windows`)
- `IPC$` - Логическая шара для межпроцессовго взаимодействия через именованные каналы, необходим удаленный RPC вызов

Обращение к этим шарам как правило порождает два события 5140(обращение к объекту сетевого ресурса) и 4624 (успешный вход в систему)

Рядовые пользователи не обращаются к ним в ходе штатной работы - они используют именованные шары вроде `Marketing` `Shared` или `IT`. Когда мы видим обращение к административным шарам это либо администратор выполняющий обслуживание либо атакующий осуществляющий боковое перемещение

В Active Directory каждый компьютер аутентифицируется с помощью учетной записи, которая соответствует его имени хоста и заканчивается на `$` Мы можем использовать это для сопоставления любого IP с его именем хоста выполнив поиск событий 4624 связанных с этим IP

```
| stats count by user, Source_Network_Address 
| sort -count
```

теперь мы знаем что пользователь IT администратор обычно работающий за своей машиной IT но его учетные данные используются с совершенно другого компьютера - рабочей станции отдела маркетинга. У IT администратора нет причин входить в систему на этом хосте, а значит вероятно кто то имеет учетные данные этого пользователя и использует их для перемещения между компьютерами. # Обнаружение PsExec Lateral Movement
Подход через net use позволяет атакующему копировать файлы и просматривать директории удаленно, но не выполнять ничего на цели. 

PsExec это инструмент из Sysenternals который сочетает доступ к административным SMB шарам с установкой Windows службы для выполнения команд на удаленных системах

Стоит понять, как PsExec работает изнутри, потому что он оставляет очень специфичный след артефактов. Даже когда атакующие переименовывают бинарник, базовое поведение остается прежним.

## Как работает PsExec
Когда у атакующего есть аутентифицированная SMB-сессия (через `net use`) и он запускает `PsExec.exe \\target cmd.exe` происходит следующее

1. PsExec подключается к шаре `ADMIN$`на цели через SMB
2. Копирует служебный бинарник `PSEXESVC.exe` в директорию `C:\Windows` на цели
3. Создает и запускает новую Windows-службу на цели (SystemEvent 7045)
4. Служба создает именованные каналы (named pipes) для коммуникации через `stdin`/`stdout`/`stderr` (Sysmon Event 17)
5. Эта служба выполняет команду указанную атакующим
6. По завершении сессии PsExec удаляет службу и очищает бинарник

Event 7045 (A new Service Was Installed) в журнале System - сигнатурный артефакт PsExec, фиксируемый на машине назначении. Именно это отличает PsExec от обычного SMB-доступа

![[Pasted image 20260619122823.png]]

## Почему атакующие используют PsExec
PsExec это легитимный инструмент администратора. Сисадмины часто используют его в работе при обновлениях запуске скриптов и решения проблем на удаленных хостах. С точки зрения протокола трафик PsExec выглядит идентичным обычному трафику администрирования SMB. Единственное различие заключается в контексте: какая учетная запись с какого компьютера в какой время и как она использовалась

## Исследование активности PsExec
### Обнаружение PsExec на получателе
Для поиска используем 7045(установка сервиса)

```
index=win EventCode=7045 
| table _time, host, Service_Name, Service_File_Name, Service_Type, Service_Start_Type, Service_Account 
| sort _time
```

![[Pasted image 20260619131138.png]]

В конфигурации по умолчанию имя службы - `PSEXECSVC`, а путь к исполняемому файлу указывает на `C:\Windows\PSEXECSVC.exe` (rdbdfktyn `%SytemRoot%\PSEXESVC.exe`). Поле `Service_Account` показывает под какой учетной записью запускается служба

По умолчанию PsExec выполняет удаленную команду от имени аутентифицирующего пользователя. При запуске с флагом -S служба работает от `LocalSystem`, предоставляя SYSTEM уровень доступа на целевом хосте
### Какие команды выполнял атакующий
После того как служба PsExec идентифицирована через 7045 и установлен хост, на котором она была создана, следующйи шаг - выяснить какие именно атакующий выполнял команды

Поскольку `PSEXECSVC.exe` это служба порождающая удаленные команды атакующего, можно использовать события создания процессов(Например Sysmon Event 1) с фильтрацией по `ParentImage`, чтобы найти процессы созданные или команды выполненные этим бинарным файлом службы

```
index=win EventCode=1 host=THM-SQL-SRV ParentImage="*PSEXESVC*" 
| table _time, host, User, ParentImage, Image, CommandLine 
| sort _time
```

![[Pasted image 20260619132604.png]]
### Обнаружение PsExec: источник
Как только мы определили выполнение команды и имя службы мы легко можем определить исходный хост с которого был запущен PsExec. Событие Sysmon 1 фиксирует создание процесса полной командной строкой

```
index=win EventCode=1 host=THM-MKT-WS
| search Image="*PsExec*" 
| table _time, host, User, Image, CommandLine 
| sort _time
```

![[Pasted image 20260619132952.png]]

CommandLine показывает какой хост и какие команды были выполнены удаленно
### Поиск переименованного PsExec 
Злоумышленники знают что инструменты безопасности ищут PSEXESVC по имена. Флаг `-r` в PsExec позволяет оператору указать пользовательское имя службы, поэтому запуск команды 
```
PsExec -r renamed_psexec \\target  
```
создаст службу с именем renamed_psexec заместо PSEXECSVC

Другие инструменты такие как psexec.py от Impacket или модуль PsExec от Cobalt Strike по умолчанию генерируют случайные имена служб. Но событие 7045 все равно срабатывает независимо от имени

Паттерн для поиска: это любая новая служба с `Service_Type` равным `user mode service` и `Service_Start_Type` равным `demand start`. Имя службы и путь к бинарному файлу могут отличаться, но сигнатура - запуск по требованию, пользовательский режим остаются неизменными. 

# Определение RDP Lateral Movement
RDP предоставляет атакующему полноценный интерактивный сеанс рабочего стола, однако не оставляет н тех же очевидных артефактов для охоты что и предыдущие техники. Нет установки службы, нет паттерна обращения к шарам, нет уникального процесса на целевой машине, который бы указывал: "Это был RDP". Поэтому расследование редко начинается с прямого поиска RDP сессий. Как правило RDP обнаруживается как механизм доставки уже после того как что то другое привлекло внимание.

Основной артефакт обнаружения RDP - событие 4624 с `Logon_Type=10` фиксируемое на целевой машине. В нем записываются имя учетной записи, IP адрес источника и временная метка сессии. SMB и PsExec оба порождают сетевые входы типа 3, тогда как успешная RDP сессия порождает тип 10 - это делает ее сразу различимой в журнале безопасности. Однако NLA вносит нюанс, заслуживающий отдельного внимания

> [!warning] ВАЖНО!!! 
> Современные версии Windows включают Network Level Authentication (NLA) по умолчанию. При NLA пользователь аутентифицируется на сетевом уровне до установления RDP сессии, что генерирует кратковременный вход типа 3 непосредственно перед типом 10. Если виден тип 3 с того же IP адреса источника за несколько секунд до типа 10 - это прелюдия а не отдельное SMB или PsExec подключение

## Нормальный vs Подозрительный RDP трафик
|Паттерн|Типично?|Причина|
|---|---|---|
|Рабочая станция → Сервер|Да|IT-администраторы подключаются по RDP со своих рабочих станций для управления серверами. Это стандартный паттерн.|
|Рабочая станция → Рабочая станция|Редко|Обычные пользователи не подключаются по RDP к машинам друг друга. Служба поддержки может, но только с выделенных IT-рабочих станций.|
|Сервер → Сервер|Подозрительно|Серверы не инициируют исходящий RDP самостоятельно. Если сервер подключается по RDP к другому серверу — кто-то находится внутри активной сессии на этом сервере и движется дальше.|
Эти паттерны не правила. Существуют среды где RDP соединение является нормой. Но в качестве отправной точки, любая RDP сессия инициированная сервером а не рабочей станцией требует более детального рассмотрения

## Исследование RDP Lateral Movement
Обычно мы не прыгаем в RDP логи потому что они могут быть шумными. Пока например рассмотрим когда пришло оповещение о командах разведки на DC. 
```
index=win EventCode=1 host=THM-DC
| search CommandLine IN ("*nltest*", "*net * user*", "*net * group*", "*net * view*")
| table _time, host, User, Image, CommandLine, LogonId
| sort _time
```

![[Pasted image 20260619144320.png]]

Заметим поле LogonID которое укажет на сессию от которой команды были исполнены. Используем этот параметр для поиска того как она была создана
### Идентификация как атакующий достиг контроллера домена

```
index=win EventCode=4624 host=THM-DC Logon_ID=0x508C55A 
| table _time, user, Logon_Type, Source_Network_Address, Logon_ID
```

![[Pasted image 20260619144914.png]]

Мы видим что атакующий подключился через RDP теперь мы можем проверить Source_Network_Address чтобы посмотреть откуда он подключился 
### Идентифицируем Source Hostname
У нас есть IP машины но нам нужно имя этой хоста чтобы запросить журналы логов на этом компьютере

```
index=win EventCode=4624 Source_Network_Address=10.5.30.120 user=*$
| stats count by user, Source_Network_Address
| sort -count
```

![[Pasted image 20260619145452.png]]

поле `user` оканчивающееся на `$` раскрывает имя хоста машины. Уберите суффикс `$` это будет имя машины
### Поиск свидетельств исходящего RDP подключения на источнике
Когда с машины инициируется RDP подключение на ней запускается `mstsc.exe`(клиент удаленного рабочего стола). Если Sysmon фиксирует создание процессов на этом хосте можно выполнить поиск

```
index=win EventCode=1 host=THM-SQL-SRV Image="*mstsc.exe*" 
| table _time, User, Image, CommandLine, LogonId 
| sort _time
```

![[Pasted image 20260619150543.png]]

Это подтверждает что с данного сервера было инициировано исходящее RDP подключение к DC
### Отслеживание пути атакующего до промежуточного сервера
Берем LogonID из предыдущего и ищем событие аутентификации для этого входа
```
index=win EventCode=4624 host="THM-SQL-SRV" Logon_ID=0x3C572BD
```

Виден уже другой RDP вход, на этот раз от другого пользователя и с другого источника

Атакующий начал с компрометированной рабочей станции использовал RDP для перехода на сервер а уже внутри этой сессии открыл еще одно RDP подключение к контроллеру домена - под другой более привилегированной учетной записью

Это называется RDP Chaining и широко применяется когда атакующие пилотируют через промежуточные машины для достижения чувствительных целей, таких как контроллеры домены. На каждом переходе используется RDP однако исходный IP адрес машины не меняется поскольку подключение исходит уже с промежуточной машины а не с оригинальной рабочей станции
