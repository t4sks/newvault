# Почему Active Directory меняет поверхность атаки

Поверхность атаки меняется из-за потому что все службы аутентифицируют пользователей через один центральный каталог. Каждая из этих служб становится потенциальной точкой входа не только для самой службы но и для каждого ресурса в домене

# Что такое IIS и почему это важно
Internet Information Services(IIS) это платформа веб сервера от Microsoft. Exchange, SharePiont, ADFS и много других внутренних бизнес приложений запущены на IIS. Любое из этих приложений может стать первоначальной точкой доступа, если злоумышленник обнаружит уязвимость для эксплуатации

Когда юзер авторизуется в IIS-hosted приложение, IIS проверяет его данные с помощью Active Directory Validation. В логаз записывается событие 4624 или 4625. Это означает что IIS аутентификация создает события в IIS access log и в Windows Security logs на веб сервере пока DC логирует 4776 для проверки учетных данных, как показано на диаграмме ниже:

> [!warning] ВАЖНО!!! 
>  IIS записывает все метки времени в формате UTC, не зависимо от локального часового пояса сервера. Это важно при сопоставлении записей IIS с событиями безопасности Windows, которые используют локальное часовое поясное время машины 

Не все поля имеют для нас значение поэтому обратить внимание стоит на следующие: 

|Поле|Описание|Почему важно|
|---|---|---|
|c-ip|IP-адрес клиента|Идентифицирует IP-адрес источника атакующего|
|cs-uri-stem|Запрошенный URI-путь|Показывает, к какому ресурсу был получен доступ (пути веб-шеллов, админ-панели)|
|cs-uri-query|Строка запроса (query string)|Может содержать команды, передаваемые веб-шеллам|
|cs-method|HTTP-метод (GET/POST)|POST-запросы к нетипичным путям — признак подозрительной активности|
|sc-status|HTTP-код статуса|200=успех, 401=ошибка аутентификации, 302=редирект (используется OWA)|
|cs(User-Agent)|Идентификатор браузера/инструмента|Может указывать на автоматизированные инструменты (curl, Python), однако атакующие могут его подделать|
# Нормальные и подозрительные IIS паттерны
| Паттерн              | Норма                                                    | Подозрительно                                                    |
| -------------------- | -------------------------------------------------------- | ---------------------------------------------------------------- |
| Объём аутентификации | Несколько событий входа на пользователя в течение дня    | Сотни попыток входа с одного IP за несколько минут               |
| Время запросов       | Вход в 09:15 с 10.5.10.x (офисная подсеть, рабочие часы) | Вход в 03:22 с 10.99.50.x (неизвестная подсеть, нерабочее время) |
| URI-пути             | /owa/, /ecp/, /internalapp/default.aspx                  | /aspnet_client/system_web/shell.aspx или /uploads/cmd.aspx       |
| Строки запроса       | ?ViewAction=ReadMessage&ItemID=AAM                       | ?cmd=whoami или ?exec=ipconfig                                   |
| HTTP-методы          | GET для страниц, POST для форм входа                     | POST к /aspnet_client/shell.aspx (статический каталог)           |
| HTTP-коды статуса    | Единичные 404 из-за опечаток                             | Сотни 404 с одного IP за минуты (сканирование каталогов)         |

При анализе IIS логов в первую очередь ищут отклонения от нормальных паттернов. Лавина ошибок аутентификации с одного IP или POST запросы к файлам в нетипичных каталогах - оба сценария являются красными флагами и требуют расследования

# Обнаружение Web шела

Вебшел это вредоносный скрипт(обычно `.aspx` в IIS средах) который дает атакующему исполнять OS команды через HTTP запросы. Они переживают перезагрузки, используют обычные веб порты и не требуют дополнительных инструментов. Базовый веб шел может легким и быть в одну строку:

```
<​%@ Page Language="C#" %​><​%System.Diagnostics.Process.Start("cmd.exe","/c "+Request["cmd"]);%​>
```

# Ключевой паттерн детектирования

Активность веб шела имеет характерную сигнатуру в цепочках процессов. Во время обычной работы IIS рабочий процесс w3wp.exe обрабатывает HTTP запросы и генерирует ответы, не запуская другие процессы

В то же время когда злоумышленник взаимодействует с веб оболочкой w3wp.exe запускает дочерние процессы для исполнения команд.

![[Pasted image 20260617162614.png]]
Если w3wp.exe запускает cmd.exe или powershell.exe или инструменты которые он недолжен запускать, это почти всегда стоит расследовать. Легитимным приложениям IIS редко требуется запускать командные оболочки

# Исследование активности
## 1 шаг - обнаружение активности сканирований
Перед установкой webshell атакующий сканирует директории. В IIS это означает много 404 ответов для одного IP

```
index=iis sc_status=404 
| stats count by c_ip 
| sort - count
```

Выведет IP которые имеют большое количество 404
## 2 шаг - Поиск подозрительных `.aspx`
Для поиска посмотрим к каким директориям получал доступ IP с наибольшим количеством 404 ответов

```
index=iis c_ip={SUSPICIOUS_IP} sc_status=200 
| stats count by cs_uri_stem 
| sort - count
```

![[Pasted image 20260617163320.png]]

Теперь мы нашли вебшел. 
Примечательно что оболочка расположена в `/aspnet_client/`  это стандартный каталог IIS который обычно хранит клиентские скрипты ASP.NET и никогда не должен содержать код приложения. Эта папка доступна для записи рабочим процессом IIS(w3wp.exe) что делает ее распространенным местом для веб оболочек.
## 3 шаг Фильтрация подозрительных `.aspx` файлов

```
index=iis cs_uri_stem="*/{WEBSHELL_FILENAME}" 
| table _time, c_ip, cs_method, cs_uri_query, sc_status 
| sort _time
```

![[Pasted image 20260617163754.png]]

в `cs_uri_query` мы можем увидеть команду которую исполнили при помощи этого шела.
## 3 шаг - Отследить цепочку процесса в Sysmon
Чтобы точно определить когда именно эти команды были выполнены на диске, мы обратимся к событиям создания процессов (Sysmon EventID1 или Security Logs 4688)

```
index=win EventCode=1 ParentImage="*\\w3wp.exe" 
| table _time, ParentImage, CommandLine 
| sort _time
```

![[Pasted image 20260617164042.png]]

Запрос покажет каждый процесс порожденный `w3wp.exe`. 
## 4 шаг - Найти когда веб шел был установлен
Для нахождения используем Sysmon EventID 11, которое покажет когда файл был записан на диск

```
index=win EventCode=11 TargetFilename="*shell.aspx"
| table _time, Image, TargetFilename
```

![[Pasted image 20260617164728.png]]

Если Sysmon EventID 11 не нашло то что нужно, мы можем проверить `POST` запросы которые содержат имя `shell.aspx` в пути

```
index=iis cs_method=POST cs_uri_query="*{WEBSHELL_FILENAME}" 
| table _time, c_ip, cs_uri_stem, cs_uri_query, sc_status 
| sort _time
```

![[Pasted image 20260617164906.png]]

Следует помнить что некоторые легитимные `.NET` приложения заставляют w3wp.exe запускать дочерние процессы, такие как csc.exe(компилятор C#) Отличительным фактором является то, какие команды исполняются

# Exchange, OWA и атаки на учетные данные
Развертывание Веб-шелов это один из способ атаки на IIS-приложения, но более распространенный вектор первоначального доступа - атаки на учетные данные через страницы входа. Exchange OWA - одна из самых популярных атакуемых точек в корпоративных средах: это шлюз к корпоративной почте, доступный из интернета по своей природе

Exchange работает на IIS, поэтому те же паттерны обнаружения через `w3wp.exe` применимы и здесь. Но данная задача сосредоточена именно на атаках учетных данных.

Терминология:

- Exchange - сервер, обрабатывающий доставку почты, календарь и контакты
- OutLook - десктопный клиент
- OWA - (Outlook Web Access) - браузерная версия работающая на IIS

## Как OWA выглядит в логах
Нормальный вход в современный Exchange: один `POST` на `/owa/auth.owa`, затем редирект 302 на почтовый ящик, затем `GET` запросы при загрузке интерфейса

![[Pasted image 20260617171530.png]]

Провальный вход так же возвращает 302, но редирект идет обратно на страницу входа а не в почтовый ящик. Таким образом, HTTP код статуса сам по себе не позволяет определить был ли вход успешным.

![[Pasted image 20260617171541.png]]

Признаки неудачного входа в query string:

- `reason=2` - способ OWA сигнализировать об ошибке аутентификации
- `url` - страница на которую пользователь пытался попасть

Далее можно смотреть на Windows Security. При расследованиях OWA переходят к ним Event 4624 и 4625 всегда фиксируют имя учетной записи 

IIS логи и логи Windows Security дополняют друг друг при расследовании инцидентов OWA.

![[Pasted image 20260617171849.png]]

Необходимо знать два основных пути 

- `/owa` - страница входа в Outlook Web Access. Именно здесь происходят атаки на учетные данные
- `/ecp` - панель управления Exchange, административный интерфейс. Доступ к этому пути должен быть редким и тщательно контролироваться, поскольку оттуда злоумышленник может создавать правила пересылки, экспортировать почтовые ящики или изменять настройки Exchange

# VPN и Active Directory
## Аутентификационный поток VPN

В большинстве коммерческих сред VPN не взаимодействует с AD напрямую - он использует RADIUS как посредник. На Windows RADIUS-сервер называется NPS(Network Policy Server)

Поток аутентификации можно изобразить следующей диаграммой:

![[Pasted image 20260617175547.png]]

NPS генерирует Event 6272/6273, DC генерирует 4624/4625
NPS события появляются только если VPN шлюз настроен на RADIUS. Если шлюз шлюх аутентифицирует напрямую через LDAP - NPS событий нет. Детектирование тогда опирается на Event 4624/4625 на самом VPN шлюзе и Event 4776 на DC для проверки учетных данных

Event ID NSP

| Event ID | Значение               | Значимость для безопасности         |
| -------- | ---------------------- | ----------------------------------- |
| 6272     | NPS предоставил доступ | Успешная VPN аутентификация         |
| 6273     | NPS отказал в доступе  | Неудачная NPS аутентификая          |
| 6274     | NPS отбросил запрос    | некорректный или отклоненный запрос |
