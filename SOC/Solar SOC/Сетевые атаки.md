Сетевая атака - это вмешательство в передачу данных между узлами или нарушение логики работы сетевого взаимодействия

Модель OSI помогает структурировать типы атак по 7 уровням сетевой архитектуры 

| Уровень OSI          | Пример атаки                            |
| -------------------- | --------------------------------------- |
| 1 - Физический       | Подмена кабеля или внедрение устройства |
| 2 - Канальный        | ARP Spoofing, MAC Flooding              |
| 3 - Сетевой          | IP Spoofing, Route Injection            |
| 4 - Транспортный     | TCP Flood, UDP Flood                    |
| 5 - Сеансовый        | SSL downgrade, Session Hijacking        |
| 6 - Представительный | SSL Stripping, Code Injection           |
| 7 - Прикладной       | SQLi, XSS, XXE, SSRF, DNS Spoofing      |
# MITM (MAN IN THE MIDLE)

MITM или "Человек по середине" - большой класс атак, который направлены на встраивание третьего абонента в канал связи между двумя легитимными абонентами

Встраивание в канал может выливаться в попытки прослушать трафик, расшифровать его и перехватить общение. Таким образом, атаки класса MITM способны приводить к нарушению конфиденциальности и целостности информации. Для прослушивания трафика используется такой класс утилит как "снифферы"

Снифферы - программы которые способны перехватывать и анализировать сетевой трафик

Они полезны в случаях когда нужно извлечь из потока данных какие либо сведения, например, пароли или провести диагностику сети
Перехватить трафик через снифер можно следующим образом

- Путем прослушивания в обычном режиме сетевого интерфейса
- Подключением в разрыв канала
- Перенаправлением трафика
- Посредством анализа побочных электромагнитных излучений
- При помощи атаки на уровень канала и сети, приводящей к изменению сетевых маршрутов

Поток данных перехваченный сниффером подвергается анализу, что позволяет:

- Выявить паразитный трафик (его присутствие значительно увеличивает нагрузку на сетевое оборудование)
- Обнаружить активность вредоносных и нежелательных программ (сканеры сети, трояны, флудеры, пиринговые клиенты)
- Произвести перехват любого зашифрованного или незашифрованного трафика пользователя для извлечения паролей и других ценных данных
# Физический уровень (L1 Physical Layer)

В модели OSI обеспечивает передачу сырых битов по физической среде: витой паре, оптоволокну, радиоканалу. На этом уровне работают интерфейсы, разъемы, кабели, передатчики и приемники

Он не содержит логики, протоколов адресации но нарушение его целостности может полностью парализовать сетевую инфраструктуру

## Типы атак на физическом уронве

Несмотря на кажущуюся "низкоуровневость" он все же привлекает внимание злоумышленников из за нескольких факторов: возможности физического подключения к линии, отсутствия контроля в большинстве систем мониторинга и сложности оперативного выявления. Например наиболее часто можно встретить следующие типы атак:

1. Физический перехват трафика через пассивные TAP устройства
2. Создание невидимых снифферов на базе минипк, например Raspberry PI
3. индуктивное считывание данных: EM-атаки, побочные каналы
4. Нарушение целостности кабелей или подмена соединений
5. Физический MITM - подключение между патч панелью и оборудованием

**Подробный сценарий действий злоумышленника**

**Установка скрытого сниффера**

Разберём детализированный план действий атакующего на примере одного из типов атак.

**Цель атакующего:** незаметно перехватить сетевой трафик между рабочими станциями и коммутатором, не нарушая соединение.

**Сценарий атаки:**

1. **Физический доступ к инфраструктуре.** Атакующий получает временный доступ в серверную, коммутационный шкаф или к линии Ethernet.
    
2. **Установка устройства-перехватчика.** Для этого атакующий использует мини-ПК (например, Raspberry Pi Zero) с двумя USB-Ethernet адаптерами или встроенным портом.
    
3. **Запуск перехвата.** Интерфейс переведён в promiscuous mode, атакующий использует инструменты «tcpdump» или «tshark».
    

```bash
tcpdump -i eth0 -w capture.pcap 
```

4. **Скрытное копирование данных.** Через Wi-Fi, Bluetooth или периодическое физическое извлечение SD-карты.

## Что видит SOC аналитик

В процессе атаки аналитик может наблюдать и анализировать признаки, которые помогают понять какие именно индикаторы могут указывать на атаку и как их интерпретировать в рамках своих рабочих задач.

- Прямых признаков в логах или SIEM нет
- При наличии SPAN-портов - можно отследить дублирующий MAC адрес

Косвенные индикаторы:

- Падение скорости соединения
- Рост коллизий или ошибок CRC
- Появление событий контроля доступа (вскрытие шкафов, отключения тревоги)

# Канальный уровень (L2)

Канальный уровень (L2) отвечает за передачу кадров между узлами в пределах одной локальной сети. Здесь работают MAC адреса, протоколы ARP, STP, VLAN, происходят: фрейминг, обнаружение ошибок и управление доступом к среде

Роль канального уровня - ключевая для локальной адресации внутри подсети и он тесно связан с функционированием коммутаторов

## Типы атак на канальном уровне

Этот уровень считают внутренним и потому менее защищенным. Однако атаки здесь высокоэффективны и особо опасны в корпоративных сегментах из-за невидимости для большинства SIEM и логов. Например, наиболее часто встречаются следующие типы:

MAC-Spoofing - это атака канального уровня, суть которой заключается в изменении MAC адреса на сетевой карте, что заставляет коммутатор отправлять на порт, к которому подключен злоумышленник, пакеты, которые до этого он видеть не мог. Либо злоумышленник сможет пройти аутентификацию, в случае если используется сверка по MAC-адресу

На практике MAC-spoofing часто сочетается с атака ARP Spoofing и MAC Flooding

## ARP-Spoofing
ARP-Spoofing (ARP Poisoning) - это техника сетевой атаки, применяемая преимущественно в Ethernet, но возможна и в других сетях, использующих протокол ARP

Она основана на использовании протокола ARP и позволяет перехватывать трафик между узлами, которые расположены в пределах одного широковещательного домена

К недостаткам протокола ARP можно отнести то, что он является незащищенным, так как он не способен проверить подлинность как запросов, так и ответов ARP. Для реализации спуфинга используется самопроизвольный ARP

Самопроизвольным называют ответ ARP, присланный без запроса. Применяется для определения конфликтов IP-адресов в сети: как только станция получает адрес по DHCP или адрес присваивается вручную, рассылается самопроизвольный ARP ответ

Он является небезопасным, поскольку с его помощью можно убедить удаленный узел в том, что MAC адрес какой либо системы, находящейся с ней в одной сети, изменился и указать какой адрес используется теперь

![[Pasted image 20260701191834.png]]

Принцип ARP-спуфинга следующий:

1. Злоумышленник (192.168.0.16) формирует ARP ответ и отправляет его на хост 192.168.0.14
2. Хост 192.168.0.14 меняет запись в своей ARP таблице: теперь шлюз по умолчанию это MAC3 а не MAC-роутера в рамках широковещательного домена
3. Хост 192.168.0.14 отправляет запросы в Интернет, но они идут в первую очередь на MAC3. А хост злоумышленника их уже переотправляет от своего имени на роутер а затем они уходят в интернет 

Таким образом злоумышленник сможет читать и видоизменять весь трафик хоста 192.168.0.14 в случае если шифрование не используется

## Методы защиты от ARP-спуфинга
- Чтобы нивелировать угрозу от самопроизвольных ARP ответов, можно задавать записи в ARP таблицах статически. Такие записи всегда будут иметь приоритет над динамическими записями. Как правило это действие потребуется только если записи соответствия MAC адреса шлюза и его IP адреса в ARP таблице 
- Сегментация сети на VLAN сужает поверхность атаки, так как атака ARP Spoofing актуальна в рамках одной широковещательной сети

## MAC-flooding

Это атака категории DDoS. Суть заключается в том, что атакующий высылает через коммутатор кадры со случайными MAC адресами отправителя тем самым забивая таблицу коммутации.

Она встречается нечасто, потому что злоумышленник должен получить доступ в локальную сеть компании. А когда злоумышленник уже проник внутрь, то DDoS средствами сетевых протоколов - это последнее что он будет делать 

Многие продвинутые коммутаторы могут быть настроены на ограничение количества MAC адресов, которые можно установить на портах подключенных к конечным станциям. Кроме того, можно включить аутентификацию обнаруженных MAC адресов на сервере аутентификации, авторизации и учета (ААА), а так же последующую фильтрацию мусорных MAC адресов

## **Подробный сценарий действий злоумышленника**

### ARP-Spoofing (MITM через ARP)

Цель атакующего: перехватить и модифицировать трафик между жертвой и шлюзом

Сценарий атаки:

- Атакующий сканирует сеть и определяет IP адреса, шлюза и жертву
- Подменяет ARP-таблицы у обеих сторон

```bash 
arpspoof -i eth0 -t 192.168.0.5 192.168.0.1 
arpspoof -i eth0 -t 192.168.0.1 192.168.0.5 
```

Теперь весь трафик между жертвой и шлюзом идет через атакующего

- Атакующий прослушивает трафик используя снифер а иногда модифицирует его с помощью Bettercap
- Для расшифровки и прослушивания трафика защищенного SSL/TLS злоумышленник может использовать утилиты, такие как SSLStrip. (Такой вектор будет рассмотрен в рамках сеансового уровня модели OSI)

## Что видит SOC аналитик

Появление новых, неизвестных сетевых устройств, подключенных в сети. Нередко коммутаторы и DHCP серверы способны залогировать факт появления нового хоста в сети и факт запроса IP конфигурации у DHCP сервера

Если сетевое устройство ранее не показывалось в сети, это может говорить о том, что 

- Сотрудник принес внештатное устройство на котором могут быть вирусы и отсутствуют политики безопасности, принятые в компании
- злоумышленник подключился к сети чтобы атаковать ее

Косвенные признаки:

- множественные ARP запросы от одного MAC
- частая смена MAC адресов у одного IP
- рост широковещательного трафика

в NIDS (например Suricata)

- ARP poisoning detected
- конфликты MAC/IP 

## **Примеры логов канального уровня**

**Атака:** ARP Spoofing (Man-in-the-Middle)

**Источник:** Suricata IDS / Zeek / PCAP

```
log
[] [1:1226:10] ET ARP Spoof Gratuitous ARP Duplicate Address Detected
[] [Classification: Attempted Information Leak]
[Priority: 2]
04/19-13:45:12.412103 10.0.0.5 -> 10.0.0.1 ARP
Opcode: reply | Sender MAC: aa:bb:cc:dd:ee:ff | Sender IP: 10.0.0.1
```

IDS сообщает, что два разных MAC-адреса претендуют на один и тот же IP — вероятный MITM через ARP.

**Атака:** MAC Flooding

**Источник:** лог коммутатора / SNMP / NDR

```
log
%SW_MGMT-4-MACFLD_EXCEED: CAM table exceeded threshold on port Gi1/0/24
%SW_MGMT-6-STORM: Unicast storm detected on VLAN 10
```

Коммутатор сигнализирует, что количество MAC-адресов на порту превышено, начался broadcast на все порты.

**Атака:** VLAN Hopping (Double Tagging)

**Источник:** PCAP (Wireshark)

```
Frame 1: 802.1Q VLAN tagged frame
Outer VLAN ID: 10
Inner VLAN ID: 20
Payload: ICMP echo request from 10.0.20.5 to 10.0.20.1
```

На одном уровне VLAN 10, но во вложении — трафик предназначен VLAN 20. Это является признаком атаки double-tagging.

**Атака:** DHCP Spoofing

**Источник:** лог DHCP-сервера / Zeek

```
log
04/19/2024 14:02:18 DHCP OFFER from 192.168.0.99
Gateway: 192.168.0.254 | DNS: 8.8.8.8 | Lease Time: 600s
Alert: Unauthorized DHCP server detected
```

В сети появился второй DHCP-сервер, предлагающий другой шлюз. Это говорит о возможном MITM или захвате управления сессией.

## **Рекомендации по защите**

Для эффективного реагирования на атаки сетевого уровня аналитик SOC должен уметь распознавать признаки таких сетевых аномалий, таких как широковещательная активность, внезапные изменения MAC-адресов, ARP-конфликты, и при необходимости оперативно инициировать анализ сетевого трафика (PCAP/дамп). Однако одних лишь знаний недостаточно: необходимо техническое укрепление сетевой инфраструктуры, которое включает следующие меры защиты:

- включение Dynamic ARP Inspection (DAI) на коммутаторах;
    
- ограничение количества допустимых MAC-адресов на порт с помощью Port Security;
    
- активация DHCP Snooping для контроля доверенных источников IP;
    
- настройка постоянного мониторинга ARP и использование SPAN-портов;
    
- применение 802.1X и сегментации сети с использованием VLAN.
    

Это позволит не только уменьшить риск сетевых атак, но быстрее выявлять и локализовать потенциальные инциденты безопасности.

# Сетевой уровень L3

## Типы атак на сетевом уровне

- IP-Spoofing - подделка IP-адреса источника
- ICMP-redirect - отправка ложных ICMP пакетов с целью изменить маршрут
- DoS через ICMP Flood / Smurf - перегрузка через отраженные ICMP
- BGP Hijacking - перехват маршрутов между провайдерами
- Ip Fragmentations Attacks - обход фильтрации через дробление IP пакетов

### IP Spoofing
Суть атаки заключается в подмене IP адреса отправителя и том, что при маршрутизации сетевое оборудование проверяет только IP адрес получателя, но не отправителя. Подмена IP может сопровождаться множеством активных угроз:

- Обход политик безопасности(обход ACL на межсетевых экранах, получение доступа в нужный VLAN, получение доступа в локальную сеть из интернета)
- DDoS (Отправки пактов с подменным IP чтобы на него приходили подменные пакеты)
- сокрытие реального адреса атакующего

Для реализации атак используются специальные утилиты, например в kali специальная утилита `spoof`

![[Pasted image 20260817181845.png]]

Недостатком атаки для злоумышленника является то что он не сможет получать ответные пакеты, потому что изначально указал неправильный адрес отправителя

#### Защита от IP спуфинга

Такие атаки можно предотвратить с помощью фильтра пакетов, который настроен таким образом, чтобы не пропускать пакеты поступившие через неопределенные сетевые интерфейсы. 
Еще один способ защиты это проверка адреса отправителя, которая выполняется программами маршрутизации

Простейшим способом проверить, что подозрительный пакет пришел от верного отправителя это отправить пакет на IP отправителя. Обычно для спуфинга используется случайный IP, и вполне вероятно что ответ не придет. Если же придет следует сравнить TTL. Если поля не совпадают то веротянопришли из разных источников

Также на большинстве современных роутеров стоит ограничение. Оно отбрасывает пакеты на интерфейсах, на которые не мог прийти пакет с указанного Source IP. Например если на WAN порт приходит пакет с IP из LAN, то это как минимум странно

Кроме перечисленных методов, можно назвать еще шифрование. как правило трафик шифруется с помощью сертификатов, который злоумышленнику изначально не известен. Защита заключается в блокировании незашифрованного трафика, либо такого трафика который невозможно прочитать

# Транспортный уровень L4
## SYN flood

Цель атаки завалить TCP стек целевого хоста висящими соединениями и вызвать отказ в обслуживании

При проведении таких атак злоумышленники интенсивно отправляют из бот-сети сервер большое количество SYN пакетов с поддельными IP адресами, это заставляет сервер реагировать, отправляя SYN-ACK в ответ на каждый ложный запрос, выделяя часть ресурсов и оставляя свои порты открытыми на каждый ложный запрос, выделяя часть ресурсов для ожидания ответов от хостов, которых на самом деле не существует и подтверждений они отправлять не будут

![[Pasted image 20260817192302.png]]

Атаку легко обнаружить по всплеску TCP пакетов SYN, в wireshark можно использовать следующий фильтр  

```
tcp.flags.syn == 1 and tcp.flags.ack == 0
```

![[Pasted image 20260817192546.png|871]]

Источники каждого SYN пакета отличаются но все имеют идентичный порт назначения 80 (HTTP), идентичную длину (120) и размер TCP окна 64

Если мы зададим фильтр

```
tcp.flags.syn == 1 and tcp.flags.ack == 1
```

То увидим количество полученных пакетов от клиентов(сразу с установленным флагом SYN а затем с флагом ACK) относительно небольшое. Это верный признак атаки TCP SYN Flood 

![[Pasted image 20260817192832.png]]

Мы также можем посмотреть графики Wireshark для визуального представления о росте трафика. График полученных/отправленных пакетов можно получить с помощью выбора меню _«Statistics —> I/O Graph»_.

## Способы борьбы с SYN Flood

- Выделять под каждый SYN запрос микрозапись на 16 байт вместо создания полноценного соединения на сервере
- Использовать SYN cookies После получения сегмента с флагом SYN, сервер отвечает сегментом SYN-ASK и тут же отчищает память выделенную под соединение, а когда вернется ответ с флагом ACK то соединение продолжится в обычном режиме
- Уменьшение времени ожидания ACK после отправки SYN+ACK в тройном рукопожатии 
- Использование средств Anti-DDoS

## UDP Flood 
В процессе UDP флуда сервер жертва получает огромное количество UDP дейтаграмм в единицу времени от широкого диапазона подменных IP-адресов. Атака провоцирует перегрузку сетевых интерфейсов посредством того, что занимает всю полосу пропускания

Учитывая что объемы атаки могут достигать сотен Гбит/с, необходимы каналы соответствующей емкости, не говоря о вычислительных мощностях, которые нужны для его обработки и отчистки, чтобы принять такой объем трафика

### Защита от UDP flood

- Закрытие неиспользуемых портов, блокирование UDP трафика на TCP порты. 
- Использование специализированных систем защиты от DDoS 
## RST Flood

Это DDoS атака, которая способна нарушить работоспособность сети путем забивания канала и ресурсов на устройствах с отслеживанием состояния (SPI)

В общем случае чтобы закрыть TCP сессию между клиентом и хостом производится обмен RST или FIN сегментами. Во время RST или FIN Flood сервер жертва на высокой скорости получает поддельные RST или FIN пакеты, не имеющие отношения к любой из сессий в базы данных сервера. 
Сервер жертвы вынужден выделять значительное количество системных ресурсов для сопоставления входящих пакетов с текущими соединениями, что приводит к потере производительности сервера и его частичной недоступности

# Сеансовый уровень L5

Управляет установкой, поддержанием и завершением логических соединений между взаимодействующими приложениями. Особенно он важен для удаленных подключений, потоковых сервисов, аутентификации и синхронизации

## Типы Атак на сеансовом уровне

- Session Hijacking - перехват активного сеанса с подменой идентификатора или состояния
- Session Fixation - навязывание предопределенного ID до входа пользователя
- SMB/RDP Relay - передача данных аутентификации другому хосту
- Token Replay - повторное использование сеансовых токенов (NTLM, Kerberos)

## SSL Negotation Flood

SSL Negotation Flood пытается установить множество новых SSL рукопожатий с целевым сервером. Каждое рукопожатие представляет новое TCP соединение и влияет на целевой сервер. Открывая и закрывая множество таких соединений, рукопожатия SSL/TLS потребляют до 15 раз больше ресурсов ЦП на сервере чем на клиенте 

## Примеры логов при атаках на сеансовом уровне: 

**Атака:** Session Hijacking (cookie reuse)

**Источник:** веб-сервер / NGINX лог / прокси

```
log
192.0.2.77 - - [20/Apr/2024:09:48:32 +0000] "GET /dashboard" 
User-Agent: Mozilla/5.0 
Cookie: session_id=ABC123 
Note: Same session_id used concurrently from 2 IPs: 192.0.2.77 and 198.51.100.99
```

Сессия используется одновременно с двух адресов - это признак её перехвата или повторного воспроизведения.

# Уровень представления L6

Уровень представления отвечает за преобразование и интерпретацию данных между приложениями включая их кодирование, шифрование и форматирование, сериализацию а также обработку протоколов SSL/TLS и MIME

## Типы атак на уровне представления 

На этом уровне часто реализуется шифрование трафика и компрессия. Например

- TLS Downgrade / SSL Stripping - принудительный перевод HTTPS на HTTP
- Padding Oracle - атака на уязвимости в реализации блочного шифрования
- Кодировочные атаки - манипуляции с Unicode/UTF, Base64 для обхода фильтров
- Инъекции в сериализацию (PHP, Java) - RCE через поддельные структуры 
- XXE - извлечение данных с помощью внешних сущностей
- SSL DDoS - неверные запросы SSL. Проверка зашифрованных пакетов требует больших ресурсов 
## SSL Stripping 

Целью атаки является получение конфиденциальной информации передаваемой по HTTPS

Сценарий атаки:

1 Пользователь открывает сайт без указания протокола: `http://example.com`
2 Атакующий перехватывает первый запрос и блокирует переход на HTTPS
3 Атакующий запускает sslstrip который подменяет HTTPS на HTTP в теле странцы
4 Пользователь работает в незашифрованной сессии, вводит логин и пароль
5 Атакующий получает все данные в открытом виде

## Пример логов для транспортного уровня 

**Атака:** SSL Stripping

**Источник:** Прокси / NGINX / PCAP

```
log
Request: http://secure.example.com/login 
Referer: http://secure.example.com/ 
User-Agent: Mozilla/5.0 
Note: Expected HTTPS, but connection is over HTTP 
HSTS header: not present 
```

Запрос к защищённому ресурсу пришёл через HTTP — это может быть результатом SSL Stripping через MITM.
