# Сетевая модель TCP/IP

Стек протjколов TCP/IP (Transmission Control Protocol//Internet Protocol) - сетевая модель которая описывает процесс передачи цифровых данных. Она названа по двум главным протоколам, по этой модели построена глобальная сеть интернет. 

Модель состоит из 4 уровней
## 1 Канальный уровень (link layer)
Уровень доступа к сети. Протоколы Ethernet, Wifi, Bluetooth. Предназначение канального уровня - дать описание тому как происходит обмен информацией на уровне сетевых устройств, определить как информация будет передаваться от одного устройства к другому. Информация здесь кодируется, делится на пакеты и отправляется по нужному каналу, т.е. среде передаче.
Как работает:
Данные делятся на небольшие кусочки фреймы и передаются между устройствами. Каждый фрейм содержит часть передаваемой информации и служебные данные. Чтобы понять куда отправляются фреймы, используют адресацию канального уровня - MAC адреса. Это уникальные физические адреса устройств по тип протоколы канального уровня определяют отправителей и получателей

MAC-адрес
Комбинация цифр и букв длиной 48 бит
00-50-B6-5B-CA-6A                                                                         
Базовые команды:                                                                       
*ifconfig -a*
*ip link list*
*ip address show*
*ipconfig /all*  

Для приема сообщений из сети и отправку их в сеть хост использует интерфейсы. Физический интерфейс отправляет и принимает фреймы, а логический интерфейс отправляет и принимает IP пакеты. Физический интерфейс идентифицируется - MAC адресом, логический интерфейс - IP адресом
## 2 Межсетевой уровень, уровень интернета(internet layer)
Протоколы IPv4 IPv6 ICMP ARP
Межсетевое взаимодействие - это основной принцип построения интернета. Локальные сети по всему миру объединены в глобальную, а передачу данных между этими сетями осуществляют магистральные и пограничные маршрутизаторы

Именно на межсетевом уровне функционирует протокол IP, позволивший объединить разные сети в глобальную 
## 3 транспортный уровень (transport layer)
TCP, UDP 
## 4 Прикладной уровень (application layer)
HTTP, HTTPS, Telnet, SSH, DNS, DHCP

# Компьютерные сети: Фундаментальные основы и архитектура

Ключевые выводы:

- Сетевое взаимодействие - строится на наборе протоколов, где каждый последующий уровень решает задачи, не охваченные предыдущим
- Модель TCP/IP является практическим стандартом реализации сетей в то время как OSI служит эталонной теоретической базой
- Адресация разделена на два типа: неизменные физические MAC адреса для локальной передачи и логические IP адреса для глобальной маршрутизации
- Транспортный уровень предлагает выбор между надежностью TCP и скоростью UDP в зависимости от бизнес задач
- Глобальная маршрутизация (BGP) базируется не только на технических параметрах но и на политических и экономических соглашениях между автономными системами

# Сети основное от солар

Хост - узел сети, любое сетевое устройство подключенное к локальной или глобальной сети
Протокол - набор правил для описания взаимодействия между двумя уровнями в пределах одного хоста.
Интерфейс - инструмент для описания взаимодействия между двумя уровнями в пределах одного хост
Сетевой интерфейс - физическое или виртуальное устройство, предназначенное для передачи данных программами через компьютерную сеть

Данные могут передаваться как через физические интерфейсы сетевых карт и телекоммуникационных устройств, так и через открытые логические соединения, а взаимодействие между интерфейсами определяется сетевыми протоколами

Сетевой протокол - набор правил определяющих способы управления соединениями на физическом и логическом уровнях. Для выполнения своих функций одни протоколы часто используют другие протоколы

## модель ISO/OSI 
Это эталонная модель сети, которая описывает взаимодействие устройств в сети.

Идеальная модель сети ISO/OSI не нашла применения в реальной жизни однако продолжает использоваться как эталонная, например, для обучения молодых специалистов. Кроме того она не является сетевой архитектурой, как как не содержит в себе описание протоколов, но в качестве "общего языка" для описания работы различных сетей вполне подходит

Обычно стандарты в области сетевых технологий описаны организацией IETF в виде документа RFC. Если возникают какие либо вопросы по конкретному протоколу и технологиям то ответ можно найти в первоисточнике на английском языке. Стоит так же отметить, что RFC не имеют ничего общего с нормами законодательства их исполнение и регламентирование не обязательно

Теоретически можно без проблем видоизменить любой из протоколов, но в таком случае твое общение с окружающим сетевым миром встанет под вопрос. Нужно быть точно уверенными что на другом конце тебя поймут иначе возможны ошибки или полный разрыв связи

# Модель TCP\IP ее сходства и различия с моделью OSI

Обычно последние три уровня модели объединяют в прикладной а первый два в канальный. Транспортный уровень TCP/IP включает в себя функции транспортного уровня OSI и некоторые функции сеансового уровня модели OSI. Таким образом теоретическая модель OSI сжимается до применяемого на практике четырехуровневого стека протоколов TCP/IP

![[Pasted image 20260624181845.png]]

В модели OSI не все уровни могут быть задействованы в процессе передачи данных, но уровни с 1 по 3 всегда участвуют при любой передаче данных между двумя хостами. Для обращения хоста самого на себя используют другие интерфейсы

## Общая схема передачи данных по уровням модели OSI
![[Pasted image 20260624182244.png]]

Согласно представленной схеме, протокол прикладного уровня запаковывает (инкапсулирует) информацию на ниже стоящие протоколы вплоть до физического уровня а затем производится непосредственно передача данных, а со стороны рабочей станции 2 осуществляется декапсуляция

Для передачи данных между разными хостами требуется обращаться к физическому уровню модели OSI. Однако в случае передачи данных на localhost сетевые протоколы обеспечивают межпроцессное взаимодействие и могут работать например, только на прикладном уровне

В зависимости от особенностей сети и передачи данных выделают три типа каналов связи

- Симплексные (только водном направлении)
- Дуплексные (в двух направлениях)
- Полудуплексные (передавать данные могут оба но не одновременно)

В качестве примера можно привести разговор по рации когда они слушает отправителя и не имеет возможности передавать данные а потом участники меняются ролями и передача идет в другом направлении

От выбранного канала связи зависит то, смогут ли рабочие станции общаться одновременно или хотя бы по очереди либо вторая будет всегда слушать а первая только передавать

# L2 OSI

Канальный уровень предназначен для обмена данными между устройствами в одном сегменте локальной сети.

Он разбивает информацию на кадры (frames) и контролирует их доставку, помогая устройствам правильно отправлять и получать данные. При создании кадров к данным добавляется заголовок с нужной служебной информацией для их правильной доставки, а затем кадры передаются на физический уровень согласно правилам доступа к сети.

## За что отвечает канальный уровень 

- Форматирование данных
- Обнаружение и исправление ошибок
- Управление доступом к середе
- Адресация

## Для чего нужна адресация

Адресация позволяет устройствам идентифицировать друг друга в рамках одного сегмента сети. 

Адрес канального уровня (MAC-адрес) - это уникальный адрес который зашивается в прошивку сетевой карты

Он состоит из 6 октетов (48бит):

- Первые три это идентификатор производителя
- Вторые три это идентификатор самого устройства

![[Pasted image 20260624190758.png]]

Существуют так же специальные MAC адреса которые не принадлежат конкретным устройствам. Например такой FF:FF:FF:FF:FF:FF - широковещательный. Все биты широковещательного адреса выставлены в 1. Фреймы отправленные на такой адрес получают все устройства локальной сети

Еще бывают мультикаст адреса. Эти адреса начинаются с 01:00:5E а оставшаяся часть формируется из 23 бит группового адреса 3-го (сетевого уровня), преобразованных в 6 шестнадцатеричных символов. Фреймы отправленные на такой, получает конкретная группа узлов

## Что такое ARP и зачем он нужен
ARP (Address Resolution Protocol) - протокол который помогает устройствам в сети найти друг друга. А точнее узнать MAC адрес зная только IP

Такое преобразование требуется когда IP пакет требуется передать по локальной сети. А хосты в локальной сети, взаимодействуют в рамках канального уровня модели OSI

### Место ARP в сетевой модели

ARP работает на канальном уровне (в модели OSI это уровень 2), но в тоже время оперирует данными (IP-адресами) 3 уровня модели OSI

- ARP не маршрутизируется через интернет
- Он используется только внутри локальных сетей

То есть ARP помогает общаться устройствам внутри сети - например внутри офиса или дома. Он помогает согласовывать передачу между 2 и 3 уровнями
### Как работает ARP запрос ответ

Работа ARP состоит из дву шагов

1 ARP запрос (ARP Request)

Когда устройство не знает MAC адрес устройства оно отправляет широковещательный ARP запрос:

У кого IP адрес 192.168.0.20 сообщите мой свой MAC

Этот запрос получают все устройства в Сети, но отвечает только тот у кого этот IP

2 ARP ответ (ARP reply)

Устройство с искомым IP отправляет ответ:
Это мой IP, вот мой MAC

Теперь компьютер знает куда отправлять данные

### Структура ARP пакета

Пакет состоит их 3 полей

- MAC адрес отправителя 
- IP отправителя
- MAC получателя 
- IP получателя

### ARP таблица

ARP таблица хранится в памяти устройства и содержит строки соответствия MAC и IP адресов для каждого узла сети. Пример таблицы 

| IP-адрес    | MAC-адрес         | Тип          |
| ----------- | ----------------- | ------------ |
| 192.168.0.1 | 08:00:34:00:2F:C3 | Статический  |
| 192.168.0.2 | 08:00:10:98:AC:24 | Динамический |
Статическая запись - запись которая внесена в таблицу вручную

Динамическая запись - которая появилась в результате работы RP. Такие записи имеют срок жизни, после которого удаляются. Сделано для отслеживания IP адресов хостов

### Обратный ARP запрос

иногда возникает ситуации когда нужно найти IP по известному MAC. Тогда действие вступает реверсивный протокол разрешения адресов (RARP)

![[Pasted image 20260624194550.png]]

Протокол применяется во время загрузки узла (например компьютера) когда он посылает групповое сообщение-запрос со своим физическим адресом. Сервер принимает это сообщение и просматривает свои таблицы в поисках IP адреса, соответствующего физическому. После обнаружения найденный адрес отсылается обратно на запросивший его узел. Другие станции также могут слышать этот диалог и локально сохранять эту информацию в своих ARP таблицах.

![[Pasted image 20260624194902.png]]

## Как протокол ARP может быть использован в атаках

Протокол ARP разработан в эпоху когда безопасность не стояла на первом месте

Его основная задача это соотнести IP адрес с MAC в пределах локальной сети. Но у него есть один большой недостаток

ARP не проверяет достоверность данных

Любое устройство в локальной сети может отправить ARP ответ - даже если его никто не спрашивал, и даже если оно лжет

### ARP работает по принципу доверия

- Если устройство слышит, что "IP 192.168.1.1 принадлежит MAC AA:BB:CC:DD:EE:FF" — оно **обновит свою ARP-таблицу**.
    
- Это происходит **даже если этот MAC не принадлежит настоящему владельцу IP.**

В итоге любое устройство сети может представиться другим

### ARP Spoofing(подмена ARP-запросов) 
Самая распространенная сетевая атака. Важно знать ARP Spoofing это синоним ARP Poisoning. 
Они обозначают одно и тоже злоумышленник внедряет ложные ARP ответы, чтобы изменить таблицу соответствий IP и MAC у других устройств. 

### Как обнаружить ARP атаки с помощью Wireshark

- Один IP привязан сразу к нескольким MAC адресам
- Частые повторяющиеся ARP ответы
- Много ARP запросов от одного устройства за короткое время

## NAT

> [!NOTE] NAT
> Network Address Translation - технология которая позволяет транслировать один адрес в другой

Существует 3 режима работы NAT

1 Статический

Каждому серому адресу ставится в соответствие адрес глобальной сети или адрес смежной серой подсети

Это справедливо и для обратного случая NAT может описывать трансляцию адресов смежной LAN или глобальной WAN в какую либо частную подсеть.

## TLS Hand Shake
Перед началом обмена данными через TLS, клиент и сервер должны согласовать параметры соединения а именно: версию используемого протокола и способ шифрования данных. И если это необходимо проверить сертификаты

Этот процесс называется TLS Handshake(рукопожатие между клиентом и сервером).

![[Pasted image 20260625165830.png]]

### 1 шаг

Установка TCP соединения между клиентом и сервером. Перед шифрованием необходимо установить базовое соединение на 4 уровне с использованием TCP

### 2 шаг

Фаза переговоров 

- Клиент посылает сообщение ClientHello, указывая последнюю версию поддерживаемого TLS-протокола, случайное число и список поддерживаемых шифронаборов, подходящих для работы TLS.
- Сервер отвечает сообщением ServerHello, который содержит: выбранную сервером версию протокола, случайное число, сгенерированное сервером и выбранный шифронабор из списка, который предоставил клиент
- Сервер посылает Certificate, которое содержит цифровой сертификат сервера.
- Если переданных сервером данных недостаточно для выработки общего симметричного секретного ключа в рамках выбранного шифронабора, то сервер передает сообщение ServerKeyExchange, которое содержит необходимые данные

Например в ServerKeyExchange передается серверная часть обмена для протокола Диффи-Хелмана

- Сервер отсылает сообщение ServerHelloDone, идентифицирующее окончание первого раунда установки соединения 
- Клиент отвечает сообщением ClientKeyExchange, которое содержит клиентскую часть протокола диффи хэлмана или зашифрованный открытым ключом из сертификата сервера секрет (PreMasterSecret)
- Клиент и сервер используя ключ PreMasterSecret и случайно сгенерированные числа, вычисляют общий секрет. Вся остальная информация о сеансовом ключе будет получена из общего секрета.
- Клиент отсылает сообщение ChangeCipherSpec, которое указывает на то, что вся последующая информация будет зашифрована установленным в процессе подтверждения связи алгоритмом и с использованием общего секретного ключа
- Клиент посылает сообщение Finished, которое содержит хэш и MAC, сгенерированные на основе предыдущих сообщений процедуры подтверждения связи
- Сервер пытается расшифровать Finished сообщение клиента и проверить хэш и MAC. Если процесс расшифровки или проверки не удается, подтверждение связи считается неудавшимся и соединение обрывается
- Сервер посылает ChangeCipherSpec и зашифрованное сообщение Finished. А клиент в свою очередь, тоже выполняет расшифровку и проверку

### 3 шаг 
Передача зашифрованных данных

С этого момента подтверждение связи считается завершенным, а протокол - установленным. Весь последующий обмен данными (Encrypted Data) будет зашифрован на сеансовом ключе

Был рассмотрен только процесс односторонней аутентификации, потому что сертификат проверяет только клиент

Если же сервер настроен на двухстороннюю аутентификацию, то после отправки своего сертификата он запрашивает сертификат клиента. А тот в свою очередь, отправляет сертификат

После получения сервером клиентского сертификата и его успешной проверки, взаимная аутентификация считается завершенной и сервер отправляет сообщение ServerHelloDone.

## Возобновление сессии TLS
Так как процедура установления соединения дорога то существует процесс ее восстановления

У сервера хранится кэш сгенерированных идентификаторов и параметров сеанса для каждого клиента. А клиент хранит у себя присланный идентификатор и включает его в первоначальное client hello

Если клиент и сервер имеют идентичные идентификаторы, то установка общего соединения происходит по упрощенному алгоритму, пропуская этап генерации симметричного ключа. Это значительно увеличивает длительность установки соединения, но не влияет на его безопасность, так как для этого используются ранее нескомпрометированные данные предыдущей сессии

Однако здесь кроется одно ограничение: серверу нужно хранить информацию обо всех активных сессия, а поскольку в современном интернете популярные ресурсы могут обслуживать тысячи или миллионы клиентов одновременно это требует значительных затрат для хранения.

Чтобы обойти эту проблему был разработан механизм `Session Ticket`, который устраняет необходимость сохранять данные каждого клиента на сервере.

Если клиент при первоначальной установке соединения указал что он поддерживает эту технологию, то сервер в ходе TLSHandshake отправляет клиенту Session Ticket - параметры сессии зашифрованные закрытым ключом сервера

При следующем обновлении сессии клиент вместе с Client Hello отправляет Session Tikcet. Это избавляет сервер хранить данные о каждом соединении, но делает его по прежнему безопасным так как Session Ticket зашифрован ключом, известным только на сервере.

## DNS
Протокол который преобразует доменные имена в IP адреса, так же отвечает информацией о запрашиваемых записях

Для работы DNS в основном используется UDP с портом 53 для отправки и получения запросов. Запросы и ответы, как правило, передаются в одной UDP датаграмме. Однако, если ответ от сервера превышает 512 байт, используется протокол TCP, так же с портом 53. Обычно это происходит при обмене данными между DNS серверами

### Типы ресурсных записей DNS
TTL записей DNS

записи DNS или ресурсные записи - это единицы хранения и передачи информации в DNS.

Каждая ресурсная запись состоит из следующих полей:

- Имя (NAME) - доменное имя к которому привязана или которому "Принадлежит" Ресурсная запись
- Тип (TYPE) ресурсной записи - определяет формат и назначение ресурсной записи
- Класс (CLASS) ресурсной записи - определяет тип сети. Теоретически считается, что DNS может использоваться не только с TCP/IP, но и с другими типами сетей.
- TTLS - Допустимое время хранения данной ресурсной записи в кэше неответственного DNS сервера
- Длина Поля данных (RDLEN) - указывает сколько байтов занимает поле данных этой записи. Например, в записи типа А (которая указывает на IP адрес), RDLEN будет равен 4 так как IPv4 занимает 4 байта
- Поле данных (RDATA) - содержит конкретную информацию соответствующую типу записи. Например, для записи типа "А" поле RData будет содержать IPv4-адрес

Самые частые DNS записи

- А запись - или запись адреса связывает имя хоста с адресом протокола IPv4. Например запрос А-записи на имя example.com вернет его IPv4 адрес
- AAAA запись - связывает имя хоста  с адресом протокола IPv6. Например АААА запись к example.com вернет 2001:7fd::1.
- Запись CNAME или каноническая запись используется для перенаправления на другое имя и рекурсивного запроса до получения IP адреса
- Запись MX указывает серверы обмена почтой для данного домена
- Запись NS указывает на DNS сервер для данного домена 
- PTR - связывает IP адрес хоста с его каноническим именем. Она выполняет обратную функцию по отношению к A записи, сопоставляет IP  с именем 

---
Обратный DNS запрос отправляется в специальную зону in-addr.arpa, где IP адрес указывается в обратном порядке. Например для IP адреса 192.0.34.164 запрос PTR записи 164.34.0.192.in-addr.arpa вернет каноническое имя example.com

PTR записи важны при передаче электронной почты. Почтовые серверы - получатели запрашивают PTR запись IP адреса отправителя и сравнивают ее с именем, указанным во время SMTP сеанса. При несоответствии письмо считается подозрительным и блокируется 
Пример: 

- Видит входящее соединение с IP `198.51.100.99`
- Делает PTR-запрос: спрашивает `99.100.51.198.in-addr.arpa`
- Получает ответ: `99-100-51-198.dynamic.comcast.net` — это динамический адрес Comcast, домашний интернет
- Сравнивает с тем, что заявил отправитель: `mail.bank.com`
- **Несоответствие** → письмо помечается как подозрительное или отклоняется

---

- SOA запись - (Start of Authority) или начальная запись зоны - указывает на каком сервере хранится эталонная информация о данном домене
Она содержит контактную информацию лица, ответственного за данную зону, тайминги кеширования зонной информации и взаимодействия DNS серверов
Важно учитывать что DNS серверы в интернете обладают разным уровнем доверия. Соответственно степень надежности DNS записей напрямую зависит от источника, то есть от конкретного сервера предоставившего ответ

Наиболее достоверную информацию о домене предоставляет DNS сервер который обслуживает доменную зону, то есть тот на который указывает NS запись. Такие серверы называются авторитеными

Авторитетный или авторитарный сервер - это сервер, который хранит оригинальную DNS запись, то есть ответственный за запрашиваемую зону.

Каждый домен или поддомен поддерживается как минимум одним авторитарным сервером DNS. Ответы от других серверов будут считаться Non-authoritative

С точки зрения кибербезопасности использование неавторитетных ответов DNS несет потенциальные риски, поскольку неавторитетные DNS серверы не имеют полного контроля над информацией о домене, одни могут возвращать устаревшие недостоверные или даже вредоносные данные. 

Злоумышленники могут воспользоваться этой уязвимостью, манипулируя ответами, которые предоставляют неавторитетные сервера, что приведет к отравлению кэша DNS или атакам с перенаправлением 

Тем не менее неавторитеный поиск - это фундаментальная концепция экосистемы DNS, поэтому отказаться от него невозможно. Он обеспечивает масштабируемость и производительность системы, несмотря на присущие ей уязвимости 

К сожалению традиционный DNS не имеет встроенных механизмов проверки подлинности данных. Для устранения этой проблемы был разработан DNSSEC он позволяет проверять достоверность ответов на уровне криптографической подписи. Однако на текущий момент он не получил широкого распространения

## Способы сделать DNS запрос

Рекурсивный, итеративный и смешанный DNS

Теоретически DNS серверы обрабатывают два типа запросов рекурсивные и итеративные. Однако на практике применяется смешанный подход. Рассмотрим как работает каждый из типов

### Рекурсивный DNS

Рекурсивный запрос - это запрос, на который DNS сервер обязан вернуть либо ответ запросившему компьютеру либо сообщение об ошибке

Также DNS сервер берет на себя опрос вышестоящих DNS серверов на предмет нужных данных. На практике такой способ используется нечасто

На рисунке ниже ПК с DNS клиентом обращается на свой основной DNS сервер с запросом А-записи DNS для доменной зоны rt.ru

![[Pasted image 20260626144754.png]]

DNS-серверу 1 эта доменная зона неизвестна, поэтому DNS сервер 1 перенаправляет запрос на DNS сервер 2. Аналогично с DNS сервером 3. В итоге DNS серверы 1 и 2 получают новую информацию о доменной зоне rt.ru, а DNS получает свой ответ на запрос

### Итеративный DNS
Итеративный запрос - это тип DNS запроса, при котором сервер либо возвращает запрашиваемую запись если она ему известна либо отвечает ссылкой на другой DNS обладающий более точной информацией. При этом дальнейшее разрешение имени осуществляется клиентом, который сам отправляет запрос по указанному адресу

Иными словами:

- Когда DNS сервер получает итеративный запрос, он просматривает собственную базу данных и кэш, пытаясь обнаружить в них сведения о запрашиваемом доменном имени
- Если доменное имя не может быть разрешено DNS сервером самостоятельно, клиент обратно получит ссылку на вышестоящий DNS сервер
- клиент должен повторно отправить запрос указанному серверу
- Тот в свою очередь просматривает собственную базу данных и возвращает либо адрес требуемого хоста, либо ссылается на другой сервер имен
- На одном из этапов клиент обратится к серверу имен, который уже содержит информацию о нужном доменном имени. В таком случае основная нагрузка по разрешению имени ложится на DNS клиента 

Итеративные запросы применяются в случаях когда рекурсивные запросы не поддерживаются либо DNS сервером, либо клиентом. Например администратор может отключить применение рекурсии на уровне DNS сервера

![[Pasted image 20260626145747.png]]

Представим, что хост store.khsu.ru должен установить соединение с хостом movies.yahoo.com. Для разрешения указанного доменного имени клиент предпринимает следующие шаги:

- Клиент обращается к **серверу имён, обслуживающему домен khsu.ru.** Этот сервер имён не обладает информацией о запрашиваемом имени и возвращает клиенту ссылку на вышестоящий сервер имён (обслуживающий домен ru);
    
- Клиент обращается к **серверу имён, обслуживающему домен ru**. Этот сервер имён не обладает информацией о запрашиваемом имени и возвращает клиенту ссылку на корневой сервер имен (домен «.»);
    
- Клиент обращается к **корневому серверу имён**. Корневой сервер имён обнаруживает, что запрашиваемое доменное имя принадлежит к домену com. Клиенту возвращается ссылка на сервер имён, обслуживающий домен com;
    
- Клиент обращается к **серверу имён, обслуживающему домен com**. Этот сервер находит в своей базе данных записи о сервере имён, обслуживающем домен yahoo.com. Ссылка на этот сервер имён возвращается клиенту.
    
- Клиент обращается к **серверу имён, обслуживающему домен yahoo.com**. Сервер имён находит в своей базе данных запись о хосте movies.yahoo.com. Соответствующий этому имени IP-адрес возвращается клиенту.

### TTL записей DNS

Большинство организаций настраивают DNS записи а затем не меняют их в течении многих лет, поскольку записи часто запрашиваются но редко обновляются, кэширование очень эффективно для повышения производительности сети

#### Что такое TTL

Время показывает как долго каждый шаг цепочки DNS будет кэшировать запись. TTL отслеживается в секундах

Этот термин действительно не отражает нюансов несмотря на то что это определенно время жизни, это может иметь больше смысла, если вы думаете об этом как о времени выполнения запроса или о том как долго хранить эту DNS запись в кэше

## Основы SMTP

SMTP - сетевой протокол который предназначен для передачи электронной почты в сетях TCP/IP

Протокол предназначен для передачи исходящей почты с использованием порта TCP 25

В то время как электронные почтовые серверы и другие агенты пересылки сообщений используют SMTP для отправки и получения почтовых сообщений, работающие на пользовательском уровне клиентские почтовые приложения обычно используют SMTP только для отправки сообщений на почтовый сервер для ретрансляции. Для получения сообщений клиентские сообщения обычно используют POP3 или IMAP

![[Pasted image 20260626162732.png]]

SMTP это текстовый протокол, требующий соединения по которому отправитель сообщения связывается с получателем посредством выдачи командных строк и получения необходимых данных через надежный канал, в роли которого обычно выступает TCP соединение. SMTP сессия состоит из команд посылаемых SMTP клиентом и соответствующих ответов SMTP сервера

![[Pasted image 20260626162945.png]]

Пример Конверта SMTP

```
Клиент → Сервер 

EHLO mail.sender.com 
	└─ "Привет, я mail.sender.com" 

MAIL FROM:<boss@sender.com> 
	└─ "Письмо от этого адреса" (куда слать NDR при ошибке) 

RCPT TO:<alice@company.com> 
RCPT TO:<bob@company.com> 
	└─ "Доставить этим двум" (Alice и Bob получат письмо) 
DATA 
└─ "Начинаю передавать само сообщение..." 

. 
	└─ "Сообщение закончилось" 
	
QUIT
```

Само сообщение 

```
From: "Иван Иванов" <boss@sender.com>         ← видит получатель
To: alice@company.com                          ← видит получатель
Cc: carol@company.com                          ← видит получатель
Subject: Отчёт за июнь
Date: Fri, 26 Jun 2026 10:00:00 +0300
Message-ID: <abc123@sender.com>
X-Mailer: Outlook 2024
Received: from mail.sender.com by mx.company.com  ← добавил сервер company.com
Received: from laptop by mail.sender.com           ← добавил сервер sender.com
                                               ← пустая строка = граница
Привет, высылаю отчёт.                        ← тело письма
...
```

При передаче по протоколу SMTP электронное письмо состоит из следующих частей:

 - Данные SMTP конверта, полученные сервером. Часть этих данных может отсутствовать в самом сообщении. Так например в RCPT TO (envelop to) содержится список получателей письма, при этом в самом письме получатель может быть не указан

Эта информация передается за пределы сервера только в рамках протокола SMTP и смена протокола при доставке почты (например на узле получателе в ходе внутренней маршрутизации) может приводить к потере этой информации. В большинстве случаев она недоступна конечному получателю, который использует не SMTP протоколы (POP3, IMAP) для доступа к почтовому ящику. Для возможности контролировать работоспособность системы эта информация обычно сохраняется в журналах почтовых серверов

Само сообщение(В терминологии SMTP - 'DATA'), которое в свою очередь состоит из следующих частей разделенных пустой строкой

- Заголовки письма - в них указывается служебная информация и пометки почтовых серверов, через которые прошло письмо, пометки о приоритете, указание на адрес и имя отправителя и получателя письма, тема письма и другая информация.
- Тело письма - в нем находится собственно сообщение письма и вложения, если они есть

Данные SMTP конверта. Содержат параметры которые задаются одноименными командами:

- Параметр HELO/EHLO содержит имя `FQDN` отправляющего узла, либо адрес литерал отправляющего узла
- Параметр MAIL FROM - содержит EMAIL отправителя. Адрес может быть произвольным (в том числе несуществующим, что допускается протоколом SMTP, однако RFC 5321 содержит рекомендацию использовать или Null Reverse-Path для специальных сообщений или существующий emailю), но именно это значение используется для формирования уведомлений об ошибках доставки сообщений (а не значение из поля From заголовка сообщения). Этот адрес так же может проверяться при первичной проверке на спам и в иных случаях. При отправке сообщения обычный почтовый клиент формирует MAIL FROM из содержимого поля From
- Параметр RCPT TO - наиболее важное содержимое конверта для доставки почты, содержит электронный адрес одного или нескольких получателей. При формировании SMTP конверта RCPT TO может использоваться несколько раз. При отправке сообщения обычный почтовый клиент формирует список для RCPT TO содержимого полей сообщения To Cc и Bcc

Заголовки письма. Описываются стандартами RFC. Заголовки отделяются от тела письма пустой строкой. Они используются для журналирования прохождения письма и служебных пометок
	 В заголовках обычно указываются:
	 - Почтовые серверы через которые прошло письмо (каждый почтовый сервер добавляет информацию о том от кого он получил это письмо)
	 - Информацию о том, похоже ли это письмо на спам, информацию о проверке антивирусами, уровень срочности
	 - Программа с помощью которой было создано письмо

Поскольку заголовки являются служебной информацией, то почтовые клиенты часто скрывают из от пользователей при обычном чтении писем, но предоставляют возможность увидеть эти заголовки, если возникает потребность в более детальном анализе письма.

Заголовки обычно добавляются снизу вверх, то есть каждый раз, когда к сообщению нужно добавить заголовок, он дописывается первой строкой, перед всеми предыдущими

Помимо служебной информации, заголовки письма так же хранят и показываемую пользователю информацию, это обычно отправитель письма, получатель, тема и дата отправки.

Заголовки сообщения могут содержать только 7 битные символы. При необходимости использовать национальные символы в каких то полях требуется использование кодировок, как правило Base64 или Quoted-Printable

Часто используемые заголовки 

 - Return-Path: **(RFC 821, RFC 1123)** — адрес возврата в случае неудачи, когда невозможно доставить письмо по адресу назначения. Может отличаться от MAIL FROM и заголовков From:, Sender: или Reply-To:, но обычно совпадает с MAIL FROM.
    
- Received: **(RFC 822, RFC 1123)** — данные о прохождении письма через каждый конкретный почтовый сервер. При прохождении через несколько почтовых серверов (обычная ситуация), новые заголовки дописываются над предыдущими, в итоге журнал перемещения будет записан в обратном порядке (от ближайшего к получателю узла к самому дальнему).
    
- MIME-Version: **(RFC 1521)** — версия MIME, с которым это сообщение создано. Зачастую этот заголовок создаётся раньше всех остальных, поэтому он обычно самый первый (то есть последний в списке).
    
- From: **(RFC 822, RFC 1123, RFC 1036)** — имя и адрес отправителя (именно в этом заголовке появляется текстовое поле с именем отправителя). Может не совпадать с return-path и даже не совпадать с заголовком SMTP MAIL FROM:.
    
- Sender: **(RFC 822, RFC 1123)** — отправитель письма. Добавлено для возможности указать, что письмо от чьего-то имени (from) отправлено другой персоной (например, секретарём от имени начальника). Некоторые почтовые клиенты показывают сообщение при наличии sender и from как «сообщение от 'sender' от имени 'from'». Sender является информационным заголовком (и также может отличаться от заголовка SMTP MAIL FROM).
    
- To: **(RFC 822, RFC 1123)** — имя и адрес получателя. Может содержаться несколько раз (если письмо адресовано нескольким получателям). На основании этого поля формируется содержимое поля SMTP RCPT TO.
    
- Cc: **(RFC 822, RFC 1123)** — (от англ. carbon copy) содержит имена и адреса вторичных получателей письма, к которым направляется копия. Участвует в формировании поля SMTP RCPT TO, как и поле «To».
    
- Bcc: **(RFC 822, RFC 1123)** — (от англ. blind carbon copy) содержит имена и адреса получателей письма, чьи адреса не следует показывать другим получателям. Участвует в формировании поля SMTP RCPT TO, как поля «To» и «Cc», но отсутствует в отправляемом сообщении.
    
- Reply-To: **(RFC 822, RFC 1036)** — имя и адрес, куда следует адресовать ответы на это письмо. Если, например, письмо рассылается роботом, то в качестве Reply-To будет указан адрес почтового ящика, готового принять ответ на письмо.
    
- Message-ID: **(RFC 822, RFC 1036)** — уникальный идентификатор сообщения. Состоит из адреса узла-отправителя и номера (уникального в пределах узла). Алгоритм генерации уникального номера зависит от сервера/клиента. Выглядит примерно так: AAB77AA2175ADD4BACECE2A49988705C0C93BB7B4A@example.com. Вместе с другими идентификаторами используется для поиска прохождения конкретного сообщения по журналам почтовой системы (почтовые системы фиксируют прохождение письма по его Message-ID) и для указания на письмо из других писем (используется для группировки и построения цепочек писем). Обычно создаётся почтовым клиентом в момент составления письма.
    
- In-Reply-To: **(RFC 822)** — указывает на Message-ID, для которого это письмо является ответом (с помощью этого почтовые клиенты могут легко выстраивать цепочку переписки — каждый новый ответ содержит Message-ID для предыдущего сообщения).
    
- Subject: **(RFC 822, RFC 1036)** — тема письма.
    
- Date: **(RFC 822, RFC 1123, RFC 1036)** — дата отправки письма.
    
- Content-Type: **(RFC 1049, RFC 1123, RFC 1521, RFC 1766)** — тип содержимого письма (HTML, RTF, Plain text) и кодировка, в которой создано письмо (см. ниже про кодировки).

Помимо стандартных, почтовые клиенты, серверы и роботы обработки почты могут добавлять собственные заголовки, начинающиеся с `X-`, например `X-Mailer` `X-MyServerNote-Ok`

- тело письма от заголовка отделяется пустой строкой

В теле сообщения допускаются только печатные символы. Поэтому для целей передачи бинарной информации применяются кодировки приводящие данные к 7 битному виду, например base64 или UUE.

### PTR записи

Так же в SMTP немаловажную роль играет PTR запись DNS, которая преобразует IP адрес в имя. Ее основная задача заключается в том, чтобы отсеять большую часть спама

Эта запись позволяет определить имя хоста с которого приходит почта. При получении почты, почтовый сервер делает два запроса

1. На получение имени по IP адресу
2. На получение IP адреса по имени отправителя

## POP3 IMAP

Для получения письма с почтового сервера используются протоколы POP3 и IMAP

POP3 забирает письмо с почтового сервера на клиент, а затем удаляет их с почтового сервера. IMAP хранит все письма только на почтовом сервере и никуда их не передает. Яркий пример IMAP это Gmail, Mail и так далее

В корпоративных сетях используется нечто среднее между POP3 и IMAP

Пример: 

![[Pasted image 20260626180933.png]]

Представим рассылку с почтового ящика yu.galtcev@humour.ru на jimmy.carr@humour.us письма с новыми шутками. Письмо создали, нажали кнопку "Отправить" - письмо оказалось на почтовом сервере домена `humour.ru` (192.168.76.52)

Почтовый сервер домена humour.ru генерирует DNS запрос MX-записи для домена humour.u и получает DNS ответ с содержанием

```
humour.us  MX 10 mx.humour.us 
```

Затем запрашивает А-Запись DNS для хоста mx.humour.us и получает от DNS сервера ответ "12.23.34.45". Затем инициирует соединение с IP адресом 12.23.34.45 по порту 25/TCP, потому что этот порт является общепринятым для SMTP

Содержимое SMTP конверта передается, оседает в почтовом ящике jimmy.carr@humour.us TCP-соединение завершается. Дж.Карр заходит в почтовый клиент, скачивает письмо по протоколам POP3/IMAP, читает его и смеется от души

## Суть протокола Whois


> [!NOTE] WHOIS
> Сетевой протокол прикладного уровня. Его основное применение: получение регистрационных данных о владельцах доменных имен, IP адресов и автономных систем

Изначально цель появления системы WHOIS состояла в том, чтобы дать системным администраторам возможность искать контактную информацию других администраторов, IP адресов или доменных имен

Протокол подразумевает архитектуру клиент сервер и используется для доступа к публичным серверам баз данных регистраторов IP адресов и регистраторов доменных имен. В некоторых случаях whois сервер для определенного домена верхнего уровня содержит полную базу данных обо всех зарегистрированных доменах. В других случаях такой whois сервер содержит лишь самую базовую информацию и отсылает к whois серверам конкретных регистраторов.

Например на запрос вила "mail.ru" сервер whois вернет нам техническую информацию об этом домене

![[Pasted image 20260627161103.png]]

Запись обычно содержит:

- имя
- Контактную информацию "регистранта"(владельца домена) и регистратора (организации которая домен зарегистрировала)
- Имена DNS серверов
- дату регистрации
- дату истечения срока ее действия

Записи об IP адресах сгруппированы по диапазонам. (например 8.8.8.0 - 8.8.8.255) и содержат данные об организации, которой этот диапазон делегирован

Часто whois используется для проверки, свободно ли доменное имя или уже зарегистрировано. Теоретически это можно сделать просто открыв домен в браузере однако на практике зарегистрированное имя не всегда используется
