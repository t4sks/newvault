Атака когда злоумышленник внедряется между клиентом и может прослушивать трафик или инжектировать в него вредоносный контент

# Типы MITM атаки
- Packet sniffing (перехват пакетов) - захват незашифрованных пакетов данных, передаваемых по сети, как правило в открытых сетях WIFI
- Session hjacking - кража и использование токенов сессии для подмены личности пользователя 
- SSL стриппинг - принудительный даунгрейд HTTPS-соединения до незащищенного HTTP с целью кражи или подмены передаваемых данных
- DNS спуфинг - перенаправление трафика с легитимных сайтов на мошенические домены путем подмены DNS ответов
- IP спуфинг - формирование вредоносных IP пакетов маскирующихся под трафик доверенных систем
- Поддельная точка доступа WiFi - создание фиктивной сети для перехвата пользовательского трафика
# MIMT по Cyber Kill Chain 
MITM это техника которую используют на этапах эксплуатации и закрепления 
- Как эксплуатационная техника - MITM эксплуатирует доверие и ограничения ключевых протоколов в сети таких как ARP и DNS. Путем манипуляции этими протоколами атакующий может перехватить канал связи. Это акт захвата сессии, формы эксплуатации, поскольку это нарушает целостность сети и предоставляет противнику первоначальную точку опоры для прослушивания или активного манипулирования
- Как фаза закрепления - однажды атакующий может успешно занять MITM позицию, когда он контролирует поток данных и может использовать это как механизм доставки для вредоносных payloads. Например атакующий может инжектировать эксплоит в браузер, malware загрузчик или троян удаленного доступа в легитимные незашифрованные загрузки. Эти действия показывают фазу закрепления где атакующий обеспечивает закрепление за жертвой или развертывает дополнительные вредоносные инструменты в системе.

# Пример через ARP спуфинг
## Индикаторы атаки
- Дублирующиеся MAC адреса к IP - несколько MAC адресов претендуют на один и тот же IP адрес
- Незапрошенные ARP ответы - высокое количество ARP ответов без соответсвующих запросов
- Аномальный объем ARP трафика - большое количество ARP пакетов за короткий промежуток времени
- Нестандартная маршрутизация трафика - трафик перенаправляется через MAC адрес атакующего
- Паттерны перенаправления шлюза - несколько различных MAC адресов назначения для одного и того же IP адреса шлюза
- Циклы ARP проб и ответов 0 многочисленные ARP запросы вида `Who has 192.168.1.x? Tell 192.168.1.y`

# Атака через DNS
## Индикаторы атаки
- Множественные ответы для одного запроса - легитимный сервер и фейковый отвечают на один запрос. Это самый сильный идикатор
- DNS ответ из неизвестного IP адреса который ни соответствует ни одному из настроенных ответчиков 
- Подозрительно низкий TTL, атакующие используют очень низкие TTL 1-30, чтобы поддерживать подмененные записи недолговечными чтобы постоянно переподтверждать контроль над ними
- Незапрошенные DNS ответы. DNS ответ появляется без соответствующего запроса жертвы

# SSL Striping
Это техника атаки MITM когда атакующий перехватывает и модифицирует трафик устраняя или блокируя TLS шифрование между клиентом и сервером. В результате клиент переходит на назащищенное соединение по HTTP заместо HTTPS. При этом атакующий сохраняет защищенную версию HTTPS сессию с сервером, одновременно передавая жертве незашифрованный HTTP трафик - что позволяет перехватывать и похищать учетный данные

## Как это работает: 
![[Pasted image 20260606160453.png]]
- Жертва инициирует подключение к сайту
- атакующий перехватывает трафик например через ARP спуфинг
- Атакующий держит HTTP к серверу а сам отдает ответ по HTTP
- Жертва работает по HTTP и чувствительные данные идут в открытом виде
## Индикаторы такой атаки:
- Несоответствие начального запроса и ответа. Первый пакет от клиента идет на HTTPS, по 443 порту, следующие пакеты к тому же домену идут по 8- порту. Шифрованного канала, который должен быть установлен нет, трафик для того же хоста продолжает идти в открытом виде
- Редиректы и перезапись ссылок. В ответах HTTP видны коды 301 и 302, которые устойчиво уводят HTTPS запрос за HTTP ресурс. В норме редирект работает в обратную сторону с HTTP на HTTPS. Здесь направление инвертированное что то систематически разворачивает шифрованные запросы в открытые
- Ошибки сертификата. Если атакующий не переписывает ссылки а проксирует TLS напрямую, его сертификат не совпадает с настоящим. Тогда либо TLS хендшейк падает, либо браузер видит самоподписанный сертификат и ругается, Грамотный атакующий это прячет - но при прямом проксировании след остается
