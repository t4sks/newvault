# Процессы
Процесс представляет исполняемую программу, приложение может содержать один или несколько процессов. Процесс имеет множество компонентов разбитых на части для хранения и взаимодействия с ними. 
Каждому процессу предоставляются ресурсы для исполнения программы. У процесса есть виртуальное адресное пространство, исполняемый код, открытые дескрипторы системных объектов, контекст безопасности, уникальный идентификатор процесса, переменные среды, класс приоритета, минимальный и максимальный размеры рабочего набора и как минимум один поток выполнения

Процесс это ядро того как функционирует Windows. Процессы это ядро того как функционирует Windows, большая часть функциональности windows может быть реализована как приложение и иметь соответствующий процесс. Ниже приведены несколько примеров приложений по умолчанию запускающих процессы

- MsMpEng (Microsoft Defender)
- wininit (keyboard and mouse)
- lsass (credential storage)

Атакующие могут нацелиться на процессы для обхода детектирования и для того чтобы спрятать malware как легитимный процесс. Ниже приведен маленький перечень потенциальных векторов атак, которые злоумышленники могут использовать против процессов

- Process Injection
- Process Hollowing
- Process Masquerading

Процессы имеют много компонентов, их можно разбить на ключевые характеристики которые мы можем использовать для описания процессов на высоком уровне. В таблице ниже показаны критические части процессов и их назначение

| Компонент процесса            | Назначенин                                                                                               |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| Private Virtual Address Space | Адреса виртуальной памяти, выделяемые для данного процесса                                               |
| Исполняемая программа         | Определяет код и данные, хранящиеся в адресном пространстве                                              |
| Открытые дескрипторы          | Определяет дескрипторы системных ресурсов, доступные процессу                                            |
| Контекст безопасности         | Маркер доступа определяет пользователя, группы безопасности, привилегии и прочую информацию безопасности |

| Потоки                        | Фрагмент процесса, планируемый для выполнение                                                            |

# Threads
Поток это исполняемая единица используемая процессом и планируемая на основе параметров устройства

Параметры устройства могут варьироваться в зависимости от характеристик процессора и памяти, приоритета логических факторов а так же других факторов. 

Мы можем упростить определение потока: "Управление выполнением процесса"

Поскольку потоки управляют выполнением это часто используемый объект для атак. Злоупотребление потоками может использоваться само по себе для выполнения кода или же оно чаще используется в цепочках с другими вызовами API в рамках других методов

Потоки разделяют те же детали и ресурсы что и родительский процесс, такие как код, глобальные переменные и т.д. Потоки также имеют свои уникальные значения и данные описанные в таблице ниже

| Компонент                        | Назначение                                                                            |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| Стек                             | Все данные, относящиеся к конкретному потоку(Исключения, вызовы процедур и так далее) |
| Локальное хранилище потока (TLS) | Указатели для выделения хранилища под уникальную среду данных                         |
| Аргумент Стека                   | Уникальное значение присваиваемое кажэдому потоку                                     |
| Структура контекста              | Хранит значения машинных регистров, поддерживаемые ядром                              |
# Virtual Memory
Виртуальная память - критически важный компонент того, как внутренние механизмы Windows функционируют и взаимодействуют друг с другом. Виртуальная память позволяет внутренним компонентам работать с памятью так, как если бы они была физической, устраняя иск коллизий между приложениями. 

Виртуальная память предоставляет каждому процессу собственное виртуальное адресное пространство. Менеджер памяти используется для трансляции виртуальных адресов в физические. Наличие приватного виртуального адресного пространства и отсутствие прямой записи в физическую память, снижает риск повреждения данных процессами

Менеджер памяти также использует страницы и перемещения для управления памятью. Приложения могут использовать больше виртуальной памяти, чем выделено физической. Менеджер памяти решает эту проблему путем вытеснения (свопинга) страниц виртуальной памяти на диск. Эту концепцию можно визуализировать на схеме ниже

![[Pasted image 20260622152020.png]]
Теоретический максимум виртуального адресного пространства на 32 битной системе х86 составляет 4гб

Это пространство разделено пополам: нижняя половина (0x00000000 - 0x7FFFFFFF) выделяется процессам как описано выше. Верхняя половина (0x80000000 - 0xFFFFFFFF) выделяется для нужд операционной системы. Администраторы могут изменить это распределение для приложений, требующих большего адресного пространства через параметр increaseUserVA или AWE(Address Windowing Extensions)

Теоретический максимум виртуального адресного пространства на современной 64-битной системе составляет 256тб. Соотношение разбивки адресного пространства из 32 битной системы сохраняется в 64 битной

# Dynamic Link Libraries
DLL - это библиотека содержащая код и данные которые могут быть использованы более чем одной программой за раз

DLL используются как одно из ключевых механизмов выполнения механизмов в Windows. Использование DLL способствует модульности кода, эффективному расходу памяти и уменьшению занимаемого дискового пространства. Благодаря этому операционная система и программы загружаются быстрее, работают быстрее и занимают меньше места на диске.

Когда DLL загружается как функция в программе, она становится зависимостью этой программы. Поскольку программа зависит от DLL, злоумышленники могут атаковать DLL, а не сами приложения, чтобы получить контроль над частью выполнения или функциональности

- DLL Hijacking
- DLL Side-Loading
- DLL injection

DLL создаются так же как и любой другой проект или приложение - требуется лишь незначительное изменение синтаксиса. Ниже приведен пример DLL

```c++
#include "stdafx.h"
#define EXPORTING_DLL
#include "sampleDLL.h"
BOOL APIENTRY DllMain( HANDLE hModule, DWORD ul_reason_for_call, LPVOID lpReserved
)
{
    return TRUE;
}

void HelloWorld()
{
    MessageBox( NULL, TEXT("Hello World"), TEXT("In a DLL"), MB_OK);
}
```

Ниже представлен заголовочный файл DLL - он определяет какие функции импортируются и экспортируются

```c++
#ifndef INDLL_H 
	#define INDLL_H 
	#ifdef EXPORTING_DLL extern 
		__declspec(dllexport) void HelloWorld();
	#else extern 
		__declspec(dllimport) void HelloWorld(); 
	#endif 
#endif
```

DLL создана но остается вопрос как она используется в приложении
DLL можно загрузить в программу двумя способами: с помощью динамического связывания во время загрузки (load-time dynamic linking) или динамического связывания во время исполнения (run-time dynamic linking)
При загрузке через динамическое связывание во время загрузки приложение напрямую вызывает функции DLL, такой тип связывания требует наличия заголовочного файла (.h)  и библиотеки импорта (.lib). Ниже приведен пример вызова экспортированной функции DLL из приложения

```c++
#include "stdafx.h"
#include "sampleDLL.h"
int APIENTRY WinMain(HINSTANCE hInstance, HINSTANCE hPrevInstance, LPSTR lpCmdLine, int nCmdShow)
{
    HelloWorld();
    return 0;
}
```

При загрузке динамического связывания во время выполнения для загрузки DLL используется отдельная функция - `LoadLibrary` или  `LoadLibraryEx`. После загрузки необходимо вызывать `GetProcAddress` чтобы получить адрес экспортированной функции DLL. Ниже приведен пример загрузки DLL и импорта ее функции в приложении

```c++
...
typedef VOID (*DLLPROC) (LPTSTR);
...
HINSTANCE hinstDLL;
DLLPROC HelloWorld;
BOOL fFreeDLL;

hinstDLL = LoadLibrary("sampleDLL.dll");
if (hinstDLL != NULL)
{
    HelloWorld = (DLLPROC) GetProcAddress(hinstDLL, "HelloWorld");
    if (HelloWorld != NULL)
        (HelloWorld);
    fFreeDLL = FreeLibrary(hinstDLL);
}
...
```

В вредоносном коде, злоумышленники как правило используют динамическое связывание во время выполнения чем во время загрузки. Это объясняется тем, что вредоносной программе может потребоваться перемещение файлов между областями памяти, а перенос одной DLL проще в управлении чем импорт с использованием других файловых зависимостей.

# Interacting With Windows Internals
Взаимодействие с внутренностями Windows может казаться пугающим, но оно было значительно упрощено. Наиболее доступный и изученный способ взаимодействия с Windows Internals - использование вызовов Windows API. Windows API представляет нативную функциональность для работы с операционной системой. API включает Win32 API и реже используемый Win64 API.

Большинство компонентов Windows Internals требуют взаимодействия с физическим оборудованием и памятью. Ядро Windows управляет всеми программами и процессами и является мостом между всеми программными и аппаратными взаимодействиями. Это особенно важно, поскольку многие внутренние компоненты Windows так или иначе требуют работы с памятью

По умолчанию приложение не может напрямую взаимодействовать с ядром или модифицировать физическое оборудование - для этого требуется интерфейс. Проблема решается через режим работы процессора и уровни доступа.

Процессор Windows имеет пользовательский режим и режим ядра. Процессор переключается между этими режимами в зависимости от запрошенного доступа и режима.

Переключение между пользовательским режимом и режимом ядра обычно осуществляется через системные вызовы и вызовы API. В документации эта точка иногда называется точкой переключения (Switching Point)

|Пользовательский режим|Режим ядра|
|---|---|
|Нет прямого доступа к оборудованию|Прямой доступ к оборудованию|
|Создаёт процесс в изолированном виртуальном адресном пространстве|Выполняется в едином общем виртуальном адресном пространстве|
|Доступ только к «собственным» областям памяти|Доступ ко всей физической памяти|
Приложения запущенные в пользовательском режиме остаются в нем же до тех пор пока не будет выполнен системный вызов или обращение через  API. При системном вызове приложение переключает режим.

При рассмотрении того, как языки программирования взаимодействуют с Win32 API, этот процесс усложняется: приложение проходит через среду выполнения языка прежде чем обратиться к API. Наиболее типичный пример C#, который выполняется через CДК перед взаимодействием с Win32 API и выполнением системных вызовов.

Для демонстрации концепции взаимодействия с памятью мы внедрим окно сообщения в локальный процесс

Шаги записи окна сообщения в память

1. Выделить память локального процесса под окно сообщения
2. Записать/Скопировать окно сообщения сообщения в выделенную память
3. Выполнить окно сообщения из памяти локального процесса

Шаг 1 Используем `OpenProcess` для получения дескриптора указанного процесса

```c
HANDLE hProcess = OpenProcess(
    PROCESS_ALL_ACCESS, // Определяет права доступа
    FALSE,              // Дескриптор цели не наследуется
    DWORD(atoi(argv[1])) // Локальный процесс, переданный через аргументы командной строки
);
```

Шаг 2 Используем `VirtualAllocEx` для выделения области памяти под буфер с полезной нагрузкой 

```c
remoteBuffer = VirtualAllocEx(
    hProcess,               // Открытый целевой процесс
    NULL,
    sizeof payload,         // Размер выделяемой области памяти
    (MEM_RESERVE | MEM_COMMIT), // Резервирует и фиксирует страницы
    PAGE_EXECUTE_READWRITE  // Разрешает выполнение и доступ на чтение/запись к зафиксированным страницам
);
```

Шаг 3 Используем `WriteProcessmemory` для записи полезной нагрузки в выделенную область памяти

```c
remoteThread = CreateRemoteThread(
    hProcess,    // Открытый целевой процесс
    NULL,
    0,           // Размер стека по умолчанию
    (LPTHREAD_START_ROUTINE)remoteBuffer, // Указатель на начальный адрес потока
    NULL,
    0,           // Выполняется сразу после создания
    NULL
);
```
