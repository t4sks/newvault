## 🗺 Карта: путь письма и где SOC его проверяет

```
Отправитель (MUA) → SMTP → MTA отправителя → [интернет] → MTA получателя
   → антиспам/песочница → MDA → почтовый ящик → MUA получателя (POP3/IMAP)
```

| Этап | Что проверяет защита |
|---|---|
| Приём MTA получателя | SPF (IP отправителя), reverse DNS, RBL (блек-листы) |
| Содержимое | DKIM (подпись не тронута), антивирус вложений |
| Решение | DMARC (выравнивание с From) → accept/quarantine/reject |
| Детонация | песочница для вложений и URL |
| После доставки | SOC разбирает заголовки, URL, вложения по тикету |

> **Принцип для собеса:** «отправитель в письме (From) и реальный отправитель (по SPF/Return-Path) — это разные вещи. Вся почтовая безопасность крутится вокруг того, что SMTP сам по себе НЕ проверяет From».

## Почтовые протоколы

### SMTP — отправка
- [ ] Назначение: отправка и пересылка между серверами
- [ ] Порты: 25 (MTA↔MTA), 587 (submission, с аутентификацией), 465 (SMTPS)
- [ ] MTA / MUA / MDA — кто есть кто
- [ ] Конверт (envelope: MAIL FROM, RCPT TO) vs заголовки (header From) — ключевое отличие!

### POP3 — получение (скачивание)
- [ ] Порты: 110, 995 (POP3S)
- [ ] Забирает письма и обычно удаляет с сервера (одно устройство)

### IMAP — получение (синхронизация)
- [ ] Порты: 143, 993 (IMAPS)
- [ ] Письма остаются на сервере, синхронизация между устройствами

📖 **Читать:** Selectel/любой обзор «SMTP, POP3, IMAP» (база) ; для практики SMTP-команд — RFC 5321 кратко

🛠 **Потрогать (SMTP-диалог вручную — поймёшь, почему spoofing тривиален):**
```bash
# подключись к почтовому серверу и «представься» кем угодно:
nc smtp.example.com 25
# далее вводи построчно (сервер ответит кодами 220/250):
HELO test.local
MAIL FROM:<boss@victim-company.com>     # ← вот тут можно написать ЛЮБОЙ адрес
RCPT TO:<you@yourmail.com>
DATA
From: "CEO" <boss@victim-company.com>
Subject: test
.
QUIT
```
Задание: пройди SMTP-диалог, обрати внимание — сервер не спросил подтверждения, что ты boss@. Это и есть корень email spoofing. (На чужих серверах сейчас relay закрыт — делай на своём Postfix в ВМ.)

💬 **Промпт мне:** «Объясни разницу envelope (MAIL FROM) и header From на примере, почему получатель видит header From, а SPF проверяет envelope — и как на этом строится spoofing».

## Заголовки письма (главный инструмент разбора)

- [ ] **Received** — цепочка серверов, через которые прошло письмо (читать снизу вверх)
- [ ] **From** — видимый отправитель (легко подделать)
- [ ] **Return-Path** — куда вернётся при ошибке (envelope sender, проверяется SPF)
- [ ] **Reply-To** — куда уйдёт ответ (трюк: From легит, Reply-To на атакующего)
- [ ] **Message-ID** — уникальный идентификатор
- [ ] **Authentication-Results** — итог проверок SPF/DKIM/DMARC
- [ ] Служебные признаки спуфинга: `AuthAs: Anonymous`, `dkim=none`

📖 **Читать:** Habr «Дорогая, давай займёмся spoofing-ом» (разбор заголовков фальшивого письма) https://habr.com/ru/articles/1037092/ ; anti-malware «Безопасность почты SPF/DKIM/DMARC» https://www.anti-malware.ru/practice/methods/SPF-DKIM-DMARC-email-protection

🛠 **Потрогать:**
```
1. В Gmail: открой письмо → ⋮ → "Показать оригинал" → увидишь все заголовки + SPF/DKIM/DMARC статус
2. В Outlook: File → Properties → Internet headers
3. Сравни в подозрительном письме: From vs Return-Path vs Reply-To
4. Проследи Received снизу вверх — откуда реально пришло
5. Вставь заголовки в MXToolbox Header Analyzer для наглядности
```
Задание: возьми 3 письма (легит + 2 из спама), для каждого выпиши: From, Return-Path, Reply-To, результаты SPF/DKIM/DMARC. Определи, какие подделаны и по каким признакам.

💬 **Промпт мне:** «Сгенерируй учебные заголовки трёх писем: (1) легитимное, (2) спуфинг с провалом SPF, (3) хитрое — From легит, но Reply-To чужой. Проведи меня по разбору каждого, на что смотреть».

## Аутентификация почты: SPF / DKIM / DMARC

> Это спросят почти наверняка. Запомни одной фразой: **SPF проверяет IP, DKIM проверяет подпись (целостность), DMARC связывает их с видимым From и решает, что делать.**

### SPF (Sender Policy Framework)
- [ ] TXT-запись в DNS со списком IP/серверов, имеющих право слать от домена
- [ ] Проверяет envelope-домен (Return-Path), НЕ видимый From
- [ ] Ломается при пересылке (forwarding меняет IP)

### DKIM (DomainKeys Identified Mail)
- [ ] Криптоподпись заголовков письма приватным ключом
- [ ] Получатель проверяет публичным ключом из DNS (selector._domainkey)
- [ ] Гарантирует целостность (письмо не изменено в пути)

### DMARC
- [ ] Политика поверх SPF+DKIM: none (мониторинг) / quarantine (в спам) / reject (отклонить)
- [ ] Требует **выравнивания (alignment)** результата с видимым From — закрывает дыру SPF
- [ ] Шлёт отчёты владельцу домена

📖 **Читать:** Habr «SPF, DKIM, DMARC как работают вместе» https://powerdmarc.com/all-about-spf-dkim-dmarc/ ; синтаксис записей https://habr.com/ru/articles/343128/ ; почему обходятся https://habr.com/ru/companies/globalsign/articles/650485/

🛠 **Потрогать:**
```bash
dig txt example.com | grep spf                          # SPF-запись
dig txt _dmarc.example.com                              # DMARC-политика (p=none/quarantine/reject)
dig txt selector1._domainkey.example.com                # DKIM публичный ключ
# проверь свой/любой домен на MXToolbox: spf, dkim, dmarc по очереди
```
Задание: проверь 3 домена (крупный банк, мелкая фирма, свой). Сравни их DMARC-политику (p=). Объясни, чей домен легче подделать и почему.

💬 **Промпт мне:** «Объясни SPF/DKIM/DMARC через аналогию (конверт, печать, правила почты). Потом — 3 сценария: SPF=pass но фишинг; DKIM сломался при пересылке; DMARC=none и что это значит для защиты».

## Атаки на почту

- [ ] **Email spoofing** — подмена From (SMTP не проверяет)
- [ ] **Phishing / spear phishing / whaling** → детали в [[06 - Фишинг]]
- [ ] **BEC (Business Email Compromise)** — имперсонация руководителя ради перевода денег
- [ ] **Open relay abuse** — чужой неправильно настроенный SMTP рассылает спам
- [ ] **Email bombing** — заваливание ящика письмами (часто для сокрытия другого алерта)
- [ ] **Typosquatting / lookalike домены** — micros0ft.com, paypa1.com
- [ ] **DKIM replay** — переотправка легитимно подписанного письма (свежая техника)
- [ ] **Malware-вложения** — docx-макросы, LNK, ISO, архивы с паролем → [[05 - ВПО (Malware)]]
- [ ] **Credential harvesting** — ссылка на поддельную страницу логина
- [ ] **OAuth-фишинг** — выманивание токена доступа, а не пароля

📖 **Читать:** Habr (Bastion) «Современный фишинг: OAuth, DKIM replay» https://habr.com/ru/companies/bastion/articles/962214/ ; spoofing-разбор https://habr.com/ru/articles/1037092/

🛠 **Потрогать:**
```bash
# проверка домена на open relay (только свой/разрешённый!):
# nc target 25 → попробуй MAIL FROM внешнего → RCPT TO внешнего → если принял = open relay
# проверь lookalike: сравни визуально похожие домены

```
Задание: для учебного «фишинга» определи тип атаки по признакам (spoofing / BEC / credential harvesting / typosquatting). Сопоставь каждую атаку с тактикой MITRE (большинство — Initial Access, T1566 Phishing).

## ⚠️ Частые ошибки на собеседовании (почта)

- **Путать порты:** SMTP 25/587, POP3 110, IMAP 143 (защищённые 465/995/993). Назови уверенно.
- **Говорить «SPF проверяет From»** — нет, SPF проверяет envelope (Return-Path), а DMARC уже связывает с видимым From.
- **Думать, что SPF=pass = письмо безопасно** — атакующий может слать с легит-хостинга или подменить только видимый From; нужен DMARC с alignment.
- **Не знать разницу POP3 и IMAP** — POP3 скачивает и удаляет, IMAP синхронизирует и оставляет на сервере.
- **Забывать про Reply-To** — классический трюк: From выглядит легитимно, а ответ уходит атакующему.
- **На вопрос про защиту почты называть только антивирус** — назови SPF/DKIM/DMARC + SEG + песочницу + обучение пользователей.

## 🧪 Тест для повторения

> [!question]- 1. SMTP, POP3, IMAP — назначение и порты (включая защищённые).
> SMTP — отправка/пересылка (25 MTA↔MTA, 587 submission, 465 SMTPS). POP3 — получение со скачиванием и удалением (110, 995). IMAP — получение с синхронизацией, письма остаются (143, 993).

> [!question]- 2. В чём разница envelope (MAIL FROM) и header From?
> Envelope (MAIL FROM / Return-Path) — служебный адрес для маршрутизации и возврата, его проверяет SPF. Header From — видимый получателю отправитель. Они могут различаться — на этом строится spoofing.

> [!question]- 3. Почему email spoofing вообще возможен?
> SMTP исторически не проверяет подлинность отправителя — поле From задаётся произвольно при отправке. Без SPF/DKIM/DMARC получатель не может убедиться, что письмо реально от заявленного домена.

> [!question]- 4. SPF, DKIM, DMARC — что делает каждый одной фразой?
> SPF — проверяет, имеет ли право IP слать от домена (envelope). DKIM — криптоподпись, гарантия целостности письма. DMARC — политика поверх обоих + выравнивание с видимым From + что делать при провале (none/quarantine/reject).

> [!question]- 5. Письмо прошло SPF, но это фишинг. Как так?
> SPF проверяет только envelope-домен (Return-Path) и IP, а не видимый From. Атакующий шлёт с легитимного хостинга (SPF их IP разрешает для своего домена) либо подменяет только header From. Поэтому нужен DMARC с alignment.

> [!question]- 6. Какие заголовки смотреть при разборе письма?
> Received (путь, читать снизу вверх), From vs Return-Path vs Reply-To (несоответствия), Authentication-Results (SPF/DKIM/DMARC), Message-ID, домен на typosquatting.

> [!question]- 7. Что такое BEC?
> Business Email Compromise — имперсонация/компрометация делового адреса (часто руководителя) ради мошеннического перевода денег или кражи данных. Опирается на доверие и срочность, часто без вредоносных вложений — поэтому антивирус бессилен.

> [!question]- 8. Что такое open relay и чем опасен?
> Неправильно настроенный SMTP-сервер, принимающий и пересылающий почту от кого угодно кому угодно. Злоумышленники используют его для анонимной рассылки спама/фишинга от чужого имени; домен попадает в блек-листы.

> [!question]- 9. Трюк с Reply-To — в чём суть?
> From выглядит легитимно (или спуфнут под легит-домен), но Reply-To указывает на адрес атакующего. Жертва отвечает «начальнику», а ответ уходит мошеннику. Частый приём в BEC.

> [!question]- 10. Почему SPF ломается при пересылке (forwarding)?
> При пересылке промежуточный сервер меняет IP отправителя. Если его IP не в SPF-записи исходного домена — SPF-проверка на финальном сервере проваливается. Эту проблему закрывает DKIM (подпись переживает пересылку).

> [!question]- 11. Что такое DKIM replay-атака?
> Переотправка легитимно подписанного DKIM-письма множеству жертв. Подпись валидна (письмо реально подписано доменом), но используется злоумышленником для массовой рассылки, проходящей проверки. Современная техника обхода.

> [!question]- 12. Что такое DMARC-политики p=none/quarantine/reject?
> none — только мониторинг, письмо доходит (сбор отчётов). quarantine — подозрительное в спам. reject — отклонить на этапе приёма. Чем строже политика, тем труднее подделать домен.

> [!question]- 13. С какой техникой MITRE связано большинство почтовых атак?
> T1566 (Phishing) тактики Initial Access, с саб-техниками: T1566.001 (вложение), T1566.002 (ссылка), T1566.003 (через сервис). В Kill Chain — этап Delivery.

> [!question]- 14. Какие классы СЗИ защищают почту?
> Secure Email Gateway (SEG) — фильтрация на входе; антиспам + RBL; песочница для вложений/URL; SPF/DKIM/DMARC; URL-rewriting/time-of-click; DLP для исходящих; обучение пользователей.

> [!question]- 15. Плейбук: пришёл тикет «подозрительное письмо». Первые шаги?
> Не открывать на рабочей машине. Заголовки (Received, From/Return-Path/Reply-To, Authentication-Results), репутация домена/отправителя, URL через urlscan/VT (без перехода), вложение через olevba/песочницу, поиск других получателей. Вердикт TP/FP → при TP блок отправителя/URL, поиск кто открыл, эскалация.
