Web приложения состоят из 3 уровней

- Web сервер - такие как nginx или apache
- Web Application - то что выполняет основную логику приложения
- Web Host - непосредственно сама машина на которой расположен сайт

Защита веб приложений должна исходить из этих 3 уровней
# Защита на уровне Web Application 

- Безопасный кодинг: избегание необезопасных функций, обеспечение правильной обработки ошибок, удаление чувствительной информации в ответах
- Валидация и Санитизация пользовательского ввода: Валидируйте и санитизируйте пользовательский ввод для предотвращения атак
- Контроль доступа: Ограничивайте доступ опираясь на роли пользователей

# Защита на уровне веб сервера

- Логирование: держать детализированные записи всех запросов в логах доступа
- Web Application Firewall: фильтровать и блокировать вредоносный трафик по правилам
- Content Delivery Network: снизить прямой контакт с сервером и использовать встроенные WAF интерфейсы

# Защита на уровне Хост машины

- Наименьшие привилегии: использовать минимально привилегированных пользователей для сервисов
- Усиление безопасности системы: Отключение ненужных служб и закрытие неиспользуемых портов
- Антивирус: добавить защиту конечной точки которая блокирует известное вредоносное ПО

# Советы по безопасности для всех трех уровней

- Сильная аутентификация: не давайте никому получить доступ к вашему коду, панелям админа или хостовым машинам
- Patch Managment: обновляться до последней версии программного обеспечения

# Детектирование различных видов атак

## Client Side
Атаки направленные на использование уязвимостей в браузере или устройстве пользователя. Эти атаки часто эксплуатируют уязвимости браузеров или заставляют пользователя сделать небезопасное действие для получения доступа к аккаунту или для того чтобы украсть чувствительную информацию. 

### Ограничения SOC
Так как атаки происходят на стороне пользователя без дополнительной защиты увидеть что то невозможно, потому что нам как аналитикам доступны только логи сервера и сетевой поток данных из за чего увидеть атаку на стороне браузера клиента является невозможным(Хотя по факту Stored и Reflected XSS увидеть можно)
## Server Side
Сосредоточены на сервере, и имеют более разрушительные последствия. 
### Плюсы для SOC
Как защитники мы может увидеть такие атаки потому что они оставляют целую цепочку улик если вы знаете их искать. Каждый веб запрос обрабатывается из за чего остается в логах или других мониторинговых системах

# Формат логов доступа
В основном логи включают следующую информацию о то какой запрос пришел

| Поле лога                                | Пример индикатора                                                                        |
| ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| 1.IP-адрес клиента                       | Известный вредоносный IP или адрес за пределами ожидаемого географического диапазона     |
| 2.Временная метка и запрошенная страница | Запросы в нетипичное время суток или повторяющиеся с высокой частотой за короткий период |
| 3.Код статуса                            | Многократные ответы 404 — страница не найдена                                            |
| 4.Размер ответа                          | Значительно меньше или больше стандартного размера ответа                                |
| 5.Referrer                               | Ссылающиеся страницы, не соответствующие обычной навигации по сайту                      |
| 6.User-Agent                             | Устаревшие версии браузеров или известные инструменты атак (например, sqlmap, wpscan)    |

### Ограничения логов
Логи доступа могут быть полезны но они все еще не отображают полной картины например содержимое POST запроса. Вот так например выглядит лог доступа
```
10.10.10.100 [12/Aug/2025:14:32:10] "POST /login HTTP/1.1" 200 532 "/home.html" "Mozilla/5.0"
```

Пример показывает метод запроса запрошенную страницу но не фактические учетные данные или полезную нагрузку, которая была отправлена в запросе.

# Detecting Web Shells

> [!NOTE] Web Shell
> Это программа которая загружается на веб сервер и позволяет удаленно выполнять команды, часто служат методом первоначального доступа к системе. 

Часто Web Shell устанавливается из за file upload vuln, неправильной конфигурации сервера. Сама такая уязвимость возникает когда приложению не удается проверить тип файла, расширение или место назначения.

### Основные индикаторы для детекта веб шела
Необычные HTTP методы и паттерны запросов
- Повторяющиеся GET запросы с высокой скоростью могут означать что злоумышленник ищет допустимое место для оболочки
- POST запросы к допустимым местам загрузки после повторных GET запросов
- Повторяющиеся GET или POST запросы к одному и тому же файлу могут указывать на взаимодействие с веб оболочкой

#### Подозрительные User-Agents и IP
User-Agent идентифицирует клиента отправляющего запросы к веб серверу и содержит информацию о браузере, устройстве и ОС

- Изменённые User-Agent'ы: `Mozilla/4.0+(+Windows+NT+5.1)` сокращён до `Mozilla/4.0`
- Устаревшие User-Agent'ы: `Mozilla/4.0 (compatible; MSIE 6.0)` — MSIE 6.0 вышел в 2001 году
- Заблокированные User-Agent'ы: например, `curl/1.XX.X` или `wget/1.XX.X`
- Подозрительные IP-адреса: в нормальных условиях сеть видит только внутренний трафик, поэтому внешний IP-адрес является аномалией
#### Query строки
Часть `URL` связывающая параметры со значениями: `example.php?query=somequery`
- Аномально длинные или подозрительные query строки, особенно содержащие ключевые слова вроде `cmd=` или `exec=`
- закодированные query строки `?query=whoami` в base64
#### Отсутствие Referrer
Referrer показывает URL страницы, с которой пользователь перешел на текущую

- Отсутcтвие referrer может указывать на активность web шела
- Существуют легитимные причины его отсутствия(Блокировка браузером из соображений приватности, прямой ввод URL)
#### Пример подозрительного веб запроса с перечисленными индикаторами:

1. Известный вредоносный или ненадежный IP
2. Аномальная временная метка - возможна за пределами рабочих часов
3. POST запрос с query строкой к вредоносному файлу
4. Нет Referrer - страница открыта напрямую что не всегда является валидным идентификатором 
5. Подозрительная строка User-Agent которая нетипична для браузера

# Auditd
Это встроенная утилита линукс которая отслеживает и записывает события, создавая журнал аудита. Для auditd можно создавать правила, которые определяют что будет записано в файл audit.log
Правила могут быть гибко настроены для соответствия определенным условиям, например когда запускаются определенные программы или изменяются файлы в определенном каталоге. Ниже показан пример где используется ausearch для поиска любых журналов соответствующих правилу web_shell
```
user@tryhackme$ ausearch -k web_shell time->Wed Jul 23 06:20:36 2025 // A log matching the web_shell rule
"name = /uploads/webshell.php"
"OGID = www-data"
```
## Корреляция веб логов и auditd
Эффективное обнаружение шелов требует корреляции нескольких источников логов. Совместный анализ логов веб доступа и ошибок с данными `auditd` дает более полную картину: позволяет установить был ли файл создан, изменен или выполнен и каким пользователем или процессом. Подозрительный POST запрос в веб логах можно связать с событием аудита, содержащим системный вызов `creat` или `execve` - это покажет что скрипт записал файл или выполнил команды. Совокупность этих данных позволяет восстановить последовательность атаки

- Возможность создавать целевые запросы для выявления признаков вредоносной активности, включая веб-шелы

# Анализ файловой системы
Веб шел должен где то лежать, соответственно анализ файловой системы хоста веб сервера является самым эффективным, но некоторые платформы такие как wordpress и django хранят содержимое страниц в базе данных, а не в файловой системе, поэтому вредоносный код может быть внедрен в записи, темы или настройки поэтому обнаружить его будет сложнее

Ниже показаны базовые директории для размещения веб шел на apache и nginx

- Apache: `/var/www/html` базовая на большинстве Linux дистрибутивах
- Nginx: `/usr/share/nginx/html` базовая на многих Linux машинах

Даже если задан пользовательский корневой путь, злоумышленники могут угадать или просканировать распространенный каталоги для загрузки, такие как `/uploads/`, `/images/`, или `/admin/`, так же временные каталоги могут быть использованы не должным образом если права настроены неверно 

## Подозрительные или рандомные имена файлов
Такая схема может использоваться для того чтобы обойти защиту. Например:

- Файлы с исполняемыми расширениями такие как `.php` `.jsp` и так далее
- Двойные расширения файлов, такие как `img.jpg.php`
### Полезные команды
Мы можем использовать find для поиска недавно измененных скриптов. Или grep для нахождения подозрительного содержимого в файлах
```
find /var/www -type f -name "*.php" -newerct "2025-07-01" ! -newerct "2025-08-01" /var/www/html/uploads/awebshell.php // Web shell created between the dates above.

grep -r "eval(" wp-content /wp-content/uploads/awebshell2.php :eval(b64_dd($['cmd'])); // Web shell containing eval(
```

# DOS и DDoS
DoS - когда атака для отказа сервиса происходит с одного устройства и используется один канал связи
DDoS - когда атака происходит с большого количества устройств ботнет сети

## Типы DoS атак:

| DoS тип                       | Описание                                                                                                                                                                                                                                    |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Slowloris                     | Отправка большого количества частично переданных HTTP запросов, с целью занять ресурсы сервера(Например отправляется только часть запроса а вторая часть запроса приходит позже и держит ресурсы сервера на поддержку открытого соединения) |
| HTTP Flood                    | Отправка большого количества HTTP запросов для перегрузки сервера                                                                                                                                                                           |
| Oversized Query               | Принуждение сервера обработки, больших и ресурсоемких запросов                                                                                                                                                                              |
| Login/Form Abuse              | Перегрузка логики аутентификации попытками входа в систему или сбросом пароля                                                                                                                                                               |
| Faulty Input Validation Abuse | Эксплуатация недостатков в обработке входных данных                                                                                                                                                                                         |
## Индикаторы DoS атакм

| Индикатор                          | Пример                                             | Описание                                                                                                                                                                                                                                                         |
| ---------------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Высокая частота запросов           | `10.10.10.100 → 1000 GET /login`                   | Ресурсоёмкая страница, например `/login`, подвергается массовому потоку запросов с целью перегрузки механизмов аутентификации. Страницы входа часто становятся целью атак, поскольку каждый запрос может инициировать проверку пароля и обращение к базе данных. |
| Необычные User-Agent               | `curl/7.6.88 → /index` (многократные запросы)      | Злоумышленники используют устаревшие или нестандартные значения User-Agent, чтобы маскировать трафик или обходить фильтры. Трафик от инструментов вроде `curl` или `Python-urllib/3.x` может указывать на автоматизированную атаку.                              |
| Географические аномалии            | IP-адреса из разных стран мира                     | Легитимный трафик обычно поступает из ограниченного числа регионов, где находятся реальные пользователи. Распределённая ботнет-сеть может использовать IP-адреса со всего мира.                                                                                  |
| Всплески по времени                | `50 запросов за 1 секунду → /search`               | Резкое увеличение количества запросов в течение одной секунды создаёт неестественный шаблон трафика, характерный для автоматизированных атак.                                                                                                                    |
| Ошибки сервера (5xx)               | Значительный рост ошибок `503 Service Unavailable` | Внезапное увеличение количества ответов с кодами ошибок сервера (500–511) свидетельствует о том, что ресурсы системы исчерпываются и сервис испытывает перегрузку из-за атакующего трафика.                                                                      |
| Злоупотребление логикой приложения | `GET /products?limit=999999`                       | Атакующий формирует запросы, заставляющие сервер обрабатывать чрезмерно большие объёмы данных, что приводит к замедлению работы сервиса для всех пользователей.                                                                                                  |
## Ресурсы на которые нацелен атакующий
Когда цель атакующего провести DoS атаку на сервис он фокусируется на эндпоинте где нагрузка на сервис больше всего, такие страницы как `/login`, или поиск на форумах это первостепенные цели потому что они заставляют сервер обработать запрос и вернуть ответ, что делает такие запросы более дорогими для обработки чем возврат статического контента

Частые цели атакующего и причины 

- `/login` - включает в себя процесс аутентификации
- `/search` - включает в себя комплексные запросы к базе данных
- `/api` эндпоинты - критические для динамической доставки контента
- `/register` или `/signup` - запросы к бд на запись и валидацию входных значений
- `/contact` или `/feedback` - запросы записи к бд и запуск взаимодействий по email
- `/cart` или `/checkout` - запросы сессионного управления, проверка инвентаря или процесс оплаты
