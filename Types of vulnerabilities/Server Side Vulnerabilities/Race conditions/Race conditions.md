> [!note] Определение Race Conditions
> Тип уязвимости тесно связан с уязвимостями бизнес логики. Возникают когда сайты обрабатывают запросы конкурентно друг другу без достаточных мер защиты. В результате несколько независимых потоков одновременно взаимодействуют с одними и теми же данными, это приводит к столкновению и непреднамеренному поведению приложения. Атака состояния гонки использует точно выверенное время отправления запросов, чтобы вызвать такие преднамеренные столкновения и эксплуатировать это

Промежуток времени в течении которого возможно столкновение, называется "окном гонки"
или race window. Это может быть доля секунды между двумя взаимодействиями с базой данных
Как и с уязвимостями бизнес логики, влияние состояние гонки очень сильно зависит от приложения и конкретной функциональности в которой оно возникает
# Состояние гонки для превышения лимитов или Linit overrun
Тип уязвимости когда состояние гонки позволяет превысить некоторый лимит, установленный бизнес-логикой 
Пример: интернет магазин который позволяет ввести промокод на этапе оформления заказа, чтобы получить разовую скидку. Для применения нужно выполнить следующие шаги: 
1 Проверить что код не использовался ранее
2 Применить скидку к итоговой сумме заказа
3 Обновить запись в бд, чтобы отразить факт использования кода

![[Pasted image 20260313200547.png]]

Если позже мы захотим использовать код снова то проверки не дадут нам это сделать
Что если пользователь который ни разу не применял этот промокод, попытался применить его дважды почти одновременно

![[Pasted image 20260313200541.png]]

Приложение проходит через временное подсостояние, то есть состояние в которое в которое оно входит и из которого выходит до завершения обработки запроса и заканчивается когда он обновляет базу данных чтобы записать уже использованный код. Это создает небольшое окно гонки, в течении которого можно повторно получать скидку столько раз сколько это возможно сделать за окно
Существуют многие вариации такого рода атаки, например
- Многократное погашение подарочной карты
- Многократную оценку товара
- Снятие или перевод средств сверх баланса счета
- Повторное использование одного решения CAPTCHA
- Обход ограничения скорости(rate limit) при защите от перебора
Превышение лимитов это подтип изъянов "от момента проверки до момента использования"
Time-to-check to time-of-use TOCTOU
# Выявления и эксплуатация состояний гонки для превышения лимитов с помощью Repeater
Процесс выявления и эксплуатации состояний гонки для превышения лимитов относительно прост
1 Найдите одноразовую или ограниченную по скорости конечную точку, которая влияет на безопасность или полезна иным образом
2 Отправить несколько запросов к этой конечной точке в быстром темпе, чтобы проверить удастся ли превысит лимит
Основная сложность это синхронизировать запросы так, чтобы хотя бы два окна гонки совпали, вызвав столкновение. Это окно часто считается в миллисекундах и может быть даже еще меньше
Даже если отправить запросы в точности одновременно, на практике есть различные неконтролируемые и непредсказуемые внешние факторы, влияющие на то, когда сервер обработает каждый запрос и в каком порядке![[Pasted image 20260313201720.png]]
В Burp Suite 2023.9 автоматически подбирается версия в зависимости от HTTP
Для HTTP/1 используется синхронизация по последнему байту (last byte synchronization)
Для HTTP/2 используется техника "атака одним пакетом"(single packet attack)
Атака одним пакетом позволяет нейтрализовать network jitter, используя один TCP пакет для 20-30 запросов одновременно ![[Pasted image 20260314094417.png]]
Часто достаточно двух запросов, отправка большого количества помогает компенсировать внутренние задержки(server side jitter). Это полезно на этапе первичного обнаружения

# Поиск и эксплуатация состояний гонки для превышения лимитов с Turbo Intruder
Turbo Intruder требует небольшие знания Python, но подходит для более сложных атак, тех что требуют множества повторов, ступенчатого тайминга или крайне большого числа запросов.
Чтобы использовать атаку одним пакетом в Turbo Intruder
1 Убедится что целевой хост поддерживает HTTP/2. Так как атака одним пакетом несовместима с HTTP/1
2 Установите параметры конфигурации движка запросов, `engine=Engine.BURP2` и `currentConnections=1` 
3 При постановке запросов в очередь сгруппируйте их назначив им именованные "ворота" с помощью аргумента `gate` и метода `engine.queue`.
4 Чтобы отправить все запросы в группе, используйте `engine.openGate()`
```
def queueRequests(target, wordlists):
		engine = RequestEngine(endpoint=target.endpoint,
		                        concurrentConnections=1,
		                        engine=Engine.BURP2
		                        )
		
		# queue 20 requests in gate '1'
		for i in range(20):
		    engine.queue(target.req, gate='1')
		
		# send all requests in gate '1' in parallel
		engine.openGate('1')
```
Подробнее можно посмотреть в шаблоне `race-single-packet-attack.py`

# Скрытые многошаговые последовательности
Часто один запрос запускает целую многошаговую последовательность внутри, переводя приложение через несколько скрытых состояний, в которые оно входит и из которых выходит до завершения обработки запроса. Назовем их подстостояними "sub-states"

Если мы можем определить один или несколько HTTP запросов, которые взаимодействуют с одними и теми же данными, потенциально можем воспользоваться этими подсостояниями, чтобы обнаружить чувствительные ко времени вариации логических изъянов, распространенных в многошаговых процессах. Это позволяет эксплуатировать состояние гонки, выходящее далеко за пределы превышений лимитов.

Например MFA которая позволяет выполнить первую часть входа с известными данными, а затем пройти непосредственно в приложение с помощью принудительного перехода, обхода MFA полностью
Пример уязвимого кода
```
session['userid'] = user.userid
if user.mfa_enabled:
    session['enforce_mfa'] = True
    # generate and send MFA code to user
    # redirect browser to MFA code entry form
```
По факту это многошаговая последовательность в рамках одного запроса, важно то, что она проходит через подсостояние, в котором пользователь временно имеет валидную сессию входа, но MFA еще не применено, атакующий потенциально может эксплуатировать это, отправляя запрос на вход вместе с запросом к чувствительной, требующей аутентификации конечной точке
## Методология
Чтобы выявлять и эксплуатировать скрытые многошаговые последовательности, рекомендуется использовать следующую методологию
### 1 Прогнозирование потенциальных столкновений
Тестировать каждую конечную точку непрактично. После обычного покрытия целевого сайта вы можете сократить число конечных точек для тестирования, задавая себе следующие вопросы:
Является ли конечная точка критичной для безопасности? Многие конечные точки не затрагивают критичные функции, поэтому их тестирование нецелесообразно
Есть ли потенциал для столкновений? Для успешного столкновения нужны два и более запроса, запускающих операции над одной и той же записью. Например рассмотрим следующие варианты сброса пароля

![[Pasted image 20260314191234.png]]

В первом примере параллельные запросы на сброс пароля для двух разных пользователей вряд ли приведут к столкновению, так как изменяются две разные записи, но во второй реализации вы можете редактировать одну и ту же запись запросами для двух разных пользователей.
### 2 Поиск подтверждений
Чтобы определить точку для атаки, нужно сначала установить базовый уровень поведения конечной точки в нормальных условиях. Это можно сделать в Burp Repeater, сгрупировав все запросы и используя опцию `Send group in sequence`

Затем отправьте ту же группу запросов одновременно, используя атаку одним пакетом(или синхронизацию по последнему байту если HTTP/2 не поддерживается), чтобы минимизировать сетевой джиттер, в Burp Repeater это делается через `Send group in parallel` либо использовать Turbo Intruder

Любые отклонения могут быть зацепкой. Ищи любую форму отличную от того, что вы наблюдали при корректном тестировании, это включает изменения в одном или нескольких ответах, а так же вторичные эффекты такие как иное содержание писем или видимое изменение поведения приложения после теста
### 3 Доказательство теории
Постарайся понять что происходит, уберите лишние запросы и убедитесь, что эффект воспроизводим

Продвинутые Race Conditions могут приводить к необычным и уникальным примитивам, поэтому путь, к максимальному воздействию не всегда очевиден, может помочь предоставление каждого состояния гонки как структурной слабости, а не изолирующей уязвимости
# Состояние гонки между несколькими конечными точками
Возможно самая интуитивная форма таких уязвимостей это когда вы отправляете запросы к нескольким конечным точкам одновременно
Один из классических примеров для магазина это когда мы добавляем товар в корзину, оплачиваем а затем добавляем еще товары и через принудительный переход попадаем на страницу подтверждения заказа
Вариация этой уязвимости может возникать когда проверка платежа и подтверждение заказа выполняются в рамках обработки одного запроса, state machine статуса может выглядеть примерно так

![[Pasted image 20260314193618.png]]

В этом случае мы потенциально можем добавить больше товаров в корзину в окно гонки между моментом когда платеж уже проверен и моментом окончательного подтверждения заказа
# Выравнивание окон гонки между несколькими конечными точками
При тестировании таких состояний гонки мы можем столкнуться с проблемой синхронизации окон для каждого запроса, даже если отправлять их строго одновременно с помощью техники одного пакета

![[Pasted image 20260314193938.png]]

Эта проблема возникает из-за
- Задержки вызванные сетевой архитектурой, например задержка при установлении фронтендом нового соединения с бекендом, протокол так же может существенно влиять
- Задержки вызванные обработкой конкретных конечных точек. Разные конечные точи по природе различаются по времени обработки иногда значительно, в зависимости от выполняемых операций
## Connection Warming
Задержки соединений с бэкендом обычно не мешают атакам состояния гонки, потому что они задерживают параллельные запросы примерно одинаково, и те остаются синхронными. Важно уметь отличать такие задержки от задержек, вызванных логикой конкретных конечных точек. Один из способов это подготовить соединение одним или несколькими несуществующими запросами и посмотреть выровняются ли оставшиеся времена обработки. В Burp Repeater попробуйте добавить `GET` запрос к главное странице в начало группы вкладок, затем использовать `Send group in sequence(single connection)`
Если первый запрос все еще обрабатывается дольше, но остальные теперь обрабатываются в небольшой временной вилке, то можно игнорировать кажущуюся задержку и продолжать тест как обычно
