> [!info] Многофакторная аутентификация
> Существуют сайты которые требуют проходить 2FA в качестве метода защиты
> Проверка биометрических факторов - для веб сайтов не является практичной, но часто встречается аутентификация основанная на "чем то, что вы знаете, что то что у вас есть" Обычно требуется чтобы пользователь ввел пароль и временный проверочный код из внешнего физического устройства
> Иногда злоумышленник может получить одно свойство для аутентификации, основанный на знании, но одновременное получение второго фактора из внешнего источника значительно менее вероятно. По этой причине двухфакторная аутентификация является более безопасной, но она будет на столько надежной на сколько надежна ее реализация. Плохая реализация можно обойти или даже полностью проигнорировать

> [!warning] ВАЖНО
> Преимущества 2FA достигаются только при проверке нескольких разных факторов, проверка одного и того же фактора разными способами не настоящая 2FA. 
> Пример: 2FA по электронной почте, хотя пользователь вводит пароль и код подтверждения, доступ к коду зависит лишь от знания учетных данных для почтового аккаунта, следовательно фактор знания просто проверяется дважды

### Токены двухфакторной аутентификации
Коды считывает пользователь с какого то физического устройства. Многие веб сайты с высоким уровнем безопасности теперь предоставляют пользователям, специальное устройство для этой цели, например токен RSA или устройство с клавиатурой, которое вы можете использовать для доступа к своему онлайн-банкингу или рабочему ноутбуку. 
Так же веб приложения отправляют коды на мобильный в виде текстового сообщения, хотя технически это все еще проверяет фактор владения
Во первых код передается по SMS, а не генерируется самим устройством. Это создает возможность перехвата кода. 
Во вторых существует возможность SIM-сваппинга, при котором злоумышленник получает симку с номером жертвы а в последствии получает все SMS в том числе и ч кодом подтверждения

### Обход двухфакторной аутентификации
Иногда реализация двухфакторной аутентификации некорректна на столько что ее можно просто обойти
Если сначала предлагают ввести пароль, а потом потом код подтверждения на другой странице, то фактическим пользователь оказывается в состоянии, вошел в систему еще до ввода кода. В таком случае стоит проверить можно ли напрямую перейти к "доступным после входа страницам" после завершения аутентификации. Иногда сайт фактически не проверят прошли ли вы второй шаг прежде чем загрузить страницу

## Ошибки логики при 2FA
Иногда из-за неправильной логики 2FA после завершения пользователем первого этапа аутентификации сайт недостаточно проверяет что именно тот же пользователь выполняет второй шаг

> [!note] Пример
```
POST /login-steps/first HTTP/1.1
Host: vulnerable-website.com
...
username=carlos&password=qwerty
```
Пользователь входит в аккаунт под обычными данными
После ему назначается cookie относящаяся к его аккаунту, после чего его переводят на другой этап аутентификации
```
HTTP/1.1 200 OK
Set-Cookie: account=carlos

GET /login-steps/second HTTP/1.1
Cookie: account=carlos
```
И при отправке кода подтверждения запрос будет использовать cookie чтобы понять к какому аккаунту пытается получить доступ пользователь, в этом случае мы можем попытаться войти используя другие учетные данные, но затем изменить значение cookie account на любое произвольное при отправке сообщения 
```
Было:
POST /login-steps/second HTTP/1.1
Host: vulnerable-website.com
Cookie: account=carlos
...
verification-code=123456
=========================
Станет:
POST /login-steps/second HTTP/1.1
Host: vulnerable-website.com
Cookie: account=victim-user
...
verification-code=123456
```
Это очень опасно потому что злоумышленник сможет перебрать код подтверждения, что позволит ему входить в аккаунты произвольных пользователей, опираясь только на имя, ему даже не нужно знать пароль пользователя
### 2FA broken logic Пример лабы
Нужно воспользоваться тем что веб приложение не проверяет кому дает доступ к 2FA, поэтому мы меняем пользователя во время отправки запроса 
на carlos в результате наши cookie должны выглядеть так
```
Cookie: verify: carlos
```
а весь `GET` запрос так:
```
GET /login2 HTTP/2
Host: 0a73001b03e23dd185b1f8e0004800fc.web-security-academy.net
Cookie: verify=carlos
...
```
После этого перед нами страница на которой мы уже пишем код для нашего `carlos`
тут обыкновенный брутфорс с помощью Burp используем режим `Bruteforce`, указываем длину для payload а так же символы которые необходимо перебрать

## Перебор кодов подтверждения
Как и с паролями сайты должны предпринимать шаги для предотвращения брутфорса 2FA, так как код состоит из 4 или 6 цифр без адекватной защиты перебрать очень быстро
Некоторые сайты стараются предотвратить это с помощью выхода из системы при вводе нескольких неверных кодов, но по факту это не является эффектинвым способом для защиты и злоумышленник может автоматизировать даже этот шаг
