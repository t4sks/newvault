> [!info] 
> Для веб сайтов использующих вход по паролю, пользователи либо самостоятельно регистрируют ее, либо получают от администратора. Такая учетная запись связана с уникальным именем пользователя и с секретным паролем, который пользователь вводит в форме входа для аутентификации. 
> В такой модели знания секретного пароля считается достаточным доказательством личности пользователя, это означает что веб сайт компрометируется если атакующий сможет получить или угадать учетные данные другого пользователя. Этого можно добиться разными способами

# Атаки перебором (Brute force attack)

Процесс угадывания пароля, с помощью автоматизации, веб сайты которые не имеют защиты от перебора по факту являются очень уязвимыми
## Перебор имен
Имена пользователей можно легко угадать, если они используют один шаблон, например адрес электронной почты, Пример: `firstname.lastname@somecompany.com`, но даже при отсутствии очевидного шаблона учетные записи с высокими привилегиями создаются с использованием предсказуемых имен, таким как `admin` или `administrator`
Стоит проверить не раскрывает ли вебсайт потенциальные имена пользователей публично, можно ли получить доступ к профилям без входа, даже если фактически содержимое полей скрыто, имя, используемое в профиле, иногда совпадает с именем для входа, так же проверьте HTTP ответы на предмет раскрытия адресов электронной почты. Встречаются случаи, когда ответы содержат адреса электронной почты пользователей с высокими привилегиями, таких как администраторы или тех поддержка 
## Перебор паролей
Пароли аналогично можно перебирать, при этом сложность зависит от надежности пароля, обычно сайты принимают политику паролей которая вынуждает пользователей создавать пароли с высокой энтропией, которые сложно взломать с помощью перебора обычно это включает 
- Минимальное количество символов
- Смесь строчных и заглавных букв
- Содержание хотя бы одного специального символа
Пароли с высокой энтропией сложно взломать компьютеру но мы можем использовать уязвимость человека, потому что вместо создания сильного пароля пользователи выбирают запоминающийся пароль и пытаются запихать его в рамки, например, `mypassword` превращается в `Mypassword1!` или `Myp3$$w0rd` 
В случаях когда политика требует постоянной смены пароля то пользователи так же часто делают незначительные и предсказуемые изменения пароля, например `Mypassword1!` станет `Mypassword2!` или `Mypassword1?`
Зная это атаки перебором могут стать намного более изощренными и эффективными
## Перечисление имен пользователей:
При таком способе мы можем определить действителен ли данный логин путем наблюдения за изменением поведения сайта, при такой технике следует обращать внимание на 
- **Статус-код:** возвращаемый HTTP код будет одинаковым для подавляющего большинства попыток потому что они будут неверными, если вернется другой код, то возможно имя пользователя будет правильным
- **Сообщения об ошибке:** Иногда возвращаемое сообщение об ошибке отличается в зависимости от того неверен ли только пароль или и пароль и имя пользователя. Лучшей практикой является использование одинаковых сообщений об ошибках, но мелкие опечатки проскакивают, достаточно отличия в один символ даже если символ не виден на отрисованной странице
- **Времени ответа:** Если большинство запросов обрабатываются за сопоставимое время, любые отклонения могут указывать что на сервере что то странное, это еще один признак, что угаданное имя может быть валидным, Например сайт может проверять правильность пароля только если имя пользователя действительно. Этот шаг может увеличить время ответа, пусть это и тонко, но атакующий может сделать задержку более заметной введя очень длинный пароль обработка которого займет больше времени
## Примеры решений:
**Username enumeration via subtly different responses**
Используем два листа которые предоставляет сама лаба и получаем вот такой пейлоад где нам нужно перебрать все возможные комбинации, делает это в burp `clasterbomb`  используем перебор, в caido используем `matrix` 
```
POST /login HTTP/2
Host: 0aa4008d0407352d80b0bcfb00e20027.web-security-academy.net
...
Priority: u=0, i

username=payload&password=payload
```
 **Username enumeration via response timing** 
 при решении у нас указано что нас будут блокировать по ip, поэтому можно использовать заголовок `X-Forwarded-For` с указанием любого значения, в этой конкретной лабе, если хочется более точных значений так как там передается IP то следует создать лист с ip. Сама лаба указывает на то что у нас будет задержка при ответе, у нас есть валидная запись `wiener:peter` которая входит очень быстро, для проверки теории, введем очень большой пароль в результате чего приложению потребуется время чтобы обработать пароль и ответить, тогда увидим что ответ по времени увеличился, пробуем найти валидного юзера через такой прием, первые запросы c использованием `pitchfork`(параллельно отправляет две строчки с разных файлов на разные пейлоады) :
 ```
POST /login HTTP/1.1
Host: 0ab5004d041606e080cf80ad000500d3.web-security-academy.net
...
X-Forwarded-For: payload_numbers

username=payload_Usernames&password=sdagfsggfsggggsgsfgfsgsdgsdgsdfgdgsfgsgdasrzgtdfggdfsgfdhsdfhgshdfshdfgshdgfshdgshfddfhhfsd
 ```
 получим что один пользователь из списка обрабатывался очень долго, значит возможно он есть в системе, пробуем второй запрос уже с нашим юзером 
 ```
 POST /login HTTP/1.1
Host: 0ab5004d041606e080cf80ad000500d3.web-security-academy.net
...
X-Forwarded-For: payload_numbers


username=ai&password=payload_passwords
 ```
 и  таким образом находим валидный пароль для нашего юзера

## Слабая защита от перебора 
Атака перебором включает множество неудачных попыток до успеха, логически защита от перебора строится на том чтобы максимально затруднить автоматизацию процесса и снизить скорость с которой атакующий может выполнять вход, наиболее распространенные метода защиты
- Блокировка учетной записи к которой пытаются получить доступ при слишком больше числе неудачных попыток входа 
- Блокировка IP адреса удаленного пользователя при слишком частых попытках входа подряд
Оба подхода обеспечивают разную степень защиты но ни один не уязвим, особенно если реализован с ошибками
Можно столкнуться с тем что IP блокируется при слишком большом количестве неудачных попыток входа, но в некоторых реализациях сбрасывается если владелец успешно входит, это значит что атакующему, достаточно входить в свою учетную запись чтобы не получить достижение лимита
По факту можно вставить свои учетные данные в словари и такая защита будет бесполезна 

**Пример лабы с блоком по IP** 
### Broken brute-force protection, IP block пример лабы
 В лабораторной работе каждый наш 4 неудачный вход блокирует нас на одну минуту, я придумал написать 2 скрипта которые дают 1 имя для успешного входа и 2 для теста, и так же с паролями, 1 который мы 100 знаем и 2 которые нужны для брутфорса, в итоге запускаем `Intruder` в режиме `PitchFork` и перебираем, в результате находим то что нам нужно, ГЛАВНОЕ выключить количество запросов за раз, до 1 штуки потому что елси отправлять 10 параллельно то не получится 
 
 **Еще один способ защиты это блокировка учетной записи**, обычно при заданном числе неудачных попыток, Как и в случае обычных ошибок при входе ответы сервера указывающие на то что учетная запись заблокирована могут помочь злоумышленнику подсчитать имена пользователей.
 Блокировка  учетной записи обеспечивает определенную степень защиты от целенаправленного взлома конкретной учетки, но такой подход не позволяет предотвратить атаки при которых злоумышленник пытается получить доступ к любой случайной учетной записи
 
 Техника такого взлома: 
 - Во первых попробуйте создать список кандидатов которые 100% будут иметь учетные записи, Осуществимо либо перечислением либо просто на основе поиска распространенных имен
 - Выбрать очень короткий список паролей которые скорее всего использует хотя бы один пользователь, важно чтобы число выбранных паролей не превышало допустимое число попыток входа, т.е. Если лимит 3 попытки нужно выбрать не более 3 догадок подряд
 - С помощью `Burp Intruder` попробуйте каждый из выбранных паролей с каждым из кандидатов имен пользователей, таким образом мы можем попытаться перебрать каждый аккаунт не инициируя блокировку, по факту нужен лишь один пользователь который использует один из паролей чтобы скомпроментировать учетную запись. 
 
 Блокировка аккаунта не защищает от атаки `credential stuffing` - которая подразумевает использование огромного словаря `username:password` составленного из подлинных учетных данных, украденных при утечках, `Credential stuffing` опирается на то что многие люди переиспользуют одни и те же имена имя и пароль для нескольких сайтов, следовательно есть шанс что некоторые учетные данные из словаря так же действительны на целевом сайте, Блокировка учетной записи не защищает от такой атаки потому что для каждой учетной записи попытка идет только один раз, `Credential Stuffing` особенно опасен тем что иногда позволяет атакующему скомпроментировать множество разных аккаунтов одной автоматизированной атакой.
### Username enumeration via account lock Пример лабы
В лабораторной есть уязвимость которая связана с логикой блокировки аккаунта, начинаем с перебора всех доступных имен, которые нам даны чтобы проверить сколько раз нужно ввести неправильный пароль чтобы заблокировать аккаунт, используем `Intruder` при этом указываем что нужно отправить каждый запрос по 5 раз, для этого `nullpayload` и смотрим какой аккаунт даст заблокированного пользователя, по итогу в моем случае это `agenda`, дальше запускаем брутфорс по всем паролям и получаем что на одном из паролей другая длина ответа и там нет надписи что запись заблокирована, поэтому вот ошибка в логике что при вводе правильного пароля она не разблокируется а просто покажет страницу авторизации, используем наш пароль и успешно сдаем лабу
## User Limimts 
Другой способ попробовать защититься от брутфорса это использовать лимиты для юзера, то есть при слишком большом числе запросов на вход за короткое время приводит к блокировке вашего IP, обычно он может быть разблокирован одним из следующих способов
- Автоматически после истечения времени
- Вручную админом
- Вручную пользователем после успешного прохождения капчи
Ограничение скорости иногда предпочитают блокировке учетной записи, потому что оно меньше подвержено перечислению имен пользователей и DOS, тем не менее это все еще не полностью безопасно. Как было видно на примере одной из работ существует несколько способов которыми атакующий может манипулировать своим видимым IP чтобы обойти блокировку. 
Так как лимиты основаны на скорости HTTP запросов отправляемых с IP адреса пользователя, иногда также возможно обойти эту защиту если удастся передать несколько паролей одним запросом 
### Broken brute-force protection, multiple credentials per request пример лабы
при проверке запроса видим что приложение отправляет данные в следующем формате
```
{
"username":"carlos",
"password":"moscow"
}
```
то есть как `json` объект можно попробовать отправить много запросов через одно соединение так как мы используем `HTTP/2` c помощью `Turbo intruder`, но это не сработает потому что можно отправить в `json`  объекте массив паролей и он проверит их все и если хотя бы один подошел выдаст сессию

## Базовая HTTP аутентификация 
Старая, простая и легкая во внедрении все равно означает что может попасться в приложениях, При таком виде аутентификации клиент получает от сервера токен аутентификации который сформирован как: `base64(username:password)` Этот токен хранится и управляется браузером, который автоматически добавляет его в заголовок `Authorization` каждого последующего запроса следующим образом: 
```
Authorization: Basic base64(username:password)
```
Это не является безопасным методом
Во первым предполагает многократную отправку учетных данных пользователем с каждым запросом. Если сайт так же не внедряет HSTS(принудительное использование HTTPS ) учетные данные могут быть перехвачены в атаке MITM
Во вторых базовая реализации HTTP-аутентификации не содержит защиты от перебора, поскольку токен состоит исключительно из статических значений, он может быть уязвим к перебору
В третьих она уязвима для атак связанных с сессиями, а в особенности к CSRF, от которых сама по себе такая аутентификация не защищает
В некоторых случаях эксплуатация такой уязвимости не может дать атакующему доступ к неинтересной странице, но помимо представления дополнительной поверхности атаки, учетные данные, раскрытые таким образом, могут быть использованы в других контекстах
