## Сохранение состояния входа

> [!info] Основное
> Это позволяет сохранить сеанс даже если браузер закрыт, за это отвечает галочка запомнить меня или остаться в системе
> Функциональность часто реализуется с помощью  генерации токена "remember me" который после сохраняется в файле cookie. Так как наличие cookie файла позволяет эффективно обойти весь процесс входа в систему, рекомендуется сделать так, чтобы файл cookie было невозможно угадать, но некоторые веб приложения генерируют их на основе предсказуемых значений, таких как имя пользователя и метка времени, в некоторых случаях используется даже пароль. 
> Такой подход не является безопасным, если атакующий может создать собственную учетную запись и изучить свой cookie, разобравшись с методом его генерации. Разобравшись в формуле, он может попытаться подобрать куки других пользователей с помощью перебора, чтобы получить доступ к их аккаунтам

По сути некоторые сайты думают что cookie зашифрован а значит его невозможно угадать даже если он использует предсказуемые значения. Это может быть верно при корректной реализации, но шифрование cookie с помощью Base64, не дает никакой защиты, даже использование корректного шифрования однонаправленной хэш функции не является особенно надежным, если атакующий легко определит используемый алгоритм шифрования и при этом соль не применяется, потенциально можем перебрать cookie просто хэшируя словари с пользователями и паролями, так же этот метод позволит обойти лимиты и блокировки при брутфорсе
Даже если невозможно создать свою учетную запись можем воспользоваться такими методами как XSS, чтобы украсть файл Cookie другого пользователя и на его основе определить как он создан
Если веб сайт создан с использованием платформы с открытым исходным кодом, ключевые детали создания файла могут быть публично задокументированы
Иногда есть возможность получить пароль из cookie напрямую даже если он захеширован, хешированные версии паролей доступны онлайн, поэтому если пароль пользователя присутствует в одном из таких списков, то "расшифровка кэша" сводится к вставке в поисковую систему и это говорит о важности использования соли
### Brute-forcing a stay-logged-in cookie пример лабы
указано что мы можем войти в свой профиль с помощью куки сохранения состояния, изучив куки стало понятно что оно зашифровано в base64 а сам вид имеет: `name:md5(password)`
тогда пишем программу для создания словаря с нужным нам форматом cookie 
```python
import hashlib  
import base64  
  
with open('passwords.txt', encoding="utf-8") as f:  
    for a in f:  
        a=a.strip()  
        md5hash=hashlib.md5(a.encode()).hexdigest()  
        data = f"carlos:{md5hash}"  
        base64result = base64.b64encode(data.encode()).decode()  
        print(base64result)
```
после этого запускам `intruder` с запросом типа `GET /my-account` а после ждем хотя бы один код 200 и забираем нужную нам cookie
### Offline password cracking пример лабы
здесь нам прямо говорят что в комментариях есть XSS, и что нужно украсть куки и дешифровать их по факту используем сразу более защищеный вариант для XSS
```

```
и таким образом забираем куки нашего `carlos` после чего просто дешифруем из base64 а потом вставляем hash в любой онлайн поисковик хэшей
в результате у меня hash это `onceuponatime` заходим в учетку удаляем аккаунт и все лаба решена

## Сброс пароля пользователя
На практике пользователи забывают свой пароль поэтому добавляют возможность его сбросить, потому что обычная аутентификация по паролю невозможна, сайты должны полагаться на другие методы чтобы убедится что это реальный пользователь сбрасывает собственный пароль. Из за этого функциональность сброса пароля по своей сути опасна и должна быть выполнена очень надежно
Есть несколько способов сброса пароля: 
### Отправка по электронной почте
Отправка пользователям пользователем их текущего пароля никогда не должна быть возможна, вместо этого некоторые сайты генерируют новый пароль и отправляют его по электронной почте.
Пересылки по небезопасным каналам стоит избегать. В данном случае безопасность опирается на то что сгенерированный пароль действует очень короткий срок или пользователь обязан будет сменить его, в ином случае такой подход уязвим для атак MITM
Электронная почта в целом не считается безопасной, потому что почтовые ящики не предназначены для хранения конфиденциальной информации, так же многие пользователи автоматически синхронизируют почту между несколькими устройствами по небезопасным каналам 
### Сброс пароля с помощью URL 
Более надежный способ сброса пароля это отправлять пользователям уникальный URL, ведущий на страницу сброса пароля, менее безопасные реализации этого метода используют URL с легко угадываемым параметром для идентификации аккаунта, чей пароль сбрасывается
> [!note] Пример
```
http://vulnerable-website.com/reset-password?user=victim-user
```
Здесь мы можем просто заменить параметр user, указав любое известное нам имя пользователя, а после попадем на страницу где установим новый пароль для произвольного пользователя
Лучшей реализацией является генерация токена с высокой энтропией, который трудно угадать и построением URL сброса на его основе, в идеале такой токен не должен давать подсказок о том чей пароль сбрасывается
> [!note] Пример
```
http://vulnerable-website.com/reset-password?token=a0ba0d1cb3b63d13822572fcff1a241895d893f659164d4cc550b421ebdd48a8
```
Когда пользователь посещает URL сайт автоматически должен проверить существование токена на сервере, в случае успеха, понять пароль какого пользователя должен быть сброшен. Токен должен иметь малый период жизни и уничтожаться сразу после сброса пароля.
Некоторые сайты не проверяют токен повторно при отправке формы сброса. В этом случае атакующий может просто открыть форму для сброса своей учетной, удалить токен и использовать эту страницу для сброса пароля произвольного пользователя
Если URL в письме генерируется динамически он так же может быть уязвим к отравлению сброса пароля, в этом случае атакующий потенциально может украсть токен другого пользователя и использовать его чтобы сменить пароль жертвы
### Password reset broken logic пример лабы

^d1e0b3

В задании сказано что нужно получить доступ к учетной записи пользователя для этого нужно воспользоваться функцией сброса пароля, здесь логика нарушена в том плане, что приложение не проверяет токен авторизации при отправке формы сброса пароля поэтому мы можем указать любого пользователя и любой пароль, для нахождения такой уязвимости следует обратиться к запросам которые создает сервер, и разобраться как работает этот функционал, то есть просто меняем токен на любой другой и меняем пароль у нужного нам пользователя

## Смена паролей пользователя 
Смена пароля чаще всего включает в себя ввод текущего пароля и затем нового пароля дважды. Эти страницы по сути опираются на тот же процесс соответствия имени пользователя и текущего пароля, что и обычная страница входа, следовательно они могут быть уязвимы к тем же техникам 
Функционал смены пароля может быть особенно опасной если она позволяет атакующему обращаться к ней напрямую без входа под целевым пользователем. Например если имя пользователя передается в скрытом поле, атакующий может отредактировать это значение в запросе, нацелившись а других пользователей. Это также может быть использовано для перечисления имен пользователей и перебора паролей
### Password brute-force via password change пример лабы
здесь указывается что есть уязвимость в смене пароля
начинаем перебирать варианты и тестировать приложение

далее я проверил что будет если ввести правильный пароль и два пароля которые совпадают, выкидывает на страницу авторизации и заставляет ждать минуту, поэтому брутфорс со сменой пароля нам не подходит
